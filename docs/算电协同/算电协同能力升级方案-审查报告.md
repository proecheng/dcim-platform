**方向成立，但 V1.0 不可直接进入开发，需先修正以下问题（3 项 P0 阻断 + 5 项 P1 + 3 项 P2）。**

## 1. 🔴 P0 阻断级问题（必须先解决）

### P0-1 核心假设冲突：现有体系把"IT 负载"定义为刚性不可转移

**方案断言**（V1.0 §5.2）："让算力做主要柔性资源""算力跟随绿电做时移/迁移"，并称"❌ 无 IT 工作负载建模"。

**真实代码**：
- `backend/app/services/datacenter_shift_strategy.py:62`
  ```python
  NON_SHIFTABLE_DEVICES = {'UPS', 'IT_SERVER', 'IT_STORAGE', 'NETWORK_SWITCH', 'CORE_ROUTER'}
  SHIFTABLE_DEVICES = {'LIGHTING', 'OFFICE_AC', 'WATER_PUMP', 'FAN'}  # :63
  ```
- `docs/算力中心特殊约束实现状态报告.md` §11.5.1 公式：`最大可转移功率 = 总功率 × (制冷占比 × 0.4 + 其他占比 × 0.6)` —— **IT 占比根本不进入可转移量**。
- 且 IT 负载**已被建模**（并非"完全空白"）：`datacenter_shift_strategy.py:22` 导入 `CabinetITLoad`；`pue_calculator.py:95` 用 `device.is_it_load`；`environment_context_service.py:125` 已实时计算 `it_load_percent`。

**影响**：方案核心（算力柔性化）与现有"IT 即刚性"的全部安全约束（ASHRAE 温度、N+1 冗余、UPS≤80%、PUE 1.2–2.0）的设计前提正面冲突。若不解决，要么方案落不了地，要么会破坏现有约束体系。

**修正**：必须显式区分**两个不同抽象层**，而不是把"IT 负载"整体改成柔性：
- **设施用电层（现状，保持刚性）**：`power_devices.is_it_load` = 机柜/服务器作为"用电体"，继续不可转移。
- **算力作业层（新增，柔性）**：只有 **AI 训练 / 离线批处理**这类**可中断、可延迟的作业**才是柔性资源；在线推理/关键业务仍刚性。新增的算力作业调度**叠加在设施层之上**（"先调作业，作业再驱动服务器功率变化"），不能直接把 `IT_SERVER` 从 `NON_SHIFTABLE_DEVICES` 拿掉。
- 落地方式见 P0-2（复用 `DispatchableDevice`，新增 `compute_*` 作业类型）。

### P0-2 大量"新增"实为重复造轮子：已存在"V3.0 电费综合优化系统"

**方案断言**（V1.0 §5.2/§7）：把 `compute_clusters/compute_workloads`、`datacenter_sites`、`energy_sources`、`market_prices`、`demand_response_events` 等列为**全新表**，并称"各模块各自为战、无统一协同大脑"。

**真实代码**（`backend/app/models/energy.py` 顶部即标注 `# V3.0 电费综合优化系统`）：

| 方案"新增"的东西 | 现实中**已存在**的等价物 | 证据 |
|------------------|----------------------|------|
| 算力/可调负荷柔性分级 | `DispatchableDevice` —— **6 类通用可调度负荷**：`shiftable/curtailable/modulating/generation/storage/rigid`，含 `allowed_periods/forbidden_periods/curtail_ratio/ramp_rate/forecast_curve/priority` | `energy.py:1288`、`:1296` |
| `coordination/plan` 调度输出 | `DispatchSchedule` —— **0–95 共 96 个 15 分钟时段**，action `on/off/charge/discharge/curtail`，含 `power_setpoint/expected_saving/status` | `energy.py:1375` |
| `energy_sources`（光伏/储能） | `PVSystemConfig`（kWp/效率/可调度）、`StorageSystemConfig`（容量/充放功率/SOC/循环成本） | `energy.py:1357`、`:1334`；demo 已播种 `demo/router.py:208-254` |
| `datacenter_sites`（多站点） | `Site`（sites）—— `site_code/address/network_config(VPN/专线)/status`，且有 `user_sites` 多租户 | `spatial.py:23` |
| `demand_response_events` / VPP 调控 | `VppDispatch`（vpp_dispatches）—— **Story 33.2 已实现** VPP 指令接收/执行，`command_type=down_adjust/up_adjust`，含 `aborted_schedule_id`（中止预冷计划的联动） | `thermal.py:174` |
| "协同大脑/联合优化" | 已有 **RL 优化器**：`rl_optimization_history/rl_training_logs/rl_model_states` + `optimizer.py`/`adaptive_optimization_service.py` + GNN | `energy.py:984` |
| 实时需量监控 | `RealtimeMonitoring`（realtime_monitoring） | `energy.py:1393` |

**影响**：V1.0 若按"新增"实施，将产生与 V3.0 系统**功能重叠的并行表与并行逻辑**，制造数据二义性与维护负担（这正是"漂移"的根源）。

**修正**：把 §7 的"复用 vs 新增"**重写为"复用 / 扩展 / 新增"三档**（见本报告 §4）。原则：
- 算力作业 → **扩展 `DispatchableDevice`**（新增 `device_type='compute_shiftable'/'compute_curtailable'`）+ 一张轻量 `compute_workloads` 只承载作业语义（deadline/SLA/优先级），通过 FK 挂到 `dispatchable_devices`。
- 调度输出 → **复用 `DispatchSchedule`**（已是 96 时段）。
- 源/储 → **扩展 `PVSystemConfig`/`StorageSystemConfig`**（补 `is_renewable/carbon_factor/wind` 语义），而非新建 `energy_sources`。
- 多站点 → **扩展 `Site`**（补绿电占比/本地电源结构/站间时延/算力余量），而非新建 `datacenter_sites`。
- VPP/DR → **复用 `VppDispatch`/`adjustable_loads`**，补一张"DR 事件/结算"表即可。

## 2. 🟠 P1 问题（数据 / 依赖一致性）

### P1-4 表命名漂移
- 方案写 `cue_histories`，并称"对标 `pue_histories`"——**真实表是 `pue_history`（单数）**（`energy.py:541`）。
- 现状命名本身就是**混用**：单数 `pue_history/demand_history/regulation_history/electricity_pricing/realtime_monitoring`，复数 `meter_points/power_devices/shift_plans/pricing_configs/capacity_histories`。记忆库"表名一律复数"的说法**不准确**。
- **修正**：新表碳指标命名为 `cue_history`（与直接对标的 `pue_history` 保持一致）；在方案里删掉"一律复数"的隐含假设，改为"与最相近的同类表保持一致"。

### P1-5 电价概念已严重重复，`market_prices` 是第 5–6 张
现存电价相关表已有：`electricity_pricing`(energy:430)、`electricity_prices`(vpp_data:68)、`pricing_configs`(energy:455)、`pricing_schemes`+`scheme_pricing_relations`+`pricing_scheme_audit_logs`(energy:1462+)。
- **修正**：不要新增 `market_prices`。真正缺的是**实时/现货价 + 动态碳因子时序**两类**信号**，应作为字段/小表挂到既有 `pricing_schemes` 体系，并复用 `docs/pricing-scheme-*` 既定设计。

### P1-6 缺失 demo 隔离字段（与 Epic 28 冲突）
现有核心表普遍带 `is_demo` + `data_source(seed/demo/real)`（`spatial.py:38-39` 等），这是 Epic 28「Demo 系统解耦与数据隔离」的硬约定。**V1.0 所有新表都没带这两个字段**。
- **修正**：所有新增/扩展表必须补 `is_demo`、`data_source`，否则绿电/碳/算力的 Demo 数据会污染真实数据，违反 Epic 28。

### P1-7 多套优化/执行栈并存，"协同大脑"会变成第 N 个孤岛
现状已有**至少 5 套**重叠的优化/调度/执行栈：① load_shift（`shift_plans/shift_executions`）② V3.0（`dispatchable_devices/dispatch_schedules`）③ energy 机会-执行（`energy_opportunities→execution_plans→execution_results`）④ precool（`precool_schedules`）⑤ VPP（`vpp_dispatches`）+ RL 优化器。
- **修正**：方案必须先回答"**谁是调度唯一事实源**"。建议把"算电协同引擎"定位为**编排层（orchestrator）**，统一调用既有 ④/⑤ 执行器并以 `DispatchSchedule` 为统一输出，而**不是再起一套并行表**。否则必然漂移。

### P1-8 "完全空白"判断不准，需改为"有物理、缺语义"
PV / 储能 / 多站点 / 可调度资源 / VPP 调控**都已存在**。真正空白的是**绿色与碳的语义层**：`is_renewable`、`carbon_factor`、`renewable_ratio`、`CUE`、绿证/绿电交易、风电类型。
- **修正**：§3.2 缺口表从"完全缺失"改为精确表述——"**物理资源已建模，绿电/碳属性未建模**"。这会显著降低工作量估算（V1.0 的 6–9 月明显高估）。

## 3. 🟡 P2 问题（边界 / 闭环）

### P2-9 闭环不完整
- 现状**已有成熟闭环**：机会→措施→执行计划→执行结果→`monitoring_records/effect_reports/measure_baselines`→RL 学习（`energy.py:855-1058`）。方案的"监测→决策→执行→核算→学习"应**接入这条线**，而非新画一条。
- **绿电/碳维度闭环缺失**：方案有了"测 CUE（监测）"和"进优化目标（决策）"，但**绿电/绿证采购、碳结算的"执行"与"事后核算（绿电占比是否真升到 80%、碳是否真降）"未接入 `effect_reports`**——闭环断在执行与核算之间。
- **算力路径是开环**：无真实 actuator（K8s/Slurm 未接），只能"建议+模拟"。需在方案中**明确标注算力路径一期为开环**，避免演示被误读为"已闭环控制"。
- **绿证合规闭环缺失**：用电量→应消纳绿证→已持有/已交易→年度缺口核销，这条合规闭环未定义。

### P2-10 边界条件未定义
- **80% 绿电达不到时**：当可再生出力不足且作业 SLA 不允许延迟时如何取舍？需定义优先级（保 SLA vs 保绿电占比）与降级策略。
- **跨站点空间协同**：`Site.network_config` 有 VPN/专线信息，但**无站间时延/带宽/算力余量**字段，方案的"空间协同"缺数据支撑——一期应明确**只做单中心多区域(zone)**，跨站点列为预留。
- **时段粒度对齐**：方案说"每 15 分钟滚动"，需对齐既有 `DispatchSchedule.time_slot 0–95` 约定，避免两套时间索引。
- **告警级别不一致**（既有）：`realtime_dispatch.py` 服务用 5 级，`RealtimeMonitoring.alert_level` 表注释只有 3 级（normal/warning/critical）——既有小漂移，新功能勿沿用错的一侧。

## 5. 修正后的建议

1. **重定核心叙事**：从"让 IT/算力变柔性"改为"**在刚性设施层之上，新增一个可中断 AI 作业的柔性调度层，并给现有源网荷储资源贴上绿电/碳标签**"——既不破坏现有安全约束，又实现算电协同。
2. **Epic 编号改 36+**（或命名 Epic），架构章节号先核对再定。
3. **§7 用本报告 §4 的三档表替换**；删除所有与 `DispatchableDevice/DispatchSchedule/Site/PV/Storage/VppDispatch` 重复的"新增"。
4. **所有新表补 `is_demo/data_source`**，命名对齐最近同类表（`cue_history` 等）。
5. **明确一期边界**：算力路径=开环（建议+模拟）、空间协同=单中心多 zone、市场/碳因子=配置+模拟器。
6. **工作量重估**：因复用率高，Phase 1（绿电碳底座+大屏）可显著小于 V1.0 估计；建议先做 Phase 1 验证闭环再扩展。
