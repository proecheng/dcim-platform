## 操作人员速查指南（30 秒看懂）

### 这套系统干什么？

**一句话**：电费便宜的时候多开空调把机房"冻凉"，电费贵的时候少开空调让温度慢慢回升，全程保证机柜不过热。

**为什么比旧方案好？**

| | 旧方案（固定比例 0.4） | 新方案（TCL 模型） |
|---|---|---|
| 怎么决定转多少 | 写死 40%，不看温度 | 看实际温度算出来的，热了就少转，凉了就多转 |
| 安全保障 | 无，全凭经验 | 实时预测温度曲线，超限自动回退 |
| 适应性 | 夏天冬天一样 | 自动适应季节、负载、时段 |
| 操作感受 | 配一次就不管了 | 仪表盘显示预测温度，看得见放得心 |

### 操作人员需要做什么？

**日常只看三件事：**

| 看什么 | 在哪看 | 正常范围 | 异常处理 |
|-------|-------|---------|---------|
| **最热机柜进风温度** | 转移仪表盘 | ≤ 25°C 绿灯 | > 26°C 系统自动回退制冷，无需手动 |
| **温度预测曲线** | 预冷调度预览 | 曲线在 18-27°C 之间 | 预测超 27°C 时系统会拒绝该调度方案 |
| **今日节省金额** | 转移仪表盘 | 正数即可 | 持续为 0 或负数 → 检查电价配置 |

**首次配置清单：**

- [ ] 1. 确认冷通道拓扑已配好（能源管理 → 拓扑配置 → 制冷拓扑）
- [ ] 2. 填写冷通道面积和层高（CoolingZone 的 area_m2、height_m）
- [ ] 3. 等 2 周系统自动学习 R/C 参数（此期间用温度裕度法兜底）
- [ ] 4. R/C 标定完成后，设置预冷目标温度（默认 18°C）
- [ ] 5. 检查分时电价配置是否正确
- [ ] 6. 在 1 个低密度冷通道试运行 2 周
- [ ] 7. 确认温度预测误差 ≤ 1°C 后推广到全部冷通道

**系统会自动保护你：**

| 保护条件 | 系统动作 |
|---------|---------|
| 任一机柜进风温度 > 26°C | 30 秒内恢复正常制冷 |
| 温升速率超过预测的 1.5 倍 | 30 秒内恢复正常制冷 |
| 温度变化超过 5°C/h | 限制功率调整速度 |
| 空调故障告警 | 立即停止功率转移 |
| 温度传感器离线 | 切回保守固定比例模式（0.2） |
| 市电中断切 UPS | 峰时温度上限收紧到 25°C |
| 预冷时湿度接近露点 | 停止降温，防止结露 |

## 1. 问题背景

### 1.1 用户核心担忧

用户在配置负荷转移方案时，最大的顾虑是：

> "转移了这么多制冷功率，万一空调制冷效果变差，导致对应冷通道中某个机柜温度上升过多，甚至服务器烧坏，损失巨大。"

### 1.2 问题本质

**可转移制冷功率的安全上限，应该由"离温度红线还有多远"来决定，而不是一个固定比例。**

核心矛盾：
- 转移太多 → 制冷不足 → 机柜过热 → 设备损坏（灾难性后果）
- 转移太少 → 节能效果差 → 方案缺乏吸引力
- 固定比例 → 无法适应不同季节、不同负载密度、不同机房布局

## 2. 现有算法分析

### 2.1 当前公式

```
最大可转移功率 = 总功率 × (制冷占比 × 0.4 + 其他占比 × 0.6)
```

**代码位置**：
- 后端：`backend/app/services/load_shift/algorithms/constraint_checker.py` 第 489-494 行
- 配置：`backend/app/services/load_shift/shift_constraint_service.py` 第 32-33 行

### 2.2 当前算法的不足

| 缺陷 | 说明 | 风险等级 |
|------|------|---------|
| **固定比例 0.4** | 不考虑实际温度状况，夏季高温和冬季低温用同一个值 | 高 |
| **无温度感知** | 不读取任何机柜/冷通道温度传感器数据 | 高 |
| **无机柜粒度** | 不区分高密度机柜和低密度机柜，统一处理 | 中 |
| **无热惯性考虑** | 不考虑削减制冷后温度上升的滞后效应和速率 | 中 |
| **无环境温度因素** | 室外温度影响制冷系统效率，但未纳入计算 | 中 |
| **无安全时间窗口** | 用户无法知道"削减后还有多少时间是安全的" | 中 |

## 3. 行业主流方法

### 3.1 方法一：温度裕度法（Temperature Headroom, THM）

#### 核心思想

可削减的制冷功率由"当前温度距安全上限还有多少空间"决定。

#### 公式

```
温度裕度 = T_max(ASHRAE上限) - T_current_max(当前最热机柜进风温度)
最大温度范围 = T_max - T_supply(设计送风温度)
动态可转移比例 = (温度裕度 / 最大温度范围) × 安全系数
```

#### 示例

```
T_max = 27°C (ASHRAE推荐上限)
T_current_max = 23°C (当前最热机柜)
T_supply = 12°C (设计送风温度)

温度裕度 = 27 - 23 = 4°C
最大温度范围 = 27 - 12 = 15°C
动态可转移比例 = (4 / 15) × 0.8 = 0.213 (约21%)
```

对比固定 0.4（40%），此场景下温度裕度法给出更保守的 21%，避免过度削减。

若 T_current_max = 18°C（冬季低负载）：
```
温度裕度 = 27 - 18 = 9°C
动态可转移比例 = (9 / 15) × 0.8 = 0.48 (约48%)
```

此时裕度充足，允许更多转移，比固定 0.4 更灵活。

#### 学术来源

Boston University THM 模型（Tuncer et al., ICCD 2014）：通过安全收缩热裕度（Thermal Headroom），在保证安全的前提下实现 **21% 吞吐量提升**。

**核心论文**：[Data Center Power Budgeting with Workload and Cooling Awareness](https://www.bu.edu/peaclab/files/2014/03/tuncer_ICCD14.pdf)

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 简单直观，易于实现 | 依赖温度传感器精度和覆盖率 |
| 实时响应温度变化 | 未考虑温度变化的滞后效应 |
| 用户容易理解 | 仅反映当前状态，不预测未来 |

### 3.2 方法二：热缓冲时间法（Thermal Mass Buffer）

#### 核心思想

制冷削减后，机房温度不会立刻升高。由于建筑围护结构、空气体积、机柜金属等的热容量，存在一个"安全时间窗口"。只要这个窗口足够长（大于制冷系统恢复时间），就是安全的。

#### 公式

```
安全缓冲时间 = (热容量 × 温度裕度) / (IT热负荷 - 削减后制冷功率)
```

其中：
- **热容量 C**：单位面积热容量，典型值 0.015 ~ 0.065 kWh/°C/m²
- **温度裕度**：T_max - T_current_max
- **IT 热负荷**：当前 IT 设备总发热功率
- **削减后制冷功率**：转移后剩余的制冷输出

#### 关键参数影响（ASHRAE 研究数据）

| 参数变化 | 对缓冲时间的影响 |
|---------|----------------|
| 机房高度翻倍（10ft→20ft） | 缓冲时间延长 **100%** |
| 热负载密度 50 W/sqft vs 200 W/sqft | 后者 5 分钟内可达 60°C |
| 每增加 50 磅机柜重量 | 缓冲时间延长约 **12%** |
| 机柜行数 5→20 行 | 缓冲时间改善 **26-48%** |

#### 安全准则

```
安全缓冲时间 ≥ 制冷滞后时间 × 1.5（安全倍数）
```

例如制冷滞后 20 分钟，则安全缓冲时间必须 ≥ 30 分钟。

#### 学术来源

- **ASHRAE TC9.9**：Khankari, "Thermal Mass Availability for Cooling Data Centers During Power Shutdown", ASHRAE Transactions, 2010
- **参考链接**：[Thermal Mass Availability (Academia)](https://www.academia.edu/67604091/Thermal_Mass_Availability_for_Cooling_Data_Centers_During_Power_Shutdown_AB_10_C022_)

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 考虑了物理热惯性，更科学 | 热容量参数需要标定 |
| 可量化安全时间，用户安心 | 不同区域热容量可能差异大 |
| 适合预调度场景 | 需要较多物理参数 |

### 3.3 方法三：冷冻水热平衡法（Chilled Water Thermal Balance）

#### 核心思想

基于冷冻水管路中的蓄冷量，计算制冷中断后能维持安全运行多长时间。

#### 关键实测数据（20MW 数据中心 CFD 案例）

| 冷冻水供水温度 | CRAH 出风温度 | 机柜进风 | 状态 |
|--------------|-------------|---------|------|
| ≤ 17°C | ≤ 24°C | ASHRAE 安全范围内 | 安全 |
| 18°C | 25°C | 制冷能力 < 热负荷 | 临界 |
| > 18°C | 快速上升 | 超出安全范围 | 危险 |

- CRAH 盘管利用率 85% 时，制冷中断后安全运行窗口约 **320 秒**（约 5 分钟）
- 配备蓄冷水箱可大幅延长安全时间

#### 公式

```
蓄冷量 = 水体积 × 水密度 × 比热容 × (T_water_max - T_water_current)
安全运行时间 = 蓄冷量 / (IT热负荷 - 自然散热量)
```

#### 学术来源

**参考论文**：[Thermal Performance Evaluation of a Data Center Cooling System under Fault Conditions (MDPI, 2019)](https://www.mdpi.com/1996-1073/12/15/2996)

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 与实际冷冻水系统直接关联 | 仅适用于冷冻水系统 |
| 有明确的物理量可测量 | 需要冷冻水温度传感器 |
| 可配合蓄冷系统增强安全性 | 对直接膨胀（DX）系统不适用 |

### 3.4 方法四：预冷+温控负载模型（Pre-Cooling TCL Model）

#### 核心思想

将数据中心视为"恒温控制负载（Thermostatically Controlled Load, TCL）"，在低电价时段预冷，高电价时段"释放"热裕度。

#### 工作原理

```
1. 谷时：降低机房温度至 T_min（如 18°C），存储"冷量"
2. 峰时：允许温度缓慢上升至 T_max（如 27°C），削减制冷功率
3. 可转移量 = 预冷存储的冷量 / 峰时持续时间
```

#### 公式

```
预冷存储量 = C_room × (T_normal - T_precool)
可削减制冷时长 = 预冷存储量 / (Q_IT - Q_cooling_reduced)
可转移功率 = Q_cooling_normal - Q_cooling_reduced
```

其中：
- **C_room**：机房热容量（kWh/°C）
- **T_normal**：正常运行温度（如 22°C）
- **T_precool**：预冷目标温度（如 18°C）
- **Q_IT**：IT 热负荷
- **Q_cooling_reduced**：削减后的制冷功率

#### 学术来源

**参考论文**：[Integrating Pre-Cooling of Data Center operated with Renewable Energies (HAL Science)](https://hal.science/hal-02970488/file/article_precooling.pdf)

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 与电价时段天然配合 | 预冷潜力有限（仅几个百分点） |
| 特别适合负荷转移场景 | 高密度机房效果差 |
| 可与蓄冷系统结合 | 需要较长的预冷时间 |

### 3.5 方法五：MPC 模型预测控制（Model Predictive Control）

#### 核心思想

用机器学习建立热力学模型，实时预测"削减 X kW 制冷功率后，未来 N 分钟内各机柜温度变化轨迹"，在满足温度约束的前提下最大化转移功率。

#### 优化模型

```
目标函数: min Σ(制冷能耗)
约束条件:
  T_rack_i(t) ≤ T_max,  ∀ 机柜 i, ∀ 时间 t
  Q_cooling(t) ≥ Q_min（最低制冷功率）
  ΔQ_cooling(t) ≤ ΔQ_max（最大调整速率）
```

#### 实现方式

1. **数据采集**：5 分钟/次，采集温度、功率、COP 等参数
2. **异常过滤**：高斯分布识别和删除异常数据
3. **特征选择**：卡方检验找出影响能效的关键参数（5 类控制参数 + 14 类过程参数 + 2 类环境参数）
4. **模型训练**：时变状态空间模型，MAE 仅 0.28°C
5. **在线优化**：PSO（粒子群优化）算法求解最优冷冻水流量和供水温度

#### 学术来源

- **MPC 多冷机优化**：[Model Predictive Control for Multi-Chiller System (ScienceDirect, 2024)](https://www.sciencedirect.com/science/article/abs/pii/S0378778824010351)
- **华为 iCooling**：[iCooling@AI 推动数据中心制冷走向"智冷"](https://www.huawei.com/cn/huaweitech/publication/86/icooling-ai-for-energy-optimization)
- **数据中心热建模**：[Thermal Modeling of Data Centers for Control and Energy Usage Optimization (ScienceDirect)](https://www.sciencedirect.com/science/article/abs/pii/S0065271718300029)

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 最精准，考虑所有约束 | 实现复杂度高 |
| 可预测未来温度轨迹 | 需要大量历史数据训练 |
| 自适应不同季节和负载 | 模型需要持续维护 |
| 业界大厂验证（华为等） | 对中小型 DC 可能过度设计 |

### 4.2 推荐组合

对于本系统（DCIM 中小型算力中心），**最终推荐采用预冷 TCL 模型**（详见第 6 节），融合温度裕度法作为安全兜底：

- **核心算法：预冷 TCL 模型**：基于 RC 热力学方程，结合分时电价，在谷时预冷、峰时释放热裕度
- **安全兜底：温度裕度法**：实时监控最热机柜温度，裕度不足时禁止转移
- **二次校验：热缓冲时间法**：确保安全缓冲时间足够

理由：
1. TCL 模型与本系统的分时电价负荷转移场景天然匹配
2. 系统已有完整的温度采集能力（进风/出风/供回水温度）
3. 已有制冷联动配置和冷通道拓扑映射
4. 温度裕度法作为实时安全护栏，简单可靠

## 5. 原推荐改进方案（温度裕度法+热缓冲时间法）

> **注**: 此方案仍作为安全兜底层保留，但核心算法改为第 6 节的预冷 TCL 模型。

### 5.1 改进后的算法伪代码

```python
def calculate_cooling_transferable_ratio(
    rack_inlet_temps: List[float],       # 各机柜进风温度列表
    t_max: float = 27.0,                 # ASHRAE 推荐上限 (°C)
    t_supply: float = 12.0,              # 设计送风温度 (°C)
    safety_factor: float = 0.8,          # 安全系数 (0.7~0.9)
    absolute_max_ratio: float = 0.6,     # 绝对上限
    min_headroom: float = 2.0,           # 最小温度裕度 (°C)，低于此值禁止转移
) -> Tuple[float, dict]:
    """
    基于温度裕度动态计算制冷可转移比例。

    返回: (可转移比例, 详细信息字典)
    """
    # 1. 取最热机柜进风温度作为约束基准
    t_current_max = max(rack_inlet_temps)
    t_current_avg = sum(rack_inlet_temps) / len(rack_inlet_temps)

    # 2. 计算温度裕度
    headroom = t_max - t_current_max
    max_range = t_max - t_supply

    # 3. 安全红线：裕度不足时禁止转移
    if headroom < min_headroom:
        return 0.0, {
            "reason": "温度裕度不足",
            "headroom": headroom,
            "min_headroom": min_headroom,
            "t_current_max": t_current_max,
            "blocked": True,
        }

    # 4. 动态计算可转移比例
    ratio = min(
        (headroom / max_range) * safety_factor,
        absolute_max_ratio,
    )

    return ratio, {
        "headroom": round(headroom, 2),
        "t_current_max": round(t_current_max, 2),
        "t_current_avg": round(t_current_avg, 2),
        "dynamic_ratio": round(ratio, 4),
        "blocked": False,
    }


def validate_thermal_buffer_time(
    transfer_power_kw: float,            # 计划转移的制冷功率 (kW)
    current_cooling_power_kw: float,     # 当前制冷总功率 (kW)
    it_heat_load_kw: float,              # IT 热负荷 (kW)
    room_area_m2: float,                 # 机房面积 (m²)
    headroom_celsius: float,             # 温度裕度 (°C)
    cooling_lag_minutes: float = 20.0,   # 制冷滞后时间 (分钟)
    c_per_m2: float = 0.04,             # 单位面积热容量 (kWh/°C/m²)
    safety_multiplier: float = 1.5,      # 安全倍数
) -> Tuple[bool, dict]:
    """
    热缓冲时间校验：确保安全缓冲时间 ≥ 制冷滞后时间 × 安全倍数。

    返回: (是否通过, 详细信息字典)
    """
    # 1. 计算削减后制冷功率
    reduced_cooling = current_cooling_power_kw - transfer_power_kw

    # 2. 计算热失衡功率（IT 发热 - 剩余制冷）
    heat_imbalance = it_heat_load_kw - reduced_cooling

    if heat_imbalance <= 0:
        # 制冷仍然充足，无热失衡
        return True, {
            "buffer_time_minutes": float("inf"),
            "required_minutes": cooling_lag_minutes * safety_multiplier,
            "safe": True,
            "message": "削减后制冷功率仍大于 IT 热负荷",
        }

    # 3. 计算热容量
    thermal_capacity_kwh = room_area_m2 * c_per_m2  # kWh/°C

    # 4. 计算安全缓冲时间
    buffer_time_hours = (thermal_capacity_kwh * headroom_celsius) / heat_imbalance
    buffer_time_minutes = buffer_time_hours * 60

    # 5. 校验
    required_minutes = cooling_lag_minutes * safety_multiplier
    is_safe = buffer_time_minutes >= required_minutes

    return is_safe, {
        "buffer_time_minutes": round(buffer_time_minutes, 1),
        "required_minutes": round(required_minutes, 1),
        "heat_imbalance_kw": round(heat_imbalance, 2),
        "thermal_capacity_kwh_per_c": round(thermal_capacity_kwh, 2),
        "safe": is_safe,
        "message": (
            f"安全缓冲时间 {buffer_time_minutes:.1f} 分钟 "
            f"{'≥' if is_safe else '<'} "
            f"要求 {required_minutes:.1f} 分钟"
        ),
    }


def calculate_max_transfer_power(
    total_power_kw: float,
    cooling_ratio: float,
    other_ratio: float,
    rack_inlet_temps: List[float],
    it_heat_load_kw: float,
    room_area_m2: float,
    cooling_lag_minutes: float = 20.0,
    other_transferable_ratio: float = 0.6,
    **kwargs,
) -> dict:
    """
    完整的可转移功率计算流程：温度裕度法 + 热缓冲时间校验。
    """
    # 第一步：温度裕度法计算动态可转移比例
    cooling_ratio_dynamic, headroom_info = calculate_cooling_transferable_ratio(
        rack_inlet_temps=rack_inlet_temps,
        **kwargs,
    )

    # 第二步：计算初始可转移功率
    cooling_power_kw = total_power_kw * cooling_ratio
    initial_transfer = total_power_kw * (
        cooling_ratio * cooling_ratio_dynamic + other_ratio * other_transferable_ratio
    )

    # 第三步：热缓冲时间校验
    cooling_transfer_kw = cooling_power_kw * cooling_ratio_dynamic
    is_safe, buffer_info = validate_thermal_buffer_time(
        transfer_power_kw=cooling_transfer_kw,
        current_cooling_power_kw=cooling_power_kw,
        it_heat_load_kw=it_heat_load_kw,
        room_area_m2=room_area_m2,
        headroom_celsius=headroom_info.get("headroom", 0),
        cooling_lag_minutes=cooling_lag_minutes,
    )

    # 第四步：如果热缓冲时间不足，按比例缩减
    final_transfer = initial_transfer
    if not is_safe and buffer_info["buffer_time_minutes"] > 0:
        scale_factor = buffer_info["buffer_time_minutes"] / buffer_info["required_minutes"]
        cooling_ratio_dynamic *= scale_factor
        final_transfer = total_power_kw * (
            cooling_ratio * cooling_ratio_dynamic + other_ratio * other_transferable_ratio
        )

    return {
        "max_transfer_power_kw": round(final_transfer, 2),
        "cooling_transferable_ratio": round(cooling_ratio_dynamic, 4),
        "other_transferable_ratio": other_transferable_ratio,
        "headroom_info": headroom_info,
        "buffer_info": buffer_info,
        "method": "温度裕度法 + 热缓冲时间校验",
    }
```

#### 6.0.2 各设备角色说明

| 设备 | 作用 | 温度测点 | 与冷通道关系 |
|------|------|---------|------------|
| **精密空调 (CRAC/CRAH)** | 将热通道回风冷却后送入冷通道 | 送风温度 T_supply、回风温度 T_return、制冷量、功率、COP | 一台空调可服务 1~N 个冷通道 |
| **冷通道 (Cold Aisle)** | 封闭通道，汇集空调冷风，为机柜前面板（进风侧）供冷 | 通道温度、通道湿度、通道压差 | 核心制冷对象 |
| **IT 机柜** | 服务器、存储设备的物理承载 | 进风温度 T_inlet（前面板）、出风温度 T_outlet（后面板） | 两列机柜面对面排列形成冷通道 |
| **PDU 柜** | 为同列机柜配电，自身也产生少量热量 | 一般无独立温度传感器 | 物理上位于机柜列末端或中间 |
| **热通道 (Hot Aisle)** | 机柜背面排出的热空气汇集区 | 无独立传感器（≈ 各机柜出风温度的混合值） | 热空气回流到空调回风口 |
| **室外机** | 将空调冷凝热排出室外 | 环境温度、冷凝器温度 | 影响空调COP和制冷能力 |

```

              │         │             │          │             │          │             │          │

                  └─────────────────────────────────────────────────────────────────────────┘
```

**温度递增关系**（正常运行时）：

```
T_supply (12-18°C) < T_aisle (18-24°C) ≈ T_inlet (18-27°C) < T_outlet (30-45°C) ≈ T_return (25-35°C)
```

**关键说明**：

| 关系 | 说明 | 温差原因 |
|------|------|---------|
| T_supply < T_aisle | 冷风从空调出来到冷通道有温升 | 管路损失、与地板/环境混合 |
| T_aisle ≈ T_inlet | 冷通道封闭良好时两者近似相等 | 冷通道就是为了保证 T_inlet |
| T_inlet < T_outlet | 服务器风扇将冷风加热后排出 | **ΔT = Q_IT / (ṁ × c_p)** |
| T_outlet ≈ T_return | 热通道热空气回流到空调回风口 | 若有多个冷通道则为加权混合 |

#### 6.0.4 空调控温控的是哪里的温度？

**这是最关键的问题**。精密空调的温控目标不是一个简单的答案，要分层理解：

| 控制层级 | 控制目标 | 传感器位置 | 说明 |
|---------|---------|-----------|------|
| **空调自身控制器** | **回风温度 T_return** | 空调回风口内置传感器 | 空调的 PID 控制器直接控制的是回风温度，通过调节压缩机频率、风机转速来维持 T_return 在设定值附近 |
| **用户关心的指标** | **机柜进风温度 T_inlet** | 机柜前面板温度传感器 | ASHRAE 标准约束的是机柜进风温度 18-27°C，这才是 IT 设备"感受"到的温度 |
| **系统安全目标** | **所有 T_inlet ≤ 27°C** | 所有机柜进风传感器取最大值 | TCL 模型的温度约束应作用于 T_inlet_max |

**空调控温与机柜温度的间接关系**：

```
空调设定值（T_return_setpoint）
    ↓  空调 PID 控制
回风温度 T_return 被维持在设定值
    ↓  物理传热
送风温度 T_supply = T_return - Q_cool / (ṁ × c_p)
    ↓  冷通道混合
冷通道温度 T_aisle ≈ T_supply + ΔT_delivery
    ↓  近似相等
机柜进风温度 T_inlet ≈ T_aisle
```

**因此**：
- 空调直接控的是 **回风温度**（这是空调自己的事）
- 但我们真正需要保证的是 **机柜进风温度** ≤ 27°C（这是服务器感受到的温度）
- 两者之间有差距，取决于风量、冷通道封闭性、机柜密度分布
- **TCL 模型中的 T_room 应对应最热机柜的 T_inlet**，而非空调回风温度

**通俗理解**：空调像一个恒温水龙头，它控制的是"出水温度"（回风温度），但我们关心的是"花洒喷到身上的水温"（机柜进风温度）——中间管路越长、分岔越多，温度差异就越大。

#### 6.0.5 PDU 柜在制冷中的角色

PDU 柜（配电柜）虽然不是制冷设备，但在冷通道拓扑中需要特别注意：

```
┌─ 冷通道 ─────────────────────────────────────────────────┐
│                                                           │
│  机柜01  机柜02  机柜03  [PDU柜]  机柜04  机柜05  机柜06  │
│  5kW     5kW     5kW    0.5kW    5kW     5kW     5kW     │
│                                                           │
└───────────────────────────────────────────────────────────┘
```

| 特性 | IT 机柜 | PDU 柜 |
|------|--------|--------|
| 发热量 | 3-15 kW/柜（高） | 0.3-1 kW/柜（低） |
| 进风温度要求 | ASHRAE 18-27°C（严格） | 无严格标准 |
| 温度传感器 | 必须有进风/出风传感器 | 通常无温度传感器 |
| 在 TCL 模型中 | 计入 Q_IT 热负荷 | 发热量可忽略或归入 Q_IT |
| 在冷通道拓扑中 | 通过 CoolingZoneCabinet 关联 | 一般不纳入拓扑管理 |

**结论**：PDU 柜在制冷功率转移计算中可忽略其热贡献，但在物理布局上占用冷通道空间。

### 6.1 方法概述

**预冷 TCL（Thermostatically Controlled Load）模型**将数据中心机房视为一个"恒温控制负载"，利用 RC（电阻-电容）热力学等效电路描述机房温度随时间的变化，结合分时电价实现：

- **谷时预冷**：低电价时段加大制冷，将机房温度降至下限（如 18°C），"存储冷量"
- **峰时释放**：高电价时段减少制冷功率，允许温度缓慢上升至上限（如 27°C），"释放冷量"
- **动态约束**：全程保证每个冷通道/机柜的进风温度不超过 ASHRAE 安全上限
- **湿度保护**：预冷降温时同步监控湿度，确保送风温度高于露点 3°C 以上，防止结露

**核心优势**：与负荷转移的分时电价场景天然匹配，不是"拍脑袋定比例"，而是基于物理方程计算"还能安全削减多少、能持续多久"。

#### 步骤 1：参数标定

**目标**：确定每个冷通道（或机房区域）的热阻 R 和热容 C。

**方法 A：历史数据自动拟合（推荐）**

利用系统已有的温度历史数据，当制冷功率发生变化时（如空调定时启停、群控切换、故障恢复等**自然发生的事件**），观测温度响应曲线，自动拟合出时间常数 τ = R × C。**无需在生产环境做任何人为实验**，系统自动检测这类事件并记录为标定样本。

```python
# 拟合方法: 制冷功率阶跃后，温度从 T0 向 T_steady 指数趋近
# T(t) = T_steady + (T0 - T_steady) × e^(-t/τ)
# 其中 τ = R × C

# 已知:
#   制冷功率变化前后的稳态温度 → 可求 R
#   温度响应的时间常数 → 可求 τ，进而求 C = τ / R
```

**方法 B：物理估算**

| 参数 | 公式 | 典型值范围 | 说明 |
|------|------|-----------|------|
| C (热容) | C = ρ_air × V_room × c_p_air + Σ(m_i × c_p_i) | 0.015 ~ 0.065 kWh/°C/m² | 空气+机柜金属+地板等 |
| R (热阻) | R = 1 / (U × A_envelope) | 1/R = 0.001 ~ 0.003 kW/°C/m² | 围护结构传热系数 |
| τ (时间常数) | τ = R × C | 5 ~ 65 小时 | τ 越大热惯性越强 |

**注意**：数据中心不同于普通建筑，IT 设备金属质量大、气流封闭（冷通道隔离），C 值通常偏高。

**参数标定的精度要求**：R/C 误差 ±20% 时，3 小时后温度预测偏差可达 ±2.5°C，接近安全裕度。因此：
1. 物理估算后，至少用 3 次历史事件数据交叉校验
2. 参数取偏保守方向（宁可高估 R、低估 C，让温升预测偏快）
3. 每月用近期数据自动重新标定

**新系统上线路径（冷启动方案）**：

| 阶段 | 时间 | 做什么 | 安全策略 |

### 6.3 公式体系

#### 6.3.1 核心方程：一阶 RC 热动力学方程

将冷通道（或机房）视为单节点集总参数（lumped-capacitance）模型：

```
                  Q_IT(t)          Q_cool(t)
                    ↓                 ↑
                ┌───────────────────────┐
  T_ambient ──R──│    机房 (热容 C)     │── T_room(t)
                └───────────────────────┘
```

**微分方程**：

```
C × dT_room/dt = Q_IT(t) - Q_cool(t) + (T_ambient(t) - T_room(t)) / R
```

**离散化形式**（时间步长 Δt）：

```
T_room(k+1) = T_room(k) + (Δt / C) × [Q_IT(k) - Q_cool(k) + (T_amb(k) - T_room(k)) / R]
```

**数值稳定性要求**：步长必须满足 **Δt < 2 × R × C**，默认 5 分钟步长在常规参数下安全。实现时应校验 `Δt/(R×C) < 0.5`，不满足则自动缩小步长。

**变量说明**：

| 符号 | 含义 | 单位 | 数据来源 |
|------|------|------|---------|
| T_room(t) | 冷通道温度（以进风温度为代表） | °C | 机柜进风温度传感器 |
| T_ambient(t) | 冷通道外侧等效环境温度 | °C | 热通道温度（封闭冷通道场景）或机房环境温度传感器（非室外温度！） |
| Q_IT(t) | IT 设备热负荷 | kW | 机柜 IT 负载功率（≈发热量） |
| Q_cool(t) | 制冷系统输出功率（冷量） | kW | 精密空调制冷量 = 制冷功率 × COP(t)（注意：COP 随工况动态变化） |
| C | 冷通道热容量 | kWh/°C | 标定参数（含空气、机柜金属、地板等） |
| R | 冷通道与外部的等效热阻 | °C/kW | 标定参数（主要为冷通道围护与热通道之间的热阻，非室外围护热阻） |
| Δt | 时间步长 | h | 建议 5 分钟 = 1/12 h |

#### 6.3.2 进风温度与出风温度的关系

**进风温度**（T_inlet）即冷通道温度，是 RC 模型的状态变量。

**出风温度**（T_outlet）由 IT 设备加热后决定：

```
T_outlet = T_inlet + Q_IT / (ṁ_air × c_p_air)
```

其中：
- ṁ_air = 空气质量流量 (kg/s)，与精密空调风量相关
- c_p_air = 空气比热容 ≈ 1.005 kJ/(kg·°C)

**进出风温差的实际意义**：

```
ΔT = T_outlet - T_inlet = Q_IT / (ṁ_air × c_p_air)
```

| 应用场景 | 如何利用进出风温差 |
|---------|------------------|
| **验证 IT 热负荷** | Q_IT = ṁ_air × c_p_air × ΔT，用于校验 IT 功率计数据 |
| **检测气流短路** | 若 T_inlet 异常升高但 ΔT 正常 → 热通道回风混入冷通道 |
| **评估制冷效果** | 若 ΔT 持续增大 → 风量不足或 IT 负荷增加 |
| **预估削减影响** | 制冷功率降低 → 风量可能降低 → ΔT 增大 → T_outlet 升高 |

**精密空调的送风温度**（T_supply，即空调出风口温度）：

```
T_supply = T_return - Q_cool / (ṁ_air × c_p_air)
```

其中 T_return 为回风温度（≈热通道温度≈T_outlet 的加权平均）。

**完整温度链路**：

```
精密空调送风 T_supply → 冷通道 T_inlet → 服务器 → 热通道 T_outlet → 精密空调回风 T_return
     ↑                                                                    ↓
     └──────────── 精密空调制冷 (Q_cool) ────────────────────────────────┘
```

#### 6.3.3 冷通道级别的多节点模型

当单个机房有多个冷通道且密度差异大时，为每个冷通道建立独立 RC 模型：

```
对于冷通道 i (i = 1, 2, ..., N):

C_i × dT_i/dt = Q_IT_i(t) - Q_cool_i(t) + (T_amb(t) - T_i(t)) / R_i + Σ_j [(T_j(t) - T_i(t)) / R_ij]
```

其中 R_ij 为相邻冷通道之间的耦合热阻（通常较大，可简化忽略）。

**气流短路修正**：冷通道密封不良时，热空气可能回流到进风口。模型中增加短路系数 β 修正：

```
T_inlet_actual = T_inlet_model × (1-β) + T_outlet × β    (典型 β = 0.05~0.15)
```

当冷通道压差 ΔP < 5Pa 时，说明密封不良，自动将安全裕度从 2°C 提高到 4°C。

**冷通道 ↔ 空调的映射关系**：

系统已有 `CoolingZone → CoolingZoneCabinet + CoolingZoneUnit` 拓扑，可直接用于确定每个冷通道对应哪些机柜和空调。

```
Q_cool_i(t) = Σ (该冷通道关联的空调 j 的制冷输出)
Q_IT_i(t)   = Σ (该冷通道内各机柜的 IT 功率)
T_i(t)      = max(该冷通道内各机柜进风温度)  # 取最热点
```

#### 6.3.4 预冷储能量计算

谷时预冷"存储"的冷量：

```
E_precool = C × (T_normal - T_precool)
```

| 符号 | 含义 | 典型值 |
|------|------|-------|
| E_precool | 预冷存储的冷量 | kWh |
| T_normal | 正常运行温度 | 22°C |
| T_precool | 预冷目标温度 | 18°C（ASHRAE 下限） |
| C | 热容量 | kWh/°C |

**示例**：机房面积 200 m²，C = 0.04 kWh/°C/m²

```
C_total = 200 × 0.04 = 8 kWh/°C
E_precool = 8 × (22 - 18) = 32 kWh
```

这 32 kWh 的"冷量储备"可以在峰时支撑制冷功率的削减。

#### 6.3.5 峰时可削减制冷功率与持续时间

```
可削减时长 = E_precool / (Q_IT - Q_cool_reduced)
可削减功率 = Q_cool_normal - Q_cool_reduced
```

**约束**：

```
Q_cool_reduced ≥ Q_cool_min                      # 最低制冷功率
T_room(t) ≤ T_max = 27°C,  ∀t ∈ [t_peak_start, t_peak_end]   # 温度上限
```

**示例**续：

```
Q_IT = 150 kW（IT 热负荷）
Q_cool_normal = 180 kW（正常制冷功率，含冗余）
Q_cool_reduced = 140 kW（削减后）

热失衡 = 150 - 140 = 10 kW（温度将缓慢上升）
可持续时间 = 32 / 10 = 3.2 小时

温度上升速率 = 10 / 8 = 1.25 °C/h
从 18°C 升到 27°C 需要 (27-18)/1.25 = 7.2 小时（远超峰时时段）
```

**注意**：上述为简化线性估算，实际温升为指数曲线（随 T_room 接近 T_ambient 而减速），实施时必须用完整 RC 方程迭代计算。

#### 6.3.6 优化目标函数

**目标**：最小化制冷系统的电费

```
min Σ_k [ price(k) × P_cool(k) × Δt ]
```

其中：
- price(k) = 第 k 时段的电价 (元/kWh)
- P_cool(k) = 第 k 时段的制冷系统电功率 (kW)
- Δt = 时间步长 (h)

**注意**：Q_cool = P_cool × COP(t)，制冷量与电功率的关系取决于 COP。COP 随室外温度和负载率动态变化：

| 季节 | 室外温度 | 建议 COP 值 | 说明 |
|------|---------|------------|------|
| 夏季 | > 30°C | 2.8 | COP 最低，电费计算影响最大 |
| 过渡季 | 15-30°C | 3.5 | 中间值 |
| 冬季 | < 15°C | 4.0 | COP 高，预冷策略收益相对小 |

使用固定 COP 会导致电费计算误差 30-50%，实施时应至少按季节分段取值。

**约束条件**：

```
(1) 温度动力学约束:
    T(k+1) = T(k) + (Δt/C) × [Q_IT(k) - Q_cool(k) + (T_amb(k) - T(k))/R]

(2) 温度上下限:
    T_min ≤ T(k) ≤ T_max,  ∀k
    T_min = 18°C (ASHRAE 推荐下限)
    T_max = 27°C (ASHRAE 推荐上限)

(3) 冷通道级温度约束（安全兜底）:
    T_inlet_i(k) ≤ T_max - margin,  ∀i, ∀k
    margin = 2°C (安全裕度)

(4) 制冷功率上下限:
    P_cool_min ≤ P_cool(k) ≤ P_cool_max,  ∀k

(5) 功率调整速率约束:
    |P_cool(k+1) - P_cool(k)| ≤ ΔP_max

(5.1) 温度变化速率约束（设备保护）:
    |T(k+1) - T(k)| / Δt ≤ 5 °C/h
    (防止硬盘等机械部件热应力损伤)

(6) 日总冷量守恒（可选，软约束）:
    Σ_k Q_cool(k) × Δt ≈ Σ_k Q_IT(k) × Δt + Q_envelope_loss
```

#### 6.4.3 模型验证标准

#### 6.4.4 进风口温度与出风口温度的利用方式汇总

| 温度数据 | 在 TCL 模型中的角色 | 具体用法 |
|---------|-------------------|---------|
| **机柜进风温度 T_inlet** | **RC 模型状态变量** | 作为 T_room(t) 的代表值；取冷通道内最高值作为安全约束基准 |
| **机柜出风温度 T_outlet** | **IT 热负荷校验** | Q_IT = ṁ_air × c_p × (T_outlet - T_inlet)，交叉验证 IT 功率 |
| **精密空调出风温度 T_supply** | **制冷效果指标** | T_supply 越低，制冷功率越大；是 Q_cool 的间接度量 |
| **精密空调回风温度 T_return** | **T_ambient 近似值** | 在冷通道隔离良好时，T_return ≈ 热通道温度 ≈ RC 模型的 T_ambient |
| **T_outlet - T_inlet (温差)** | **气流健康度指标** | 温差过大 → 风量不足；温差异常小 → 可能存在气流短路 |
| **T_return - T_supply (空调温差)** | **制冷量估算** | Q_cool ≈ ṁ_air × c_p × (T_return - T_supply) |

**关键洞察**：

1. **进风温度是核心约束**：TCL 模型的温度上限约束直接作用于 T_inlet，因为 ASHRAE 标准针对的是"服务器进风温度"
2. **出风温度是验证手段**：通过 ΔT = T_outlet - T_inlet 可以反推 IT 热负荷，与功率计读数交叉验证
3. **回风温度替代环境温度**：对于冷通道隔离良好的机房，精密空调回风温度可作为 RC 模型中 T_ambient 的近似
4. **送风温度反映制冷能力**：制冷功率削减后，送风温度会上升，是制冷效果退化的早期信号

### 6.5 完整算法伪代码

```python
from typing import List, Dict, Tuple
from dataclasses import dataclass
import numpy as np


@dataclass
class ColdAisleParams:
    """冷通道 RC 模型参数"""
    zone_id: int                # 冷通道 ID
    zone_name: str              # 冷通道名称
    C: float                    # 热容量 (kWh/°C)
    R: float                    # 热阻 (°C/kW)
    area_m2: float              # 面积 (m²)
    cabinet_ids: List[int]      # 关联机柜 ID 列表
    cooling_unit_ids: List[int] # 关联空调 ID 列表


@dataclass
class TimeSlot:
    """时段定义"""
    start_hour: float           # 起始时刻 (0-24)
    end_hour: float             # 结束时刻 (0-24)
    price: float                # 电价 (元/kWh)
    period_type: str            # 时段类型: peak/valley/normal/sharp


def tcl_temperature_predict(
    T_current: float,           # 当前冷通道温度 (°C)
    Q_IT: float,                # IT 热负荷 (kW)
    Q_cool: float,              # 制冷功率 (kW, 冷量)
    T_ambient: float,           # 环境温度 (°C, 用回风温度近似)
    C: float,                   # 热容量 (kWh/°C)
    R: float,                   # 热阻 (°C/kW)
    dt: float = 1/12,           # 时间步长 (h), 默认5分钟
) -> float:
    """
    一阶 RC 模型单步温度预测。

    核心方程: C × dT/dt = Q_IT - Q_cool + (T_amb - T) / R
    """
    dT = (dt / C) * (Q_IT - Q_cool + (T_ambient - T_current) / R)
    return T_current + dT


def tcl_trajectory_predict(
    T_init: float,              # 初始温度 (°C)
    Q_IT_schedule: List[float], # 各时段 IT 热负荷 (kW)
    Q_cool_schedule: List[float], # 各时段制冷功率 (kW)
    T_amb_schedule: List[float],  # 各时段环境温度 (°C)
    C: float,
    R: float,
    dt: float = 1/12,
) -> List[float]:
    """
    预测完整温度轨迹。
    返回: 各时步的温度值列表
    """
    temps = [T_init]
    T = T_init

    for k in range(len(Q_cool_schedule)):
        T = tcl_temperature_predict(
            T_current=T,
            Q_IT=Q_IT_schedule[k] if k < len(Q_IT_schedule) else Q_IT_schedule[-1],
            Q_cool=Q_cool_schedule[k],
            T_ambient=T_amb_schedule[k] if k < len(T_amb_schedule) else T_amb_schedule[-1],
            C=C, R=R, dt=dt,
        )
        temps.append(T)

    return temps


def calculate_precool_storage(
    C: float,                   # 热容量 (kWh/°C)
    T_normal: float = 22.0,    # 正常运行温度 (°C)
    T_precool: float = 18.0,   # 预冷目标温度 (°C)
) -> float:
    """
    计算预冷储能量 (kWh)。
    """
    return C * (T_normal - T_precool)


def calculate_max_reduction(
    E_precool: float,           # 预冷储能量 (kWh)
    Q_IT: float,                # IT 热负荷 (kW)
    Q_cool_normal: float,       # 正常制冷功率 (kW)
    duration_hours: float,      # 峰时持续时间 (h)
    T_max: float = 27.0,       # 温度上限 (°C)
    T_precool: float = 18.0,   # 预冷后起始温度 (°C)
    C: float = 8.0,            # 热容量 (kWh/°C)
) -> Dict:
    """
    计算峰时最大可削减制冷功率。

    返回: {
        max_reduction_kw: 最大可削减功率,
        safe_duration_hours: 安全持续时间,
        temp_rise_rate: 温度上升速率,
    }
    """
    # 温度裕度约束: 温度上升不超过 T_max - T_precool
    max_temp_rise = T_max - T_precool  # °C

    # 最大允许热失衡 = C × max_temp_rise / duration
    max_heat_imbalance = C * max_temp_rise / duration_hours  # kW

    # 最大可削减 = 正常制冷 - (IT热负荷 - max_heat_imbalance)
    # Q_cool_reduced ≥ Q_IT - max_heat_imbalance
    Q_cool_min_required = Q_IT - max_heat_imbalance
    max_reduction = Q_cool_normal - max(Q_cool_min_required, 0)
    max_reduction = max(max_reduction, 0)

    # 若按最大削减，温度上升速率
    if max_reduction > 0:
        heat_imbalance = Q_IT - (Q_cool_normal - max_reduction)
        temp_rise_rate = heat_imbalance / C  # °C/h
        safe_duration = max_temp_rise / temp_rise_rate if temp_rise_rate > 0 else float('inf')
    else:
        temp_rise_rate = 0
        safe_duration = float('inf')

    return {
        "max_reduction_kw": round(max_reduction, 2),
        "safe_duration_hours": round(safe_duration, 2),
        "temp_rise_rate_per_hour": round(temp_rise_rate, 2),
        "precool_energy_kwh": round(E_precool, 2),
        "max_temp_rise": round(max_temp_rise, 2),
    }


def optimize_cooling_schedule(
    time_slots: List[TimeSlot],     # 分时电价时段
    Q_IT: float,                    # IT 热负荷 (假设恒定, kW)
    Q_cool_normal: float,           # 正常制冷功率 (kW)
    Q_cool_min: float,              # 最低制冷功率 (kW)
    Q_cool_max: float,              # 最大制冷功率 (kW)
    COP: float,                     # 制冷系数（注意：实际随工况变化，此处为简化）
    T_init: float,                  # 初始温度 (°C)
    T_min: float,                   # 温度下限 (°C), ASHRAE 18°C
    T_max: float,                   # 温度上限 (°C), ASHRAE 27°C
    T_ambient: float,               # 环境温度 (°C)
    C: float,                       # 热容量 (kWh/°C)
    R: float,                       # 热阻 (°C/kW)
    delta_P_max: float,             # 最大功率调整速率 (kW/步)
    dt: float = 1/12,               # 时间步长 (h)
) -> Dict:
    """
    求解最优制冷功率调度方案。

    简化版: 贪心策略
    - 谷时: 加大制冷至 Q_cool_max（预冷）
    - 峰时: 削减制冷至安全下限
    - 平时: 维持正常

    完整版可用 scipy.optimize.linprog 或 PuLP 求解 LP/MILP。

    注意：Q_IT 恒定是重大简化。算力中心 GPU 集群负载峰谷比可达 10:1，
    谷时可能正是 AI 训练高峰。实际部署时应接入算力调度系统获取负载预测。
    """
    schedule = []
    T = T_init

    for slot in time_slots:
        n_steps = int((slot.end_hour - slot.start_hour) / dt)

        for step in range(n_steps):
            if slot.period_type == 'valley':
                # 谷时: 预冷，尽量降温（但不低于 T_min）
                if T > T_min + 0.5:
                    Q_cool = min(Q_cool_max, Q_IT + C * (T - T_min) / dt)
                else:
                    Q_cool = Q_IT + (T_ambient - T) / R  # 维持温度
            elif slot.period_type in ('peak', 'sharp'):
                # 峰/尖峰时: 削减制冷（但不超过 T_max）
                if T < T_max - 2.0:  # 留 2°C 安全裕度
                    Q_cool = max(Q_cool_min, Q_IT - C * (T_max - 2.0 - T) / dt * 0.5)
                else:
                    Q_cool = Q_IT + (T_ambient - T) / R  # 温度接近上限，维持
            else:
                # 平时: 正常制冷
                Q_cool = Q_IT + (T_ambient - T) / R

            # 功率限幅
            Q_cool = max(Q_cool_min, min(Q_cool_max, Q_cool))

            # 功率变化率限幅
            if schedule:
                prev_Q = schedule[-1]["Q_cool"]
                if abs(Q_cool - prev_Q) > delta_P_max:
                    Q_cool = prev_Q + delta_P_max * (1 if Q_cool > prev_Q else -1)

            # 温度更新
            T_new = tcl_temperature_predict(T, Q_IT, Q_cool, T_ambient, C, R, dt)

            # 温度安全校验
            if T_new > T_max:
                # 紧急加大制冷
                Q_cool = Q_IT + (T_ambient - T) / R + C * (T - T_max + 1.0) / dt
                Q_cool = min(Q_cool_max, Q_cool)
                T_new = tcl_temperature_predict(T, Q_IT, Q_cool, T_ambient, C, R, dt)

            if T_new < T_min:
                # 减少制冷，避免过冷
                Q_cool = Q_IT + (T_ambient - T) / R - C * (T_min - T + 0.5) / dt
                Q_cool = max(Q_cool_min, Q_cool)
                T_new = tcl_temperature_predict(T, Q_IT, Q_cool, T_ambient, C, R, dt)

            P_elec = Q_cool / COP  # 制冷电功率
            cost = P_elec * dt * slot.price  # 该步电费

            schedule.append({
                "time_step": len(schedule),
                "period_type": slot.period_type,
                "price": slot.price,
                "Q_cool": round(Q_cool, 2),
                "P_elec": round(P_elec, 2),
                "T_room": round(T_new, 2),
                "cost": round(cost, 4),
            })

            T = T_new

    total_cost = sum(s["cost"] for s in schedule)
    baseline_cost = sum(
        (Q_cool_normal / COP) * dt * s["price"] for s in schedule
    )
    saving = baseline_cost - total_cost

    return {
        "schedule": schedule,
        "total_cost": round(total_cost, 2),
        "baseline_cost": round(baseline_cost, 2),
        "saving": round(saving, 2),
        "saving_percent": round(saving / baseline_cost * 100, 2) if baseline_cost > 0 else 0,
        "T_min_actual": round(min(s["T_room"] for s in schedule), 2),
        "T_max_actual": round(max(s["T_room"] for s in schedule), 2),
    }


def calculate_vpp_adjustable_capacity(
    T_current: float,           # 当前冷通道温度 (°C)
    Q_IT: float,                # 当前 IT 热负荷 (kW)
    Q_cool_current: float,      # 当前制冷功率 (kW, 冷量)
    Q_cool_min: float,          # 最低制冷功率 (kW)
    Q_cool_max: float,          # 最大制冷功率 (kW)
    T_min: float,               # 温度下限 (°C), ASHRAE 18°C
    T_max: float,               # 温度上限 (°C), ASHRAE 25°C (含应急余量)
    COP: float,                 # 当前 COP
    C: float,                   # 热容量 (kWh/°C)
    R: float,                   # 热阻 (°C/kW)
    response_window_hours: float = 0.25,  # 响应窗口 (h), 默认 15 分钟
) -> Dict:
    """
    计算当前时刻的实时可调容量，供虚拟电厂（VPP）上报。

    返回:
    - up_adjustable_kw: 可向上调节量（增加制冷功率 = 增加用电，填谷）
    - down_adjustable_kw: 可向下调节量（减少制冷功率 = 减少用电，削峰）
    """
    # 向下可调（削峰）: 减少制冷，但温度不能超 T_max
    # 在 response_window 内，允许的最大温升
    max_temp_rise = T_max - T_current
    if max_temp_rise <= 1.0:
        # 温度裕度不足，不可向下调
        down_kw_thermal = 0.0
    else:
        # 允许的最大热失衡
        max_imbalance = C * (max_temp_rise - 1.0) / response_window_hours  # 留 1°C 裕度
        # Q_cool 最少削减到 Q_cool_min
        max_cool_reduction = Q_cool_current - Q_cool_min
        # 实际可削减的冷量
        down_kw_thermal = min(max_cool_reduction, max_imbalance)
        down_kw_thermal = max(down_kw_thermal, 0)

    # 向上可调（填谷）: 增加制冷，但温度不能低于 T_min
    max_temp_drop = T_current - T_min
    if max_temp_drop <= 0.5:
        up_kw_thermal = 0.0
    else:
        up_kw_thermal = min(
            Q_cool_max - Q_cool_current,
            C * (max_temp_drop - 0.5) / response_window_hours
        )
        up_kw_thermal = max(up_kw_thermal, 0)

    return {
        "down_adjustable_kw": round(down_kw_thermal / COP, 2),  # 转为电功率
        "up_adjustable_kw": round(up_kw_thermal / COP, 2),
        "down_adjustable_thermal_kw": round(down_kw_thermal, 2),
        "up_adjustable_thermal_kw": round(up_kw_thermal, 2),
        "T_current": T_current,
        "headroom_up": round(T_max - T_current, 2),
        "headroom_down": round(T_current - T_min, 2),
        "response_window_hours": response_window_hours,
    }
```

## 8. 对抗性审查记录（V3.0 新增）

> 审查方法：由暖通工程师、电气工程师、机房运维工程师、算力中心调度员四个专业角色对 V2.0 文档进行独立审查，识别问题、风险和改进建议。审查发现已直接融入文档正文（标注为"审查补充"或"审查注意"），本节记录完整的审查意见和处理结果。

### 8.1 暖通工程师审查意见

| # | 问题 | 严重性 | 审查意见 | 处理方式 |
|---|------|--------|---------|---------|
| H1 | **R 值定义含糊** | 高 | 文档原文"冷通道与外部的热阻"，"外部"定义不清。对封闭冷通道，主要传热路径是冷通道→热通道（通过天窗缝隙、侧板缝隙），而非机房围护结构→室外。T_ambient 应明确为热通道温度而非室外温度 | ✅ 已修正变量表（6.3.1）：T_ambient 改为"冷通道外侧等效环境温度"，R 改为"冷通道与外部的等效热阻" |
| H2 | **一阶 RC 模型忽略气流短路** | 高 | 数据中心最常见的热安全事故来源是气流短路（bypass）——热通道热空气从天窗/侧板缝隙回流到冷通道。一阶 RC 模型完全无法捕捉此类局部热点，可能导致模型预测"安全"但实际已过热 | ✅ 已在 6.3.3 增加短路系数 β 修正公式和压差传感器联动逻辑 |
| H3 | **预冷过程结露风险** | 高 | 送风温度快速降低时，若低于露点温度，冷通道内会产生结露，可能导致：(1) 服务器前面板结水滴→短路；(2) 地板湿滑→安全隐患。文档完全未提及湿度约束 | ✅ 已在 6.1 方法概述增加湿度约束提醒：露点温度 ≤ T_supply - 3°C |
| H4 | **送风温度范围过时** | 中 | 文档写 T_supply 12-18°C，但现代高效数据中心送风温度常提高到 18-22°C 以提升自然冷却时长和 COP。12°C 是 10 年前的设计标准 | ⚠️ 未改正文（因为是一般范围描述），此处记录供实施时参考 |
| H5 | **COP 作为常数是重大简化** | 高 | 实际 COP 受室外温度、冷凝器温度、压缩机负载率影响。夏季室外 40°C 时 COP≈2.5，冬季 5°C 时 COP≈4.5。恒定 COP 假设导致电费计算误差 30-50% | ✅ 已在 6.3.6 增加 COP 动态变化提醒和季节分段建议值 |
| H6 | **风量与制冷功率耦合** | 中 | DX（直接膨胀）系统中，变频压缩机降频时风量也下降（蒸发器管路阻力变化），导致 ΔT 关系改变。文档 6.3.2 的 T_outlet 公式隐含"风量恒定"假设 | ⚠️ 文中公式已标注 ṁ_air 为变量，此处记录供实施时注意 |
| H7 | **多空调共享冷通道的气流不均** | 中 | 一台空调服务多个冷通道时，各冷通道获得的风量不均等，距空调远的冷通道温度更高。多节点模型（6.3.3）虽有但未量化分配系数 | ⚠️ 建议实施时为 CoolingZoneUnit 增加 `airflow_ratio` 字段 |

### 8.2 电气工程师审查意见

| # | 问题 | 严重性 | 审查意见 | 处理方式 |
|---|------|--------|---------|---------|
| E1 | **Q_cool 和 P_cool 概念混用** | 高 | 文档中有时 Q_cool 指制冷量（热功率 kW_th），有时指制冷系统电功率（kW_e）。6.3.1 的 RC 方程中 Q_cool 是热功率，但优化目标函数中 P_cool 是电功率，转换关系 Q_cool = P_cool × COP 在部分场景被忽略 | ⚠️ 公式已标注明确。建议实施时在代码中严格区分 `Q_cool_thermal_kw` 和 `P_cool_electric_kw` 两个变量名 |
| E2 | **功率调整速率约束单位不明** | 中 | 约束 (5) `ΔP_max` 和伪代码中 `delta_P_max` 未标明是制冷量（kW_th）还是电功率（kW_e）。若为制冷量，需除以 COP 换算实际电网功率变化 | ⚠️ 建议实施时统一使用电功率（kW_e）作为调度基准 |
| E3 | **频繁调节对电能质量的冲击** | 中 | 大功率制冷压缩机频繁启停或快速变频会造成电网电流谐波和电压波动，特别是多台空调同时调节时。文档未提及电能质量约束 | ⚠️ 建议实施时增加约束：同一时段最多调节 N/2 台空调（N 为总空调数），且相邻两台空调调节间隔 ≥ 2 分钟 |
| E4 | **UPS 容量约束未纳入 TCL 优化** | 中 | 状态报告指出 UPS 约束未实现，但 TCL 优化模型也未将 UPS 剩余容量作为约束条件。削减制冷功率时 UPS 负载率降低（好事），但预冷加大功率时可能超出 UPS 容量 | ⚠️ 建议在约束 (4) 中增加：P_cool(k) + P_IT ≤ P_UPS_rated × 0.8 |
| E5 | **变频压缩机最低频率限制** | 低 | 变频压缩机有最低运行频率（通常 30Hz），低于此频率必须停机。`Q_cool_min` 应对应此物理下限，而非任意设定 | ⚠️ 建议实施时从空调铭牌参数获取实际最低运行功率 |

### 9.2 数值仿真工程师审查意见

| # | 问题 | 严重性 | 审查意见 | 处理方式 |
|---|------|--------|---------|---------|
| N1 | **显式欧拉法数值稳定性** | 高 | 离散化使用前向欧拉法，稳定性条件 Δt < 2RC。若 R=0.5°C/kW, C=2kWh/°C，则 Δt < 2h（满足）。但标定误差可能使 RC 偏小导致振荡。且前向欧拉的截断误差为 O(Δt)，精度较低 | ✅ 已在 6.3.1 离散化公式后增加稳定性条件说明和自适应步长建议 |
| N2 | **参数敏感性未量化** | 高 | R、C 标定误差 ±20% 时，预测偏差多大？对安全决策的影响？文档无任何敏感性分析 | ✅ 已在步骤 1 增加敏感性分析数据和保守参数选取建议 |
| N3 | **示例中线性外推不准确** | 中 | 6.3.5 示例"从 18°C 升到 27°C 需要 7.2 小时"使用 ΔT/升温速率 的线性计算，但 RC 模型的温升是指数曲线而非线性。随着 T_room 升高，(T_amb-T)/R 项减小，实际升温加速。线性外推偏乐观 | ✅ 已在示例后增加注释说明指数曲线 vs 线性外推的区别 |
| N4 | **一阶模型无法描述超调现象** | 中 | 一阶 RC 是单调指数响应，无法描述温度超调。实际空调功率快速变化时，送风→冷通道→机柜的多级传热可能出现短暂超调（温度先升高再降低），一阶模型预测不到 | ⚠️ 建议：若实测发现超调现象频繁，可升级为二阶 RC 模型（增加一个节点表示机柜金属热容） |
| N5 | **非线性传热被线性化** | 低 | RC 方程为线性 ODE，但实际传热包含辐射（Stefan-Boltzmann T⁴ 项）和强制对流（Nu 与 Re 的非线性关系）。在数据中心温度范围（18-35°C）内，辐射占比较小（<5%），线性化误差可接受 | ⚠️ 无需修改，线性化在该温度范围内足够 |
| N6 | **初始条件敏感性** | 低 | 传感器精度 ±0.5°C 对 T_init 的影响：3 小时后预测偏差约 ±0.3°C（因指数衰减），可接受 | ⚠️ 无需修改，初始条件影响随时间自然衰减 |
