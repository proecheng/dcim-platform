## 1. 产品概述

### 1.1 产品愿景

打造面向数据中心的**新一代数字孪生大屏产品**，以"易用性"和"智能诊断"为核心卖点，通过沉浸式 3D 体验和能源可视化"魔法"打动客户，成为数据中心可视化管理的行业标杆。

### 1.2 一句话定位

> **"走进虚拟机房，直观感知每台设备的运行状态；上传 CAD 图纸，5 分钟生成数据中心 3D 模型。"**
>
> *注：3D 沉浸式漫游和实时数据叠加为 MVP-α 核心能力；CAD 自动建模为 MVP-β 核心能力，两者均在 MVP 阶段完成。*

### 1.3 产品定位：独立产品 + 开放集成

本产品定位为**完全独立的商业化产品**，具备以下特征：

| 特征 | 说明 |
|------|------|
| **独立部署** | 可独立于任何现有系统单独部署和运行 |
| **开放集成** | 通过标准 API/协议与各类数据源系统对接 |
| **容器化交付** | Docker/Kubernetes 部署，快速交付 |
| **多租户架构** | 支持 SaaS 模式或私有化部署 |

**对接模式选项：**

| 模式 | 描述 | 适用场景 |
|------|------|---------|
| **模式 A: 纯独立** | 直接对接动环/配电等底层系统 | 新客户，无现有 DCIM |
| **模式 B: 与现有 DCIM 对接** | 通过 API 从现有 DCIM 获取数据 | 已有 DCIM 的客户 |
| **模式 C: 混合模式** | 部分数据从 DCIM，部分直接采集 | 复杂环境 |

**数据迁移策略** (针对模式 B/C)：

| 场景 | 策略 | 说明 |
|------|------|------|
| **实时数据** | API 实时同步 | 通过 REST API 或 WebSocket 从现有 DCIM 获取 |
| **历史数据** | 批量导入工具 | 提供 CSV/JSON 批量导入，支持时间戳映射 |
| **资产数据** | 增量同步 | 首次全量导入，后续通过 Webhook/定时同步 |
| **告警数据** | 双向同步 | 支持告警状态回写到源系统 |

### 1.5 核心差异化

| 差异点 | 我们的优势 | 竞品现状 | 我们的不足 |
|--------|-----------|---------|-----------|
| **易用性** | 拖拽式建模，游戏化交互 | 学习曲线陡峭，依赖专业培训 | 新产品，客户案例少，需用 MVP 证明 |
| **智能诊断** | 分步排查引导+诊断面板 (MVP-β 基础版, Phase 2 完整版含语音+四合一) | 只报警不指导 | MVP 阶段仅提供基础引导，完整版需 Phase 2 |
| **能源可视化** | 电力+气流双流粒子动画，电价联动特效 | 静态热力图或简单动画 | 依赖 Babylon.js GPU 粒子系统，团队需学习期 |
| **产品化程度** | Docker 交付，多租户架构，开箱即用 | 项目制定制，难以复制 | 产品化打磨需时间，初期可能需定制 |
| **开放集成** | 标准 API，支持多种协议 | 封闭系统，集成困难 | 协议适配需按客户环境逐一验证调试 |

### 1.6 竞品分析

| 竞品 | 定位 | 3D 能力 | 优势 | 劣势 | 价格区间 |
|------|------|---------|------|------|---------|
| **优锘 ThingJS** | 物联网 3D 可视化平台 | 自研 3D 引擎，模型库丰富 | 平台成熟度高、生态完善 | 定制成本高、SaaS 依赖 | 10-50 万/年 |
| **蓝图 BlueMap** | 数据中心专用可视化 | BIM + 3D 集成 | 数据中心垂直深耕 | 产品封闭、集成困难 | 50-200 万/项目 |
| **DataV (阿里云)** | 通用大屏可视化 | 2D 为主，有限 3D | 云原生、低成本 | 3D 能力弱、无运维功能 | 5-15 万/年 |
| **Mapvision** | BIM+运维可视化 | Revit 模型导入 | BIM 深度集成 | 需要 BIM 专业人员 | 30-100 万/项目 |
| **51World** | 通用数字孪生 | 高精度渲染 | 视觉效果顶级 | 成本极高、项目周期长 | 100-500 万/项目 |
| **SmartDC** | 数据中心智能运维 | 有限 3D (WebGL) | 运维功能深入、国产化适配 | 3D 体验一般、定制周期长 | 30-80 万/项目 |
| **美的楼宇科技** | 暖通+楼宇智控 | BIM 轻量化 | 硬件+软件一体化、品牌影响力 | 聚焦暖通、数据中心非主业 | 50-150 万/项目 |

**我们的竞争定位**: 在"3D 能力"和"易用性"两个维度上取得最佳平衡，以产品化方式交付（而非项目制），通过 Docker 容器化将交付周期缩短到天级别。

**我们的坦诚劣势**:
- **品牌与案例**: 新产品零客户案例，需通过免费试用/Demo 建立首批口碑
- **团队规模**: 初创团队，大规模定制能力有限
- **3D 引擎经验**: 团队从 Three.js 转向 Babylon.js，有学习成本（M1 阶段验证）

### 2.2 核心使用场景

#### 场景 1：告警处置 (P0 - 高频)

```
触发: 系统检测到 B3 机柜温度异常
  ↓
大屏自动弹出告警通知，显示告警级别和简要信息
  ↓
运维工程师点击"带我去"按钮
  ↓
3D 视角自动飞行到 B3 机柜，设备高亮闪烁
  ↓
右侧弹出诊断面板:
  ├─ 分步排查引导 (语音同步播报)
  ├─ 关联设备状态 (共用空调 AC-07 的状态)
  ├─ 历史同类故障记录
  └─ 实时视频监控画面
  ↓
工程师按引导完成排查，确认处置方案
  ↓
一键生成工单，记录处置过程
```

#### 场景 2：日常巡检 (P0 - 每日)

```
触发: 运维工程师开始每日巡检
  ↓
选择"AI 自动巡游"模式
  ↓
系统自动在机房内漫游，依次检查各区域
  ↓
遇到异常设备时自动暂停，高亮标记
  ↓
工程师确认或处理后，继续巡游
  ↓
巡游结束，一键导出巡检报告 (PDF)
```

#### 场景 3：新设备部署规划 (P1)

```
触发: 需要新增 10 台服务器
  ↓
进入"设备选址"模式
  ↓
系统分析各机柜的:
  ├─ 剩余 U 位空间
  ├─ 配电回路负载余量
  └─ 制冷能力余量
  ↓
3D 场景中高亮推荐机柜，显示推荐理由
  ↓
用户拖拽服务器模型到目标位置
  ↓
系统实时预览气流变化和功率影响
  ↓
确认后更新资产台账
```

#### 场景 4：领导/客户参观演示 (P0)

```
触发: 重要客户来参观
  ↓
切换到"展示模式"
  ↓
自动播放精心设计的 3D 漫游路线:
  ├─ 从建筑外部飞入机房
  ├─ 穿越机柜排，展示规模
  ├─ 开启"气流魔法"，展示制冷系统
  ├─ 开启"电力流动"，展示配电系统
  └─ 展示实时 PUE 和运行指标
  ↓
客户被震撼，建立信任感
```

#### 场景 5：应急事件响应 (P2 — 依赖 Phase 2 功能)

```
触发: 检测到多个关键告警 (如 UPS 故障)
  ↓
系统自动进入"红色警报模式":
  ├─ 背景变暗/变红
  ├─ 非关键信息隐藏
  ├─ 所有告警设备高亮脉冲
  └─ 弹出应急处置流程 checklist
  ↓
开始自动录屏存档
  ↓
一键通知所有相关人员
  ↓
事件结束后，一键生成事件回放视频
```

## 3. 功能需求

### 3.1 功能分期规划

| 阶段 | 定位 | 核心目标 |
|------|------|---------|
| **MVP-α (Phase 1a)** | 技术验证+可演示 | 3D 漫游 + 实时数据 + 基础告警，能给客户演示 |
| **MVP-β (Phase 1b)** | 最小可销售产品 | 增加 CAD 导入 + 能源可视化 + 报告导出，能签第一单 |
| **Phase 2** | 智能增强 | 提升运维效率和用户粘性 |
| **Phase 3** | 产品化完善 | 规模化销售和持续服务 |

### 3.2 MVP-α (Phase 1a) 功能清单 — 可演示

#### 3.2.1 3D 可视化引擎 (P0 - 必须)

| 功能 | 描述 | 验收标准 |
|------|------|---------|
| **沉浸式漫游** | 第一人称视角，鼠标/键盘操控 | 60fps 流畅渲染，操控响应 <100ms |
| **多层级穿越** | 建筑→楼层→机房→机柜→设备 | 层级切换动画平滑，<1秒 |
| **告警导航飞行** | 点击告警自动飞到故障设备 | 飞行路径自然，设备准确高亮 |
| **3D+2D 分屏** | 左侧 3D 场景，右侧传统仪表盘 | 两侧数据同步，可切换全屏 |
| **LOD 信息层次** | 远/中/近三级信息密度 | 远处简化显示，近处详细展开 |

#### 3.2.2 告警与运维 (P0 - 必须)

| 功能 | 描述 | 验收标准 |
|------|------|---------|
| **情境化告警展示** | 告警直接显示在 3D 设备上 | 告警级别颜色区分，脉冲动画 |
| **基础处置引导** | 告警详情面板含简单处置建议 | 至少 3 步引导，可打勾确认 |
| **告警音效** | 4 级告警对应不同音效 | 紧急告警循环播放，可静音 |

#### 3.2.3 数据采集与集成 (P0 - 必须)

| 功能 | 描述 | 验收标准 |
|------|------|---------|
| **Modbus 采集** | 支持 Modbus TCP/RTU | 成功采集并正确解析数据 |
| **SNMP 采集** | 支持 SNMPv2c/v3 | 成功采集 UPS、空调等设备数据 |
| **REST API 集成** | 对接现有 DCIM 系统 | 成功获取数据，延迟 <1秒 |
| **数据源管理** | 可视化配置数据源 | 支持新增、编辑、测试连接 |

#### 3.2.4 基础架构 (P0 - 必须)

| 功能 | 描述 | 验收标准 |
|------|------|---------|
| **用户认证** | 登录/登出，JWT 认证 | 支持记住登录状态 |
| **基础权限** | 管理员/操作员/访客 三级 | 不同角色看到不同功能 |
| **Docker 部署** | docker-compose 一键部署 | 5 分钟内完成部署 |
| **模型手动导入** | 支持上传 GLB/glTF 模型文件 | 成功加载并显示 |

#### 3.2.5 3D 建模基础 (P0 - 必须)

| 功能 | 描述 | 验收标准 |
|------|------|---------|
| **设备模型库** | 预置 21+ 款标准设备模型 | 含机柜、服务器、空调、配电设备 |
| **拖拽式布局** | 从库中拖动设备到场景 | 支持对齐、复制、删除 |

### 3.3 MVP-β (Phase 1b) 功能清单 — 可销售

## 6. 系统架构

### 6.1 架构演进策略

本系统采用**模块化单体 → 微服务**的渐进式架构演进策略：

| 阶段 | 架构 | 说明 |
|------|------|------|
| **MVP (Phase 1)** | 模块化单体 (Modular Monolith) | 单个 FastAPI 应用，内部按领域模块划分，共享数据库 |
| **Phase 2** | 部分拆分 | 将 integration-service (采集) 和 ai-service (AI) 拆为独立服务 |
| **Phase 3** | 完整微服务 | 按需拆分为完整微服务架构 |

**模块化单体的边界规则**：
- 每个模块有独立的 `router/`, `schemas/`, `services/` 目录
- 模块间通过接口 (Protocol/ABC) 和内部事件总线通信，**禁止直接导入其他模块的内部实现**
- 数据库表按模块前缀命名（如 `scene_*`, `alarm_*`, `data_*`），为未来拆分做准备
- 公共代码（认证、日志、配置）放在 `core/` 模块

### 6.2 Docker Compose 服务清单 (MVP)

```yaml
# docker-compose.yml - MVP 阶段
services:
  # 反向代理
  nginx:
    image: nginx:alpine
    ports: ["80:80", "443:443"]

  # 核心应用 (模块化单体)
  app:
    image: dt-bigscreen/app:latest
    ports: ["8080:8080"]
    # 内含: 数据/告警/用户/能源/报告/集成/3D 场景 全部模块

  # 前端
  web-app:
    image: dt-bigscreen/web:latest

  # 基础设施
  postgres:           # TimescaleDB (关系 + 时序)
  redis:              # 缓存 + 会话
  mqtt:               # MQTT Broker (EMQX)
  minio:              # 对象存储 (3D 模型文件、截图、报告)
```

**MVP 容器数量: 7 个** (对比原方案 14 个，降低 50% 运维复杂度)

> **存储策略**: 3D 模型文件 (.glb)、截图、PDF 报告等静态文件统一存储在 MinIO 中。多实例部署时通过 MinIO 共享文件，避免本地文件系统的同步问题。

### 6.3 目标微服务架构 (Phase 3)

Phase 3 拆分为完整微服务后的目标架构：

| 服务名 | 职责 | 技术栈 | 内部端口 |
|--------|------|--------|---------|

| **data-service** | 实时数据查询、历史数据、数据聚合 | FastAPI | 8001 |
| **alarm-service** | 告警处理、诊断引导、通知推送 | FastAPI | 8002 |
| **user-service** | 认证授权、权限管理、租户管理 | FastAPI | 8003 |
| **energy-service** | 能源分析、电价管理、成本计算 | FastAPI | 8004 |

| **integration-service** | 协议适配、数据采集、消息转换 | FastAPI | 8006 |
| **ai-service** | 预测分析、智能诊断、异常检测 | FastAPI + PyTorch | 8007 |

**微服务迁移策略 (前端零变更)**:
- MVP 阶段前端所有 API 调用统一通过 Nginx 反向代理，URL 路径格式为 `/api/v1/*`

- **前端代码无需修改**，路由分发由 API Gateway 层完成
- 内部端口 (8001-8007) 仅网关可访问，不对外暴露

## 7. 技术约束与选型

### 7.1 3D 引擎选型对比

| 维度 | Babylon.js | Three.js | 决策 |
|------|-----------|----------|------|
| **粒子系统** | 内置 GPU 粒子系统，支持 100万+ 粒子 | 需要自行实现或用 three-nebula 库 | Babylon.js 优势明显 |
| **物理引擎** | 内置 Havok/Cannon.js 集成 | 需要额外集成 | Babylon.js 更方便 |
| **LOD 支持** | 内置 LOD 管理和自动切换 | 需要手动实现 | Babylon.js 更成熟 |
| **Inspector** | 内置 3D 调试器 | 需要第三方工具 | Babylon.js 开发体验更好 |
| **glTF 加载** | 原生支持，优化好 | 原生支持，优化好 | 持平 |
| **社区/生态** | 较小但活跃，微软支持 | 最大的 WebGL 社区 | Three.js 优势 |
| **学习成本** | 现有团队无经验，需学习 | 现有 DCIM 项目已使用 Three.js | Three.js 优势 |
| **许可证** | Apache 2.0 | MIT | 均可商用 |

**决策: 采用 Babylon.js**

理由：
1. 内置 GPU 粒子系统是本产品能源可视化 (气流/电力粒子动画) 的核心依赖，Three.js 需额外开发
2. 内置 LOD 管理和 Inspector 降低 3D 场景优化的开发成本
3. 现有 DCIM 项目的 Three.js 代码为简单场景展示，复用价值有限
4. **风险缓解**: MVP-α 阶段先做一个 Babylon.js 技术验证 Demo (M1 里程碑)，如粒子性能不达标则回退 Three.js

**回退判定标准 (M1 结束时评估)：**
- 100 机柜场景 GPU 粒子渲染 < 30fps → 回退
- 团队在 6 周内无法完成基础 3D 漫游+数据叠加 Demo → 回退
- 回退影响评估: 需重写 3D 渲染层约 2-4 周，能源粒子动画改用 three-nebula 库实现 (效果可能降级)

### 7.4 3D 模型生成方案

| 层级 | 内容 | 方案 |
|------|------|------|
| **建筑/机房** | 墙体、地板、门窗 | CAD 自动转换 (MVP-β)，降级方案: 在线编辑器手动绘制 |
| **设备模型库** | 机柜、服务器、空调等 | 外包+购买，首批 21 款 |
| **组装布局** | 将设备放入场景 | 拖拽工具，客户自己操作 |

**CAD 格式兼容性计划：**

| 格式 | 支持级别 | 实现方式 |
|------|---------|---------|
| .dxf (R12-R2018) | 完整支持 | ezdxf 直接解析 |
| .dwg (2010-2026) | 完整支持 | ODA File Converter 转 dxf 后解析 |
| 天正 CAD (.dwg) | 有限支持 | 部分天正自定义实体可能丢失，提供手动修正 |

> **天正 CAD 兼容性说明**: 国内数据中心设计图纸大量使用天正 CAD，其自定义实体无法被标准 DWG 解析器完全识别。应对策略:
> 1. **推荐客户导出天正 T3 格式** → ODA 转换 → ezdxf 解析 (兼容性最佳)
> 2. 天正自定义墙体、门窗等实体丢失时，自动标记缺失区域，用户在在线编辑器中手动补充
> 3. Phase 2 调研天正 SDK 或逆向解析方案，持续改善兼容性
| .ifc (BIM) | Phase 2 | ifcopenshell 解析 |
| 不支持的格式 | 降级 | 提供在线 2D 编辑器手动绘制房间布局 |

```
# 设备数据上报

dt/status/{tenant_id}/{device_id}

# 告警事件
dt/alarm/{tenant_id}/{device_id}

# 控制命令 (下行)
```

**MQTT QoS 与 Retain 策略：**

| 主题类型 | QoS | Retain | 说明 |
|---------|-----|--------|------|
| `dt/data/*` | 0 | false | 实时数据允许少量丢失，优先吞吐量 |
| `dt/status/*` | 1 | true | 设备状态需要可靠传输，新订阅者需获取最新状态 |
| `dt/alarm/*` | 1 | false | 告警消息必须可靠传输，不可丢失 |
| `dt/cmd/*` | 1 | false | 控制命令必须可靠传输 |

### 9.9 WebSocket 实时推送

#### 9.9.0 推送性能与扩展策略

> **问题**: 10,000 点位每 5 秒刷新 + 50 并发用户 = 理论峰值每秒 100,000 条消息，直接全量推送不可行。

| 策略 | 说明 |
|------|------|
| **增量推送** | 仅推送值发生变化的点位 (超过死区阈值才算变化)，通常 <20% 点位同时变化 |
| **批量合并** | 服务端将 1 秒内同一租户的多条变更合并为一条 JSON 数组消息，减少帧数 |
| **视口订阅** | 前端仅订阅当前 3D 视口内可见设备的点位 (基于 LOD 层级)，远处设备不订阅 |
| **分频推送** | 非焦点设备降频推送 (15秒)，焦点设备保持高频 (5秒) |
| **客户端限流** | 前端使用 requestAnimationFrame 节流渲染，WebSocket 消息缓冲后批量更新 DOM/3D |

**预估优化后实际负载**: 50 用户 × 平均 200 条变更/秒 ÷ 批量合并 = 约 500 条消息/秒 (可控)

#### 9.9.1 连接认证

```javascript
// 前端连接示例

ws.onopen = () => {

    type: 'subscribe',
    channels: ['data', 'alarm', 'status']
  }));
};

  const message = JSON.parse(event.data);
  // 处理消息
};
```

```sql
-- 创建超表 (按 tenant_id 分区空间维度)
SELECT create_hypertable('point_data', 'time');
SELECT add_dimension('point_data', 'tenant_id', number_partitions => 4);

-- 创建索引 (包含 tenant_id 避免跨租户查询)
CREATE INDEX ON point_data (tenant_id, point_id, time DESC);

-- 设置数据保留策略 (90天原始数据，满足行业合规要求)
SELECT add_retention_policy('point_data', INTERVAL '90 days');

-- 创建连续聚合 (1小时聚合，保留3年，满足等保二级要求)
CREATE MATERIALIZED VIEW point_data_hourly
WITH (timescaledb.continuous) AS
SELECT
  time_bucket('1 hour', time) AS bucket,
  point_id,
  AVG(value) as avg_value,
  MIN(value) as min_value,
  MAX(value) as max_value,
  COUNT(*) as count
FROM point_data
GROUP BY bucket, point_id;

SELECT add_retention_policy('point_data_hourly', INTERVAL '1095 days');  -- 3年
```

## 13. 风险与应对

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|---------|
| **Babylon.js 学习成本** | 开发进度延迟 2-4 周 | **高** | M1 前 2 周集中培训+原型验证，第 4 周末决策是否回退 Three.js；M1 总时长含 1 周缓冲 |
| **3D 性能不足** | 大场景卡顿 | 中 | LOD 优化、场景分区加载、自动降级策略 |
| **CAD 格式兼容** | 部分 CAD 无法解析 (尤其天正 CAD) | **高** | 支持 DXF/DWG + ODA 转换、推荐客户导出天正 T3 格式、提供在线编辑器降级方案 |
| **协议适配复杂** | 对接周期长 | 高 | 预置常见协议模板、提供技术支持、MVP-α 先验证核心协议 |
| **模型制作延期** | 首批模型不齐 | 低 | 提前外包、优先核心模型 (机柜、空调、PDU) |
| **客户需求变化** | 功能返工 | 中 | 增量开发、快速迭代、MVP 分两阶段降低风险 |
| **多租户隔离** | 数据泄露 | 低 | 严格的 tenant_id 过滤、安全测试、渗透测试 |
| **MVP 范围蔓延** | 交付延期 | 高 | MVP 明确拆为 α/β 两阶段，严格控制每阶段范围 |
