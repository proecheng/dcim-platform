# Story 24.4 第二轮深度对抗性审查报告

**审查日期**: 2026-03-06
**审查对象**: Story 24.4 实施文档（第一轮修复后版本）
**审查类型**: 深度对抗性文档审查
**审查方法**: 边界条件分析、安全威胁建模、并发场景推演、故障注入测试

---

## 审查发现

### 高严重程度问题（Critical）

1. **验收标准 #3 步骤顺序错误 - 签名验证时机不当**: 第 50 行说"如果版本已有签名（重新激活场景），验证签名"，但这个逻辑有严重问题。如果旧签名是用已删除的密钥生成的，验证会失败，导致无法重新激活。正确的逻辑应该是：**重新激活时不验证旧签名，直接生成新签名覆盖**。旧签名的作用是防止快照被篡改，但重新激活时管理员已经通过审批流程，应该信任当前快照。

2. **技术实现 #3 activate_version 缺少快照完整性验证**: 第 130-141 行验证 DAG，但没有验证快照中的 `device_mappings` 是否存在。如果快照被篡改删除了 device_mappings，DAG 验证会通过（因为 DAG 只检查节点和边），但激活后诊断引擎会因为缺少设备映射而崩溃。

3. **技术实现 #3 activate_version 的 SELECT FOR UPDATE 范围错误**: 第 147-152 行锁定 active 版本，但如果当前没有 active 版本（首次激活），SELECT FOR UPDATE 返回空结果集，不会获取任何锁。此时如果两个管理员同时激活不同版本，都会通过锁检查，最终可能出现两个 active 版本。应该锁定整个 tree_id 的版本记录，而不是只锁定 active 状态的版本。

4. **验收标准 #4 密钥验证时机错误**: 第 62-64 行说"系统启动时检查 FAULT_TREE_HMAC_KEY，如果未设置或长度 < 32 字节，应用拒绝启动"。但这会导致问题：如果管理员忘记设置密钥，整个应用无法启动，包括前端、告警、监控等所有功能都不可用。应该改为：**启动时只记录警告，首次调用版本管理 API 时才强制验证密钥**。

5. **技术实现 #3 rollback_version 的状态修改不安全**: 第 195-197 行将 archived 版本的状态改为 reviewed，然后调用 activate_version。但如果 activate_version 失败（如 DAG 验证失败），版本状态会停留在 reviewed，导致数据不一致。应该在 activate_version 内部处理回滚场景，而不是在外部修改状态。

6. **验收标准 #3 步骤 7 Redis 事件发布失败处理不明确**: 第 54 行说"通过 Redis Pub/Sub 发布事件"，但如果 Redis 不可用，事件发布失败，激活是否应该回滚？当前实现（第 172-177 行）只记录警告，不回滚事务。这意味着版本已激活，但诊断引擎没有收到通知，不会热加载新版本，导致诊断引擎使用旧版本故障树。应该明确：**Redis 事件发布失败时，激活事务应该回滚**。

7. **技术实现 #2 verify_signature 缺少时间常数比较**: 第 138-156 行使用 `hmac.compare_digest` 防止时序攻击，但在验证签名长度和十六进制格式时（第 139-146 行），使用了普通的 `len()` 和 `int()` 函数，这些操作的执行时间取决于输入，可能泄露签名信息。应该在验证前先用常数时间检查。

### 中严重程度问题（Major）

8. **技术实现 #3 create_version 的快照序列化不完整**: 第 73-90 行构建快照时，`config` 字段（第 84 行）是 Text 类型，可能包含 JSON 字符串。如果直接序列化，会导致双重编码（JSON 字符串被再次 JSON 编码）。应该先解析 config，再序列化到快照中。

9. **验收标准 #2 审批流程缺少状态转换限制**: 第 37-41 行只说"将版本从 draft 改为 reviewed"，但没有说明如果版本已经是 reviewed 或 active 状态，是否可以重复审批。如果允许，可能导致审批记录被覆盖。应该明确：**只有 draft 状态的版本可以审批**。

10. **技术实现 #1 表结构缺少 version_number 的范围约束**: 第 101 行 `version_number INTEGER NOT NULL`，但没有添加 CHECK 约束确保 version_number > 0。如果代码逻辑错误，可能创建 version_number = 0 或负数的版本。

11. **技术实现 #3 create_version 的版本号生成有竞态条件**: 第 92-99 行使用 SELECT FOR UPDATE 获取最大版本号，但锁定的是 `FaultTreeVersion.version_number` 字段，而不是整行。如果两个事务同时执行，都读到 last_version = 5，都会创建 version_number = 6，违反 UNIQUE 约束。应该锁定整个表或使用数据库序列。

12. **验收标准 #5 回滚逻辑缺少回滚次数限制**: 第 72-77 行允许无限次回滚，但如果管理员频繁回滚（如在两个版本之间来回切换），会导致大量 Redis 事件和诊断引擎频繁重载，影响性能。应该添加回滚频率限制（如 5 分钟内最多回滚 3 次）。

13. **技术实现 #6 API 路由缺少请求幂等性保证**: 第 298-335 行的 API 路由都没有幂等性设计。如果客户端因为网络超时重试请求，可能导致重复操作（如重复创建版本、重复激活）。应该添加幂等性 token 或使用乐观锁。

### 低严重程度问题（Minor）

14. **技术实现 #4 配置验证的错误信息不友好**: 第 280-285 行的错误信息"FAULT_TREE_HMAC_KEY must be at least 32 characters"没有说明如何生成密钥。应该改为："FAULT_TREE_HMAC_KEY must be at least 32 characters. Generate with: python -c 'import secrets; print(secrets.token_urlsafe(32))'"

15. **验收标准 #6 版本列表查询缺少分页**: 第 79-92 行返回所有版本，但如果故障树有数百个版本，查询会很慢。应该添加分页参数（offset, limit）。

16. **技术实现 #3 activate_version 的日志记录不完整**: 第 141 行只记录"HMAC signature verification failed"，但没有记录 version_id、tree_id、操作者等关键信息，不利于安全审计。

17. **技术实现 #5 API 路由的错误码不一致**: 第 314-318 行 review_version 返回 403（不能审批自己创建的版本），但这是业务规则错误，应该返回 400。403 应该用于权限不足。

18. **备注 #2 密钥轮换步骤缺少验证**: 第 430 行说"等待所有版本重新激活"，但没有说明如何验证所有版本都已重新签名。应该提供查询命令：`SELECT COUNT(*) FROM fault_tree_versions WHERE hmac_signature IS NOT NULL AND <签名是用旧密钥生成的>`。

19. **技术实现 #3 create_version 缺少快照大小限制**: 第 91 行 `snapshot_json = json.dumps(snapshot, sort_keys=True)`，但没有检查快照大小。如果故障树有数千个节点，快照可能超过数据库 TEXT 字段限制（SQLite 默认 1GB，但实际应用中应该限制更小）。

20. **测试策略 #2 缺少性能测试**: 测试用例只覆盖功能和安全，没有性能测试。应该测试：1000 个版本的查询性能、并发激活的吞吐量、大快照（10MB）的序列化性能。

## 审查结论

第一轮修复后，文档质量有显著提升，但仍存在 **7 个高严重程度问题**，主要集中在：

1. **并发控制不完善**: SELECT FOR UPDATE 的锁范围错误，无法防止首次激活时的并发冲突
2. **状态转换不安全**: rollback_version 的状态修改可能导致数据不一致
3. **错误处理不明确**: Redis 事件发布失败时的处理策略不清晰
4. **签名验证逻辑错误**: 重新激活时验证旧签名会导致无法激活
5. **快照完整性验证不足**: 只验证 DAG，不验证 device_mappings

这些问题如果不修复，会导致生产环境出现：
- 数据不一致（多个 active 版本）
- 诊断引擎使用旧版本故障树（Redis 事件丢失）
- 无法重新激活版本（旧密钥已删除）
- 诊断引擎崩溃（device_mappings 缺失）

**建议**: 必须修复所有高严重程度问题后才能进入实施阶段。
