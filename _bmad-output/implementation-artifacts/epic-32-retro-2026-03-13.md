## ✅ 做得好的地方

### 1. 校准算法设计稳健可靠

**成就:**
- 从 CoolingLinkageRecord 检测功率变化 > 10% 的自然事件作为校准数据源，禁止主动制造扰动
- 3σ 异常过滤 + 极端事件/天气过滤，确保校准数据质量
- 物理合理性验证: R>0, C>0, τ=RC 在 0.5-8 小时范围, R²≥0.7
- scipy.optimize.curve_fit 最小二乘拟合，算法成熟且久经验证
- APScheduler 月度定时任务（每月 1 日 03:37）自动校准

**影响:**
- 校准服务完全独立于 API 层，可被定时任务和手动触发两种方式调用
- 异常过滤保证了校准结果不被脏数据污染

### 2. 分阶段部署设计兼顾安全与灵活性

**成就:**
- 4 阶段递进: THM→校准→TCL→VPP，每阶段有明确前置条件
- Phase 3 前置检查: 所有非 demo 区域已校准且 R²≥0.85
- Phase 4 前置检查: ≥7 天 completed 预冷计划
- force 参数允许 admin 跳过检查（记录审计日志），平衡安全与紧急需求
- 存储在 system_configs 表，复用现有配置机制，无额外基础设施

**影响:**
- 分阶段上线策略确保预冷功能逐步验证再推广
- force 机制避免了"死锁"场景（例如 demo 区域导致所有区域校准检查失败）

### 3. 对抗性审查持续产出高价值发现

**成就:**
- Story 32.1 R1 发现 3 个 P0 级问题:
  - CoolingLinkageRecord 缺少 zone_id → 需要通过 CoolingUnit→CoolingZoneUnit 反查
  - CabinetTemperatureSensor 温度传感器查找路径不明确 → 确认 CoolingZoneCabinet→Cabinet→Sensor 链路
  - UniqueConstraint 保护并发校准冲突 → 添加 (cooling_zone_id, is_active) 约束
- Story 32.2 R1 发现 2 个 P0 级问题:
  - is_calibrated 字段不存在 → 改用 fitting_method + is_active 组合判断
  - zone.name → zone.zone_name（CoolingZone 模型实际字段名）
- 两轮审查模式（R1 找问题 + 修复 → R2 再检查）继续证明其稳定价值

**影响:**
- 审查发现的 P0 问题（错误字段名、缺失关联路径）如果流入实施，会导致运行时错误
- Story 32.3 和 32.4 的 P0 问题显著减少，说明前两个 Story 的经验被后续复用

### 4. 自管理 Session 模式统一且清晰

**成就:**
- calibrator 和 deployment_phase_service 均采用自管理 `async_session()` 模式
- API 层不传递 db session 给校准/部署服务，避免事务嵌套
- 只有标准 CRUD 操作（如 calibration-history 查询）走 API 层 Depends(get_db)
- 这一模式从 Epic 31 的 executor/scheduler 延续下来，团队已形成共识

**影响:**
- 消除了跨层事务管理的复杂性
- 服务可独立由定时任务或 API 调用，无需关心调用者的事务上下文

### 5. 前后端 API 格式一致性

**成就:**
- 4 个新端点全部遵循统一响应格式 `{code, message, data}`
- 前端 precool.ts 追加 4 个函数 + 3 个类型，与现有 getDashboard/getSchedules 完全一致
- 错误码语义明确: 404=区域不存在, 422=前置条件失败, 503=scipy 未安装, 400=通用错误

**影响:**
- 前端 DeploymentPhaseView.vue 复用了 PrecoolScheduleView.vue 的完整 API 调用模式
- 错误处理逻辑清晰，不同错误码有不同的用户提示

## 🔧 需要改进的地方

### 1. UniqueConstraint 限制校准历史保留

**问题:**
- Story 32.1 的 AC 要求"保留最近 10 次校准记录"
- 但 `thermal_parameters` 表的 `(cooling_zone_id, is_active)` UniqueConstraint 限制每个 zone 最多 2 条记录（1 active + 1 inactive）
- 实际只能保留 1 条活跃 + 1 条历史，远低于 10 条要求
- Story 32.1 完成时将此作为已知限制记录，但未修复

**影响:**
- 校准历史无法追溯超过 1 条旧记录
- calibration-history API 返回数据有限

**改进建议:**
- 将 UniqueConstraint 改为仅约束 `(cooling_zone_id, is_active=True)` 的部分唯一索引
- 或将历史记录分离到独立的 calibration_log 表

### 2. echarts.ts 按需注册文档仍未添加

**问题:**
- Epic 31 回顾 P1 行动项"echarts.ts 添加按需注册文档注释"在 Epic 32 期间未完成
- 连续两个 Epic 未处理此项
- 目前 echarts.ts 已有 9 个注册组件，后续开发者使用新 ECharts 功能时可能遗漏注册

**影响:**
- 新增 ECharts 图表类型时可能遗漏注册导致运行时崩溃（build 不报错）
- 此为低成本高收益的改进项

**改进建议:**
- 在 echarts.ts 文件头部添加 3-5 行注释说明按需注册机制

### 3. TypeScript Axios 响应层级不一致

**问题:**
- Story 32.4 代码审查发现 TypeScript 类型错误
- Axios 拦截器可能解包一层响应，导致 `res.data` 的层级不确定
- 解决方案是 `(res as any).data` + `body?.data ?? body` 的防御性处理
- 这一模式在 PrecoolScheduleView.vue 中已存在，但缺乏文档化

**影响:**
- 每个新的 Vue 组件调用 API 时都可能遇到相同的类型问题
- `as any` 绕过了 TypeScript 的类型检查，降低了类型安全性

**改进建议:**
- 考虑统一 Axios 拦截器行为，确保响应层级一致
- 或在 request.ts 中导出类型化的 helper 函数

### 4. 测试数据与 UniqueConstraint 冲突

**问题:**
- Story 32.3 测试中创建多条 ThermalParameter 记录时触发 UniqueConstraint 冲突
- 需要为每条测试记录使用不同的 zone_id，增加了 fixture 复杂度
- 测试设计需要了解数据库约束细节

**影响:**
- 后续涉及 ThermalParameter 的测试需要特别注意约束限制
- 测试 fixture 设计成本增加

## 🎯 经验教训

### 1. 对抗性审查发现率随 Epic 推进下降

**教训:**
- Story 32.1: 3P0+8P1（首个 Story，新概念多）
- Story 32.2: 2P0+1P1（复用 32.1 经验）
- Story 32.3: 0P0（API 层是成熟模式）
- Story 32.4: 1P0+1P1（前端错误处理细节）
- P0 发现率从首个 Story 的 3 个递减到后续的 0-1 个

**应用:**
- Epic 首个 Story 的审查应投入最多精力，因为它定义了后续 Story 的技术模式
- 成熟的技术模式（如 API 层）P0 发现率低，审查可以更聚焦于业务逻辑

### 2. 自管理 Session 模式是跨层服务的最佳实践

**教训:**
- calibrator 和 deployment_phase_service 都需要被定时任务和 API 两种调用者使用
- 传递 db session 参数会创建调用者和服务的强耦合
- 自管理 session 让服务完全自治，调用者只需要知道方法签名

**应用:**
- 后续需要被定时任务调用的服务，优先采用自管理 session 模式
- API 层的 Depends(get_db) 仅用于简单的 CRUD 查询

### 3. UniqueConstraint 设计需提前评估业务需求

**教训:**
- `(cooling_zone_id, is_active)` 约束在防并发方面很有效
- 但它阻止了"保留 10 条历史"的业务需求
- 约束设计时应同时考虑"保护什么"和"限制什么"

**应用:**
- 数据模型设计时需评估 UniqueConstraint 对历史数据保留的影响
- 如果业务需要历史记录，考虑用部分唯一索引或分离历史表

### 4. 前端 Axios 响应模式需要团队共识

**教训:**
- `(res as any).data` 模式在多个组件中重复出现
- 每次新组件开发都可能踩到相同的坑
- 这是一个框架级别的问题，不应该在每个组件中单独处理

**应用:**
- 考虑在 request.ts 中标准化响应处理，消除组件层面的 `as any`

### 5. 从 Service 到 API 到前端的完整链路交付效率高

**教训:**
- Epic 32 的 4 个 Story 按依赖链路顺序交付: 校准算法→部署控制→API→前端
- 每个 Story 产出被下一个 Story 直接消费
- 这种"管道式"交付避免了集成时的惊喜

**应用:**
- 后端→API→前端的分层 Story 拆分模式适合技术栈明确的功能开发
- 确保 Story 依赖链是线性的，避免循环依赖
