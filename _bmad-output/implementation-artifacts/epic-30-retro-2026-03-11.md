## ✅ 做得好的地方

### 1. 多层安全防线设计一脉相承

**成就:**
- 继承 Epic 29 的"分层安全"理念：约束引擎 → 回退保护 → API 查询 → 前端可视化，形成完整的安全闭环
- 约束引擎支持三类独立检查（温度/功率/速率），每类检查失败不影响其他检查
- 7 项回退保护机制各自独立 try/except 隔离，单项故障不影响其他保护
- WebSocket 推送失败不阻断核心回退逻辑

**影响:**
- 安全机制高度容错，即使部分传感器离线或 WebSocket 断开，核心保护仍然有效
- 遵循了 Epic 29 回顾中提出的"每个关键计算都应有降级/兜底路径"

## 🔧 需要改进的地方

### 1. 条件 2 的预测速率使用硬编码占位符

**问题:**
- Story 30.2 条件 2（温升超预测 150%）使用 SystemConfig `rollback_predicted_rate` 默认 2.0°C/h
- 这是因为 Epic 31 的预测调度尚未实现，无法获取实际预测速率
- 注释标注为 "TODO: Epic 31 替换为实际预测值"

**影响:**
- 当前条件 2 的触发阈值是固定的，非真正的"超预测"判断
- Epic 31 实现后需要回来替换

**改进建议:**
- Epic 31 实施时优先替换此占位符（在 Story 31.2 执行引擎中）

### 2. UPS/湿度条件无点位数据时静默跳过

**问题:**
- Story 30.2 条件 6（UPS 切换）和条件 7（湿度露点）在没有对应传感器点位时自动跳过不检测
- 这是合理的降级行为，但缺少日志记录

**影响:**
- 运维人员无法直观知道哪些保护条件因缺少传感器而未生效

**改进建议:**
- 在系统启动时记录一次各条件的点位可用性状况（INFO 级别日志）
- 在前端 Dashboard 中展示各保护条件的启用状态

### 3. Edit 工具导致的前端构建错误

**问题:**
- Story 30.4 集成 CoolingLinkageMonitor.vue 时，Edit 工具的 old_string 匹配丢失了部分 HTML 标签
- 导致 "Element is missing end tag" 构建错误
- 需要手动修复恢复被丢失的 `<el-col>`, `<el-card>`, `<template #header>` 等元素

**影响:**
- 额外的调试和修复时间

**改进建议:**
- 在复杂 Vue 模板中使用 Edit 工具时，old_string 应包含足够的上下文
- 编辑后立即运行 `npm run build` 验证

### 4. 前端组件缺少自动化测试

**问题:**
- RollbackStatusCard.vue 和 RollbackTimeline.vue 没有前端单元测试
- 仅通过 `npm run build` 验证了编译通过

**影响:**
- 前端组件的逻辑（状态计算、WebSocket 处理、分页逻辑）未被测试覆盖

**改进建议:**
- 后续前端组件考虑添加 Vitest 单元测试

## 🎯 经验教训

### 1. WebSocket 消息格式需要精确文档化

**教训:**
- Story 30.4 审查发现 WebSocket 消息结构的理解偏差（action 在顶层 vs data 内）
- 后端 `broadcast_alarm` 将 action 提取到顶层，data 包含剩余字段
- 前端 handler 使用 `const { action, data } = message` 解构

**应用:**
- 在 Story 文档中明确记录消息格式示例
- WebSocket 消息结构变更需要前后端同步审查

### 2. Props 数据源设计需要全局视角

**教训:**
- Story 30.4 审查发现 headroom 不应通过独立 API 调用获取（RollbackStatusCard 内部调用）
- 而应从父组件 CoolingLinkageMonitor 已有的 zoneList (DashboardZone[]) 通过 computed 传入
- 避免了不必要的 API 重复调用

**应用:**
- 组件设计时先审视父组件已有的数据，通过 props 传递优于组件内部重新获取
- 减少网络请求，提升响应速度

### 3. 循环导入的系统性解决方案

**教训:**
- Story 30.1 遇到 constraints.py 与 datacenter_shift_strategy.py 的循环导入
- 采用方案 A（独立默认值 + SystemConfig 覆盖 + lazy import）成功解决
- 这与 Epic 29 Story 29.7 的 lazy import 模式一致

**应用:**
- 项目中 precool 模块与 load_shift 模块之间存在结构性的循环依赖风险
- 考虑在 Epic 31 中评估是否需要重构模块依赖关系
