## 关键经验教训

### 棕地增强模式成熟

1. **后端模型/API 已存在，增强而非重建** — 工单、巡检、知识库的 Model/Schema/API 在早期 Epic 中已搭建骨架。本 Epic 主要工作是状态机完善、前端页面创建、业务规则补充。这种棕地增强模式效率高，但需要仔细核对已有代码的字段名和接口签名。

2. **工单状态机严格化** — 11-1 引入 VALID_TRANSITIONS 映射表，状态只能通过专用端点变更（accept/close），从 WorkOrderUpdate 中移除 status 字段。这个模式在 11-5 审批流程中得到验证。

3. **前端 API 字段名不一致问题** — 11-3 知识库发现前端 API 类型定义与后端字段名不匹配（keywords vs tags, views vs view_count），棕地项目中这类问题需要在实施前逐一核对。

### 技术模式沉淀

- **工单生命周期**：pending → assigned → accepted → processing → completed → closed，每次状态变更自动写入 WorkOrderLog
- **告警自动创建工单**：AlarmWorkOrderRule 规则匹配（按告警级别+类型），自动派单到指定人员
- **审批流程**：变更请求类工单需审批，审批超时自动升级，驳回需填写原因
- **巡检任务生成**：从计划自动生成任务，支持 pending → in_progress → completed 状态机

### 注意事项

- 工单编号格式 WO-20260217-0001 依赖当日最大序号查询，高并发场景需考虑序号冲突
- 审批超时时间默认 24 小时，生产环境需根据组织架构调整
