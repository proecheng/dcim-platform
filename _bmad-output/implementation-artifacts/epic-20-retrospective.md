## 关键经验教训

### 统一页面结构模式

- 4 个页面均遵循"统计卡片 → 工具栏 → 表格 → 对话框"结构，使用 `page-list` preset。
- 与 Epic 18 的 `page-dashboard` preset 形成互补：监控类页面用 dashboard，管理类页面用 list。
- 这两种 preset 覆盖了系统中绝大多数页面类型。

### 前端计算引擎

- 20.2 实现了纯前端规则测试引擎（`evaluateGroup` 递归函数），支持 AND/OR 逻辑和嵌套条件组。
- 20.4 实现了前端状态计算（`computeStatus`），根据时间判断屏蔽策略状态。
- 前端计算避免了后端往返，提升了交互响应速度。

### 递归组件设计

- 20.2 的 `CompoundConditionGroup.vue` 是项目中首个递归组件，处理嵌套条件组的渲染和编辑。
- 关键约束：最大嵌套深度 3 层、单规则条件数上限 20 条——这些限制在对抗性审查中提前确定。
- 条件树数据结构（`ConditionItem` / `ConditionGroup`）设计清晰，序列化为 JSON 存入 `condition_expr` 字段。

### API 字段复用策略（技术债务）

- 20.3 将升级链节点列表序列化为 JSON 存入 `description` 字段。
- 20.4 将屏蔽范围（全局/区域/设备类型）和级别列表编码到 `reason` 字段 JSON 中。
- **优点**：避免后端改动，纯前端实现功能扩展。
- **风险**：字段语义被改变，后端 schema 定义为普通字符串但实际存储 JSON 结构化数据。后端数据校验或迁移可能破坏这些数据。
- **建议**：在 project-context.md 中记录这些字段复用约定，确保后续开发者知晓。

### ECharts markLine 设计决策

- 20.1 原始需求为"拖拽阈值线调整值"，但 ECharts 原生不支持 markLine 拖拽。
- 最终采用"输入框 + 实时预览"方案，用户体验更稳定可靠，避免了大量 hack 代码。
- 这是一个正确的技术妥协——功能等价但实现成本大幅降低。

### 对抗性审查价值

- 20.2 和 20.4 的 Story 文件包含对抗性审查记录，提前识别了：
  - 条件树深度限制（防止 UI 崩溃）
  - 点位选择器数据量（限制加载前 100 个）
  - API 字段限制（reason/description 字段 JSON 编码方案）
  - 批量屏蔽策略（全局屏蔽 vs 逐点位创建）
- 审查在实现前解决了这些问题，避免了开发中途返工。
