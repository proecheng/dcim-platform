# Story 24.2 对抗性审查报告 - 第二轮

**审查日期**: 2026-03-06
**审查对象**: Story 24.2 - 诊断调度器与并发控制（修复后）
**审查类型**: 对抗性审查（第二轮）

---

## 审查发现

### 高严重程度问题（Critical）

1. **CancellablePriorityQueue.put() 逻辑冗余**: 第 92-93 行先过滤已取消任务并 heapify，然后第 98 行又重新过滤一次 `active_tasks`。这导致性能浪费（两次遍历）。应该在第 92 行过滤后直接使用 `self._queue` 而非再次过滤。

2. **DiagnosisScheduler 缺少 L1RuleEngine 初始化错误处理**: 第 220 行调用 `await self.l1_engine.load_rules()`，但如果加载失败（如数据库连接失败），调度器会启动但无法正常工作。应该捕获异常并拒绝启动。

3. **自动升级逻辑缺少去重检查**: 第 350-357 行，L1 未匹配时自动升级到 L2，但没有检查该告警是否已经有 L2 诊断记录。如果用户手动触发了 L2 诊断，自动升级会导致重复诊断。应查询 `diagnosis_results` 表检查是否已有 L2 结果。

4. **全局限流函数未定义**: API 端点第 548 行使用 `Depends(global_rate_limiter(times=30, seconds=60))`，但文档未提供 `global_rate_limiter` 的实现代码。应补充实现或说明需要在 `backend/app/api/deps.py` 中添加该函数。

### 中严重程度问题（Major）

5. **DiagnosisScheduler.stop() 等待队列清空时 worker 仍在运行**: 第 238 行设置 `self.running = False`，但 worker 协程（第 301-314 行）会继续从队列取任务并执行。如果队列中有耗时任务（如 L2 推理 10 秒），等待 30 秒可能不够。应该先停止接收新告警（取消订阅协程），再等待队列清空。

6. **手动触发时缺少设备存在性验证**: `trigger_manual` 方法第 406-436 行接受 `device_id`，但未验证该设备是否存在。如果设备不存在，推理会失败但任务已入队，浪费资源。应在入队前查询数据库验证设备存在。

7. **DiagnosisResult 模型缺少 site_id 字段**: 根据 Epic 13 和 16，系统支持多站点数据隔离，但 DiagnosisResult 表未包含 `site_id` 字段。这会导致跨站点数据泄漏（operator 可以看到其他站点的诊断结果）。应添加 `site_id` 外键并在查询时过滤。

8. **验收标准与实现不一致 - L2 未匹配是否升级到 L3**: 验收标准第 39 行说"次要/提示告警记录'L1未匹配'结果，不自动升级"，但未说明 L2 未匹配时是否升级到 L3。实现第 350-357 行只检查 `inference_level == "L1"`，如果 L2 未匹配会怎样？应明确规格。

9. **Redis 重连机制可能导致重复订阅**: `_subscribe_alarms` 方法第 256-289 行，如果订阅成功后连接断开，会重新订阅。但如果 Redis 服务端认为旧订阅仍然有效，可能导致重复接收消息。应在重连前调用 `pubsub.unsubscribe()` 或 `pubsub.close()`。

10. **CancellablePriorityQueue.qsize() 不是线程安全的**: 第 148-152 行，`qsize()` 方法未加锁，在并发环境下可能返回不准确的值（如在遍历过程中其他协程修改了队列）。虽然不影响功能，但可能导致监控数据不准确。应加锁或使用 `len(self._queue)` 后再过滤。

### 低严重程度问题（Minor）

11. **测试策略缺少 Redis 订阅失败场景**: 单元测试第 617-628 行列出了 9 个测试用例，但缺少 Redis 订阅失败和重连的测试。应添加：
    - Redis 连接断开后自动重连
    - 重连期间告警不丢失（或明确说明会丢失）
    - 重连延迟符合指数退避策略

12. **性能测试缺少队列满场景**: 性能测试第 644-648 行未包含队列满时的性能测试。应添加：
    - 队列满时新任务的丢弃/替换性能（应 < 1ms）
    - 队列满时的日志记录不影响吞吐量

13. **DiagnosisScheduler 缺少健康检查方法**: 文档提到 API 端点包含 `health`（第 573 行 TODO），但调度器类未提供健康检查方法（如 `is_healthy()` 返回 Redis 连接状态、队列大小、worker 状态等）。应补充该方法。

14. **Alembic 迁移脚本缺少 site_id 字段**: 如果需要支持多站点隔离（问题 7），迁移脚本第 487-515 行应包含 `site_id` 字段定义。

15. **日志记录缺少结构化信息**: 第 291 行日志 `f"Alarm {alarm_id} dropped (queue full, low priority)"` 缺少结构化字段（如 `extra={"alarm_id": alarm_id, "priority": priority}`），不利于日志分析和告警。建议使用结构化日志。

16. **验收检查清单缺少"实现 global_rate_limiter 函数"**: 第 667-685 行的检查清单未包含"在 deps.py 中实现 global_rate_limiter 函数"，但这是必需步骤（问题 4）。

17. **估算工作量仍未包含审查时间**: 第 704-707 行估算 3-4 天，但两轮对抗性审查和修复已花费约 1 天，实际工作量应为 4-5 天。

18. **DiagnosisScheduler 缺少指标收集**: 调度器未收集关键指标（如队列长度、推理耗时、成功/失败率），不利于监控和调优。应考虑集成 Prometheus 或类似监控系统。
