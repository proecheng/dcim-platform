# Story 24.3 第一轮对抗性审查报告

**审查日期**: 2026-03-06
**审查对象**: Story 24.3 实施文档
**审查类型**: 对抗性文档审查

---

## 审查发现

### 高严重程度问题（Critical）

1. **验收标准 #2 DAG 验证器逻辑不完整**: 第 39 行要求"检查是否存在孤立节点（除根节点外，所有节点必须有入边或出边）"，但这个定义有歧义。中间节点（intermediate）应该既有入边又有出边，叶节点只有入边无出边。当前定义允许中间节点只有入边或只有出边，这会导致无效的故障树结构通过验证。

2. **技术实现 #1 表结构 prior_probability 允许 NULL**: 第 131 行 `prior_probability` 字段没有 `NOT NULL` 约束。如果叶节点的先验概率为 NULL，L2 推理引擎在计算时会崩溃（无法对 NULL 进行数学运算）。应该要求叶节点的 prior_probability 必填，或者在代码中提供默认值（如 0.5）。

3. **技术实现 #2 DAG 验证器错误处理不一致**: 第 222-229 行，如果 `nx.is_directed_acyclic_graph()` 返回 False，代码尝试用 `nx.find_cycle()` 找出环，但如果找不到环（`NetworkXNoCycle` 异常），代码只是 `pass` 继续执行，最终返回 `True, ""`（第 246 行），这会导致实际有环的图被误判为有效 DAG。

4. **技术实现 #2 DAG 验证器性能问题**: 第 239-244 行使用 `nx.descendants()` 检查连通性，但对于大型故障树（1000+ 节点），这个操作的时间复杂度是 O(V+E)。如果每次创建边都触发完整的 DAG 验证（验收标准 #5 第 81 行），在批量创建 150 条边时会执行 150 次 O(V+E) 操作，总复杂度 O(E×(V+E))，远超性能目标（500ms）。应该优化为增量验证或延迟验证（只在提交时验证一次）。

5. **备注 #1 SQLite 兼容性说明自相矛盾**: 第 473 行说"避免使用 PostgreSQL 特有语法如 `JSONB`"，但技术实现 #1（第 133 行）和 #4（第 349 行）的表结构和 ORM 模型都使用了 `JSONB`。如果真的要兼容 SQLite，应该在 Alembic 迁移脚本中使用条件判断（`if dialect == 'sqlite': use TEXT else: use JSONB`），或者在 ORM 模型中使用 SQLAlchemy 的 `JSON` 类型（自动适配不同数据库）。

6. **技术实现 #1 表结构 evidence_point_id 外键约束过于严格**: 第 132 行要求叶节点关联 `points` 表，但如果点位被删除，外键约束会阻止删除或导致叶节点的 evidence_point_id 变为 NULL（如果使用 ON DELETE SET NULL）。应该明确说明删除点位时的处理策略（阻止删除、级联删除叶节点、或设为 NULL 并标记故障树为 invalid）。

### 中严重程度问题（Major）

7. **验收标准 #4 节点删除缺少级联影响检查**: 第 67 行允许删除节点，但未说明删除节点后如何处理依赖该节点的边。如果删除一个中间节点，所有连接到该节点的边会变成悬空边（dangling edges），导致故障树结构损坏。应该要求删除节点前先删除所有相关的边，或者自动级联删除相关边。

8. **验收标准 #5 边更新操作缺失**: 第 73-82 行只定义了边的创建、查询和删除，但没有更新操作（PUT）。如果管理员需要修改边的端点（如将 parent_node_id 从 A 改为 B），当前 API 无法支持，只能先删除再创建，这在事务中可能导致临时的无效状态。

9. **验收标准 #6 设备映射更新操作缺失**: 第 84-94 行同样缺少 PUT 操作。如果管理员需要修改映射的 priority 或 alarm_type，当前 API 无法支持。

10. **验收标准 #7 批量操作缺少部分成功处理策略**: 第 96-103 行要求"验证失败时回滚整个事务"，但未说明如果批量创建中部分节点或边的数据格式错误（如 prior_probability 超出范围），是全部回滚还是跳过错误项继续创建。全部回滚可能导致大量有效数据被丢弃，但跳过错误项又可能导致故障树结构不完整。

11. **技术实现 #1 表结构缺少唯一性约束**: 第 113-121 行 `fault_trees` 表没有对 `name` 字段添加唯一性约束。如果允许多个故障树同名，在 UI 选择时会产生歧义（"UPS 故障树 v1" 和 "UPS 故障树 v1" 无法区分）。应该添加 `UNIQUE(name)` 或 `UNIQUE(name, status)` 约束。

12. **技术实现 #1 表结构缺少 updated_by 字段**: 第 119 行 `fault_trees` 表有 `updated_at` 但没有 `updated_by`，无法追踪谁最后修改了故障树。这在多管理员环境下会导致审计信息不完整。

13. **技术实现 #3 API 路由缺少 Pydantic Schema 定义**: 第 261-311 行的 API 路由只有函数签名，但没有定义请求和响应的 Pydantic Schema（如 `FaultTreeCreate`, `FaultTreeResponse`）。这会导致 FastAPI 无法自动生成 Swagger 文档，也无法进行请求参数验证。

14. **测试策略 #2 API 集成测试缺少并发测试**: 第 396-410 行的测试用例都是单线程顺序执行，但验收标准 #5 第 81 行要求"创建边时自动触发 DAG 验证"。如果两个管理员同时创建边，可能导致竞态条件（race condition）：两个请求都通过了 DAG 验证，但合并后的图包含环。应该添加并发创建边的测试用例。

### 低严重程度问题（Minor）

15. **技术实现 #4 ORM 模型使用 datetime.utcnow 而非 datetime.now(timezone.utc)**: 第 330-331 行和其他地方使用 `datetime.utcnow`，但 Python 3.12+ 已弃用此方法。应该使用 `datetime.now(timezone.utc)` 或 SQLAlchemy 的 `func.now()`。

16. **技术实现 #4 ORM 模型缺少反向关系**: 第 352 行 `FaultTreeNode` 只定义了 `tree` 反向关系，但没有定义 `parent_edges` 和 `child_edges` 关系。这会导致查询"某个节点的所有父节点"或"某个节点的所有子节点"时需要手动 JOIN，降低代码可读性。

17. **测试策略 #1 单元测试缺少边界情况**: 第 386-394 行列出了 8 个测试用例，但缺少以下边界情况：(1) 自环（节点指向自己）；(2) 重复边（A→B 添加两次）；(3) 叶节点有出边；(4) 根节点有入边；(5) 中间节点 gate_type 为 NULL。

18. **测试策略 #3 性能测试标准不明确**: 第 412-416 行定义了性能目标，但没有说明测试环境（CPU、内存、数据库类型）。"1000 节点故障树加载时间 < 2 秒"在开发机（SQLite）和生产环境（PostgreSQL + 网络延迟）的表现可能差异巨大。应该明确测试环境或提供不同环境的性能基线。

19. **依赖关系缺少 NetworkX 版本依赖说明**: 第 420-429 行列出了前置和后续依赖，但备注 #2（第 475 行）提到需要 `networkx>=3.0`，这应该在依赖关系章节明确说明，因为 NetworkX 3.0 与 2.x 有 breaking changes（如 `nx.find_cycle` 返回值格式不同）。

20. **验收检查清单缺少数据迁移验证**: 第 433-446 行的检查清单没有包含"从空数据库执行迁移"和"从已有数据的数据库执行迁移"两种场景。如果迁移脚本在已有 `diagnosis_rules` 表的数据库上执行，可能因为表名冲突或字段冲突导致失败。
