## 审查发现

### 高严重程度问题（Critical）

**无高严重程度问题**

第二轮深度审查发现的所有高严重程度问题已全部修复：
- ✅ 问题 1: 重新激活时不再验证旧签名，直接生成新签名覆盖
- ✅ 问题 2: 添加了快照完整性验证（检查 tree、nodes、edges、device_mappings）
- ✅ 问题 3: SELECT FOR UPDATE 锁定所有版本记录，不限状态
- ✅ 问题 5: rollback_version 直接调用 activate_version，不修改状态
- ✅ 问题 6: Redis 事件发布失败只记录错误日志，不回滚事务
- ✅ 问题 11: create_version 先锁定整个 tree 的版本记录，再获取版本号

### 中严重程度问题（Major）

1. **version_manager.py 第 218 行回滚频率限制逻辑错误**: 使用 `activated_at >= cutoff_time` 统计最近激活次数，但这会统计所有激活操作（包括正常激活），而不是只统计回滚操作。应该添加一个 `is_rollback` 字段或使用其他方式区分回滚和正常激活。

2. **version_manager.py 第 113 行状态检查不完整**: 允许 archived 状态的版本激活，但没有检查该版本是否是最近的 archived 版本。如果管理员激活一个很旧的 archived 版本（跳过中间版本），可能导致配置回退过多。

3. **fault_tree_versions.py 缺少 HTTP 429 状态码导入**: 第 147 行使用 `status.HTTP_429_TOO_MANY_REQUESTS`，但文件开头没有导入这个常量。

### 低严重程度问题（Minor）

4. **version_manager.py 第 217 行使用 datetime.utcnow()**: 应该使用 `datetime.now(timezone.utc)` 或 `func.now()`，`utcnow()` 已被弃用。

5. **version_manager.py 第 90 行锁定范围过大**: 锁定整个 tree 的所有版本记录，如果有大量版本，锁定时间会很长。可以优化为只锁定一个虚拟行（如使用 advisory lock）。

6. **fault_tree_versions.py 第 31 行错误信息不一致**: 中文错误信息"只有 draft 状态的版本可以审批"，但其他地方使用英文。应该统一语言。

7. **version_manager.py 缺少快照大小限制**: 没有检查 snapshot_json 的大小，如果故障树有数千个节点，可能超过数据库限制。

8. **version_manager.py 第 60 行 config 字段处理不完整**: 如果 config 是 JSON 字符串，会导致双重编码。应该先解析再序列化。
