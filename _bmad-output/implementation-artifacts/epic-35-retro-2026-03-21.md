## ✅ 做得好的地方

### 1. Story 拆分层次清晰，依赖链路递进合理

**成就:**
- 35.1（数据模型+批量创建）→ 35.2（故障隔离逻辑）→ 35.3（告警+前端展示）
- 每个 Story 有明确边界：35.1 建模型基础、35.2 做运行时状态管理、35.3 做告警可视化
- 3 个 Story 间零集成冲突，后 Story 自然消费前 Story 产出

**影响:**
- 无需回退修改已完成 Story 的代码
- parent_datasource_id 字段在 35.1 创建，35.2/35.3 直接使用

### 2. 对抗性审查持续发现高价值问题

**成就:**
- 35.1 R1+R2 审查发现 18 处问题（含 IPv4 验证缺失、baud_rate 枚举、mac_address 范围约束）
- 35.2 R1+R2 审查发现关键设计修正：connect() 超时保护、条件恢复逻辑、flush 保证 SELECT 读到最新值
- 35.3 R1 审查发现 11 项问题（含 point_id nullable JOIN 风险、julianday() 方言依赖、N+1 子设备告警关闭、跨模块耦合）
- 35.3 R2 审查发现 8 项边缘场景（孤儿设备、WebSocket 时序、point_id NULL 聚合）
- 代码审查额外发现：alarm_type String(20) 溢出风险、幂等检查缺少 alarm_type 作用域、created_at 空值防护、前端死代码

**影响:**
- 所有 CRITICAL/HIGH 问题在合并前修复
- 形成了"R1 通用审查 → R2 边缘场景 → 实施后代码审查"三层质量门

### 3. 共享模块提取时机恰当

**成就:**
- 35.3 R1#5 发现 gateway_monitor 和 communication_monitor 都需要告警创建/恢复方法
- 立即提取 `datasource_alarm.py` 共享模块，而非让两个 monitor 互相导入
- 三个公共函数（create/resolve/resolve_batch）接口清晰，职责单一

**影响:**
- 避免了 gateway_monitor ↔ communication_monitor 循环依赖
- 后续新增告警类型只需调用共享模块

### 4. asyncio.wait_for 超时保护设计实用

**成就:**
- 35.2 R2#8 发现 BacnetIpAdapter.connect() 可能永久阻塞
- 统一对 connect() 和 test_connection() 使用 asyncio.wait_for(timeout=10s)
- try/finally 确保 adapter.disconnect() 总是被调用

**影响:**
- 单个网关故障不会阻塞整个健康检查循环
- 定时任务的 30s 周期内可完成多个网关探测

### 5. commit-first-then-broadcast 模式一致

**成就:**
- 35.3 gateway_monitor 和 communication_monitor 均采用"先收集广播消息 → commit 成功后再推送 WebSocket"
- `_probe_gateway()` 返回 `list[dict]` 待推送消息，由 `check_mstp_gateway_health()` 统一在 commit 后推送
- communication_monitor 同理，pending_alarm_broadcasts 在 commit 后遍历

**影响:**
- 避免了数据库回滚后 WebSocket 已推送"幽灵告警"的问题
- WebSocket 推送失败不影响告警数据持久化

## 🔧 需要改进的地方

### 1. alarm_type 列宽度差点引发 PostgreSQL 溢出

**问题:**
- 原始 `alarm_type = Column(String(20))`，`mstp_gateway_offline` 恰好 20 字符
- SQLite 不强制 VARCHAR 长度，测试通过但 PostgreSQL 会截断或报错
- 代码审查才发现此问题，R1/R2 审查均未注意

**改进建议:**
- 新增数据库列时，对抗性审查应检查字段长度 vs 实际值长度
- 建议所有 String 列预留 2x 余量

### 2. 幂等检查缺少 alarm_type 维度

**问题:**
- 初始实现仅检查 `source + status=active`，未按 alarm_type 区分
- 理论上同一 DataSource 可能同时有不同类型告警（虽然实际不太可能）
- 代码审查发现后修复

**改进建议:**
- 幂等性设计时明确"唯一性键"包含哪些维度
- Story Dev Notes 中应显式列出幂等键定义

### 3. 告警 API N+1 查询未在本 Epic 修复

**问题:**
- alarm API 的 `get_alarms`/`get_active_alarms` 对每条告警单独查询 Point
- 35.3 增加了 datasource 级告警（point_id=NULL），加大了循环范围
- 代码审查标记为预存问题，但未修复

**改进建议:**
- 在告警 API 中使用 JOIN 或批量查询替代 N+1 循环
- 可作为后续性能优化 Story

### 4. 前端 keyword 搜索参数后端未处理

**问题:**
- datasource/index.vue 发送 `keyword` 查询参数
- `list_datasources` API 未声明 `keyword` 参数，FastAPI 静默忽略
- 用户在搜索框输入关键字无效果
- 代码审查发现的预存问题

**改进建议:**
- 后端增加 `keyword` 参数并实现 LIKE 过滤
- 或前端移除无效的搜索框

## 🎯 经验教训

### 1. SQL 级别字段更新 + ORM 内存状态需要注意 synchronize_session

**教训:**
- 35.2 `_probe_gateway()` 使用 `db.execute(update(DataSource).where(...).values(...))` 批量更新
- SQLAlchemy 默认 `synchronize_session="evaluate"` 可能更新 ORM 对象的内存状态
- 必须在 SQL UPDATE 之前捕获 `pre_probe_status = gw_ds.status`，而非 UPDATE 之后读取
- 35.2 代码已正确处理（先捕获再 UPDATE），但需要文档化此模式

**应用:**
- 涉及批量 UPDATE 后需要读取旧值的场景，先缓存再 UPDATE

### 2. SQLite 不强制 VARCHAR 长度和 NOT NULL 修改

**教训:**
- 35.3 迁移脚本不修改 `point_id` nullable（SQLite 不支持 ALTER COLUMN）
- ORM 模型层面改 `nullable=True` 在 SQLite 上可以直接 INSERT NULL
- PostgreSQL 迁移时需要额外 `ALTER COLUMN point_id DROP NOT NULL`
- `alarm_type String(20)` 在 SQLite 测试中不会报错，但 PostgreSQL 会

**应用:**
- 面向 PostgreSQL 生产环境时，所有列长度和约束修改必须有对应迁移脚本
- 测试中使用 SQLite 时，要人工审查列长度约束

### 3. 双层故障隔离中的状态跳过逻辑很关键

**教训:**
- communication_monitor 必须跳过 `gateway_offline` 状态的子设备（由 gateway_health 管理）
- 如果不跳过，communication_monitor 可能将 gateway_offline 设备恢复为 connected
- parent_status_map 预加载一次性查询所有父网关状态，避免 N+1

**应用:**
- 多个定时任务操作同一张表时，必须明确职责边界和跳过条件
- 预加载相关状态映射是避免 N+1 的有效模式

### 4. R1+R2+代码审查三层质量门各有侧重

**教训:**
- R1（对抗性审查）发现架构级问题：跨模块耦合、方言依赖、JOIN 安全性
- R2（边缘场景）发现运行时极端情况：孤儿设备、WebSocket 时序
- 代码审查发现实现级细节：列宽度溢出、幂等键不完整、死代码

**应用:**
- 三层审查覆盖不同维度，不可互相替代
- 代码审查应特别关注"接近边界值"的约束（如恰好等于最大长度）
