## 关键经验教训

### 反复出现的模式（系统性问题）

1. **`value or fallback` 陷阱**（3/4 Story：8-1, 8-3, 8-4）
   - 对 0、0.0、空字符串会误判为 falsy
   - **必须用** `if value is not None` 替代 `value or default`
   - **行动**：加入对抗性审查必查清单

2. **前后端枚举不匹配**（8-4，Epic 7 也出现过）
   - 8-4 的 `impact_level`：后端返回英文（critical/major/minor），前端显示中文
   - 代码审查阶段发现并修复
   - **行动**：建立前后端枚举常量共享机制

3. **SQLite 限制**（8-1, 8-3）
   - ALTER TABLE 限制影响迁移策略
   - 无 ISO 周号、窗口函数限制
   - 已知约束，非新增债务

### 对抗性审查高价值发现

- **8-1 C1**: SQLite ALTER TABLE 不支持 DROP COLUMN → 迁移脚本需要重建表
- **8-1 C3**: 级联删除策略 → 必须明确 `cascade="all, delete-orphan"`
- **8-1 C4**: Excel 导入竞态条件 → 需要事务隔离
- **8-3 H1**: 权重归一化 → 用户输入权重之和不为 1 时自动归一化
- **8-3 H2**: 三相不平衡系数 → 需要明确计算公式和阈值
- **8-4 C1**: PDU 类型过滤 → 区分单路/双路 PDU 的影响范围
- **8-4 H4**: 双路供电降级/断电 → 区分 degraded 和 power_loss 状态

### 代码审查高价值发现

- **8-4**: `impact_level` 前后端枚举不一致 → 前端映射表修复
- **8-1**: 多项 ORM 关系和查询优化

### 关键架构决策

> **决策**: Epic 9 联动引擎暂不引入 Redis，使用进程内内存方案（asyncio 事件总线）。设计时预留抽象接口，未来服务器迁移后可无缝切换到 Redis Pub/Sub。
>
> **理由**: 系统未来将迁移到其他服务器，当前阶段引入 Redis 增加部署复杂度，内存方案满足单实例需求。
