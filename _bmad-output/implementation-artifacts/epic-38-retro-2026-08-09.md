### 4. 做得好的地方

#### 4.1 恢复了真正完整的 CI 门禁

- 后端依赖、Ruff lint、Ruff format、compileall 和配置的完整 pytest 集合进入同一 Job。
- 后端 Job 上限适配完整测试实际运行，不再因默认上限误判失败。
- 前端 ESLint、TypeScript、完整 Vitest 和生产构建均为必过步骤。
- 覆盖率产物和安全扫描结果进入远端证据链。

#### 4.2 测试环境隔离得到落实

- 关键 E2E 使用专用 SQLite 数据库。
- Redis、Demo 和 Simulation 在 E2E 中关闭。
- 测试 HMAC key 明确配置。
- 本地热模型、拓扑和启动冒烟也使用隔离数据库，临时进程和数据已清理。

#### 4.3 发布物与测试 SHA 精确绑定

- CD 只接收 `master` 成功 CI。
- 检出 `workflow_run.head_sha`，而不是依赖分支移动位置。
- 后端、前端镜像同时生成 `sha-*` 和 `latest` 标签。
- 候选镜像 OCI revision、digest、CI/CD URL 可追溯。

#### 4.4 RC 报告没有越界声明

报告明确列出依赖漏洞、真实设备联调、生产密钥与网络、数据库迁移、备份恢复、性能/容量/安全验证和现场 UAT，不把自动化成功包装成生产批准。

### 5. 需要改进的地方

#### 5.1 管理员认证 setup 存在可复现波动

关键 E2E Job 成功，但管理员认证 setup 在两轮远端运行中都出现首次等待 `/dashboard` 超时、重试成功。重试保护了门禁可用性，也可能掩盖登录响应、路由跳转或服务就绪的真实不稳定。

#### 5.2 安全扫描尚未形成阻断或例外治理

当前 `pip-audit` 为非阻断步骤，7 个包共 28 个漏洞没有机器可读的处置状态。仅记录总数不足以支撑生产风险接受。

#### 5.3 覆盖率与测试通过是不同指标

全部配置测试通过，但总体覆盖率为 63%，低于 PRD 对核心模块 ≥80% 的目标。现有证据可支持当前软件 RC 门禁，不应据此声明所有核心路径达到覆盖率目标。

#### 5.4 docs-only 提交重复发布镜像

最终规划/证据收口提交未改变候选业务代码，但仍触发完整 CI 和双镜像发布。这样提供了最终 SHA 的完整证据，也增加了无业务变化的镜像构建和 `latest` 更新。需要明确这是合规要求还是可按路径过滤优化。

#### 5.5 生产验证仍是开放工作

- 真实 Modbus/SNMP 设备与协议网关未联调签署。
- 生产 HMAC key、JWT secret、数据库、Redis、MQTT、网络和访问控制未验证。
- 生产等价数据库迁移、备份恢复和回滚演练未完成。
- 性能、容量、安全和现场用户验收未签署。

### 7. 关键经验

1. CI 成功、E2E 成功、镜像发布成功和生产批准是四个相关但独立的状态。
2. CD 必须使用触发 CI 的精确 SHA，测试和镜像不能只靠同名分支关联。
3. 重试成功仍应记录为 flaky，不能从报告中消失。
4. 安全扫描需要可执行的阻断规则或可审计例外，而不只是生成日志。
5. 测试数量、通过率和覆盖率需要分别陈述。
6. 文档收口也应评估是否需要更新 `latest` 镜像。
