## ✅ 做得好的地方

### 1. 双认证体系设计干净分离

**成就:**
- VPP 对外端点 (POST /vpp/dispatch) 使用独立 API Key 认证 (X-VPP-API-Key header)
- 内部管理端点 (GET /vpp/dispatches, /vpp/statistics) 使用标准 JWT + RBAC 认证
- API Key 配置通过 `settings.VPP_API_KEY` 统一管理，不硬编码
- 认证逻辑写在 endpoint 层面的 `verify_vpp_api_key` dependency，非中间件，粒度可控

**影响:**
- 外部 VPP 平台和内部管理员使用完全独立的认证路径，安全隔离
- 后续若需增加 IP 白名单等限制，只需在 `verify_vpp_api_key` 中扩展

### 2. Redis 降级策略一致且健壮

**成就:**
- 速率限制：Redis 不可用时降级放行（不阻塞 VPP 指令），记录 warning 日志
- 容量缓存：Redis 不可用时降级为实时计算（不返回缓存过期数据）
- 统一使用 `redis_service.get_json/set_json` 而非 `increment/expire`（RedisService 不支持后者）
- 对抗性审查在 R1 就发现了 RedisService API 不支持 increment/expire 的问题，避免了运行时错误

**影响:**
- 系统在 Redis 故障场景下仍能正常运行，符合降级设计原则
- 速率限制的降级放行策略优先保证 VPP 指令可达性（宁可放行多余指令也不阻塞合法请求）

### 3. 时间类型处理正确无误

**成就:**
- 对抗性审查 R1 发现 PrecoolSchedule 的 `precool_start_time/precool_end_time` 是 **Time 类型**（非 DateTime）
- 冲突检测正确分离：`now.date()` 比较 `schedule_date`，`now.time()` 比较时间字段
- 这个 P0 问题如果流入实施，会导致类型比较错误和静默的逻辑 bug

**影响:**
- 冲突检测逻辑在所有时间场景下正确运行
- 证明了对抗性审查对数据模型细节的核查价值

### 4. 前端组件复用效率高

**成就:**
- VppMonitorView.vue 复用了 3 个现有组件模式：
  - `GaugeChart.vue` 仪表盘（不需要新建 VppCapacityGauge.vue，Epic 建议的独立组件被合理精简）
  - `el-page-header` 导航模式（与 CoolingLinkageMonitor/DeploymentPhaseView 一致）
  - `el-statistic` 统计卡片模式（与 ShiftDashboard 一致）
- TypeScript 类型通过 `TagType` 联合类型解决了 Element Plus el-tag `:type` 类型推断问题
- 新页面零 TypeScript 错误（项目已有文件的同类 TS 错误未波及新代码）

**影响:**
- 前端开发效率高，复用成熟组件避免了重复造轮子
- 代码风格与现有页面一致，维护成本低

### 5. 管道式 Story 交付模式继续验证有效

**成就:**
- 33.1 容量计算 → 33.2 指令处理（调用容量计算做约束校验）→ 33.3 前端（调用所有后端端点）

## 🔧 需要改进的地方

### 1. VPP 统计中 accepted_power_kw 含义模糊

**问题:**
- `get_statistics` 使用 `func.sum(VppDispatch.accepted_power_kw)` 计算"总调控量"
- 但 `accepted_power_kw` 是瞬时功率（kW），非能量（kWh）
- 实际节省电量应为 `accepted_power_kw × duration_minutes / 60`（kWh）
- 当前统计将功率直接累加，物理含义不准确

**影响:**
- 统计数据的"总调控量"和"节省电费"计算偏差
- 对于短时间高功率和长时间低功率的指令，误差方向不同

**改进建议:**
- 将统计改为 `SUM(accepted_power_kw * duration_minutes / 60.0)` 计算 kWh
- 或新增 `actual_energy_kwh` 字段在指令完成后记录实际能量

### 2. VPP 指令执行状态缺少生命周期管理

**问题:**
- VppDispatch 有 `status` 字段支持 received/accepted/rejected/executing/completed/failed
- 但当前实现只设置 received → accepted/rejected，缺少后续 executing → completed/failed 的状态流转
- 前端 statusText 映射了所有状态值，但后端实际只产生 accepted/rejected 两种终态

**影响:**
- 指令被接受后没有执行跟踪和完成确认
- 无法知道指令是否实际执行成功

**改进建议:**
- 后续 Epic 可添加执行监控：accepted → executing（开始调整制冷）→ completed/failed（调整完成/超时）
- 需要定时任务或事件驱动的状态更新机制

### 3. echarts.ts 按需注册文档仍未添加（连续 3 个 Epic 遗留）

**问题:**
- Epic 31 回顾首次提出，Epic 32 回顾再次标记未完成，Epic 33 仍未处理
- echarts.ts 已有 9+ 注册组件（GaugeChart 在 Epic 33 中被 VppMonitorView 使用）
- 新开发者使用未注册的 ECharts 功能时，build 不报错但运行时崩溃

**影响:**
- 连续 3 个 Epic 未处理表明此项被持续降优先级
- 实际风险较低（团队已熟悉机制），但对新接手的开发者不友好

**改进建议:**
- 在 echarts.ts 文件头部添加 3-5 行注释，解释按需注册机制
- 这是一个 5 分钟的改进，不应再次遗留

## 🎯 经验教训

### 1. 外部 API 认证设计需要在首个 Story 审查中彻底验证

**教训:**
- Story 33.2 的对抗性审查发现了 5 个 P0 级问题：
  - Redis API 不匹配（increment/expire 不存在）
  - PrecoolSchedule 时间字段类型（Time vs DateTime）
  - executor 单例命名错误（precool_executor_service → precool_executor）
  - Header 未导入
  - get_settings 未导入
- 这些都是"代码会编译但运行时出错"的隐蔽问题
- 外部 API 端点因为涉及独立认证体系，引入了更多的框架细节需要核查

**应用:**
- 涉及新认证体系的端点，审查时需要逐行核对 import 和依赖注入
- 对外 API 的审查应包括"如果 Redis 不可用会怎样"等降级场景

### 2. 数据模型字段的用途需要在 Story 间传递

**教训:**
- Story 33.3 复用 33.2 的 `_build_response` 方法时，发现缺少 `created_at` 字段
- Story 33.2 实现 `_build_response` 时，只考虑了 POST 响应需要的字段
- Story 33.3 的列表展示需要时间字段，但 33.2 没有预见到这个需求

**应用:**
- 在 Story 文件中明确标注"此 Story 产出的接口/方法将被后续 Story 如何使用"
- 创建服务方法时，考虑其被列表查询等场景复用的可能性

### 3. 前端 TagType 联合类型是解决 Element Plus 类型推断的正确方式

**教训:**
- Element Plus 的 el-tag `:type` 属性在 TypeScript 中有严格的类型约束
- 使用 `Record<string, string>` 返回的类型不满足 el-tag 的 EpPropMergeType
- 定义 `type TagType = 'success' | 'info' | 'warning' | 'danger' | 'primary'` 并用于函数返回类型，完美解决
- 项目中多个现有文件（CoolingLinkageMonitor、PrecoolScheduleView 等）有同样的 TS 错误，VppMonitorView 是首个零 TS 错误的页面

**应用:**
- 后续前端页面中涉及 el-tag `:type` 绑定时，使用 TagType 联合类型
- 考虑将 TagType 提取为共享类型定义

### 4. 对抗性审查 P0 发现率模式延续

**教训:**
- Epic 33 的审查发现模式与 Epic 32 一致：
  - 33.2（新概念：API Key 认证 + 速率限制）: 5P0 + 3P1
  - 33.3（复用成熟模式）: 4P0 + 2P1（主要是跨文件数据一致性问题）
- P0 问题类型分布：
  - API 不存在/不匹配: 2 个（Redis increment、executor 名称）
  - 数据类型不匹配: 1 个（Time vs DateTime）
  - 缺失 import/导入: 2 个（Header、get_settings）
  - 跨 Story 数据遗漏: 2 个（_build_response 缺 created_at、func 未导入）
  - 路由/meta 模式不一致: 2 个（roles vs icon、el-button vs el-page-header）

**应用:**
- 审查应重点关注：(1) 框架 API 是否存在 (2) 数据类型是否匹配 (3) import 是否完整 (4) 跨 Story 接口兼容性
