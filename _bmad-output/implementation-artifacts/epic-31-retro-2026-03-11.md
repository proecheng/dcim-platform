## ✅ 做得好的地方

### 1. 核心算法设计扎实可靠

**成就:**
- 贪心调度算法采用 O(N) 时间复杂度（N=288 步），谷时预冷/峰时释放/平时维持的三阶段策略
- RC 热力学方程集成 COP 修正和 bypass 制冷量修正，物理模型准确
- 约束验证逐步检查轨迹，3 次重试自动放宽策略（递增目标温度 0.5°C/次）保证鲁棒性
- 电价时段优先从 ElectricityPricing 表读取，硬编码仅作 fallback

**影响:**
- 算法产出的预冷计划天然满足 ASHRAE 约束，与 Epic 30 约束引擎无缝衔接
- 重试放宽策略避免了约束过紧导致无法生成计划的窘境

### 2. 执行引擎的安全架构出色

**成就:**
- scan(1min)/tick(5min) 双定时器架构：scan 检测状态转换，tick 执行功率调整
- APScheduler max_instances=1 确保单例执行，避免并发冲突
- 功率调整遵守 step_limit(20kW) 和 ratio_limit(0.25) 双重限幅
- 安全中止集成 rollback_manager 状态检查 + 温度偏差 > 3°C 判断
- 功率恢复公式 `(Q_IT + (T_amb - T) / R) / COP` 正确转换为电功率

**影响:**
- 执行引擎完全委托 Epic 30 的安全机制，避免了重复实现安全检查
- 双重限幅避免了功率突变导致的机房温度剧烈波动

### 3. 对抗性审查持续发现关键问题

**成就:**
- Story 31.3 审查发现 3 个 P0 级问题：
  - abort 端点调用私有方法 → 新增 `abort_plan_by_api()` 公共方法
  - `generate_precool_plan` 错误是异常而非返回值 → 改用 try/except
  - IntegrityError 需要 `await session.rollback()` 再返回 409
- Story 31.5 审查发现 3 个 P0 级问题：
  - ECharts 缺少 CustomChart/MarkAreaComponent/MarkPointComponent 注册（运行时崩溃）
  - API 时间格式未明确（前端解析可能出错）
  - 电价时段数据来源不明
- 两轮审查模式（R1 找问题 + 修复 → R2 再检查）已成为稳定流程

**影响:**
- 每轮审查发现的 P0 问题如果流入实施阶段，会导致运行时崩溃或数据错误
- 审查投入的时间远低于后期 debug 的时间

### 4. API 设计模式统一且清晰

**成就:**
- 统一响应格式 `{code, message, data}` + HTTP 状态码
- ScheduleListItem（不含 trajectory）vs ScheduleDetailOut（含 trajectory）分离，减少传输量
- API 层控制事务（不调用 save_plan 避免双重 commit）
- 权限分层：viewer 禁止 / operator 只读 / admin 读写
- 审计日志模式（OperationLog with old_value/new_value JSON）

**影响:**
- 6 个端点的设计完全一致，前端集成无需猜测格式
- 事务控制在 API 层统一管理，避免了 service 层的 commit 副作用

## 🎯 经验教训

### 1. API 层事务控制优于 Service 层

**教训:**
- Story 31.3 发现 `save_plan` 内部 commit 会导致 API 层无法处理 IntegrityError
- 改为 API 层 `session.add()` + `session.commit()` + `try/except IntegrityError` → `rollback()` + 409
- Service 层方法应该只修改对象状态，不执行 commit

**应用:**
- 后续 API 开发统一遵循"API 层控制事务"模式
- Service 层返回对象或抛出异常，不调用 commit/rollback

### 2. 公共方法封装是跨层调用的关键

**教训:**
- Story 31.3 发现 API 端点调用 executor 的私有方法 `_abort_plan` 需要传入内部状态参数
- 解决方案：新增 `abort_plan_by_api()` 公共方法封装内部状态获取
- 这是依赖反转原则的实际应用

**应用:**
- Service 类需要考虑外部调用者的需求，提供合适粒度的公共 API
- 内部状态不应泄漏到外部调用者

### 3. ECharts 按需注册是隐性依赖

**教训:**
- Story 31.5 发现 echarts.ts 的按需注册机制是一个"隐性依赖"
- TypeScript 编译通过 ≠ 运行时正常
- 新图表类型（CustomChart）、新组件（MarkAreaComponent）需要显式注册

**应用:**
- 使用 ECharts 新功能时，第一步检查 echarts.ts 是否已注册
- 对抗性审查清单中增加"ECharts 组件注册检查"项

### 4. 前端路由和组件路径一致性

**教训:**
- Story 31.5 R2 审查发现组件路径不一致（`views/energy/` vs `views/energy/shift/`）
- 现有 shift 子页面都在 `views/energy/shift/` 目录，新页面应保持一致
- 路由定义中的 component 路径必须与实际文件路径匹配

**应用:**
- 新建前端文件前先确认目录约定
- 路由注册时检查现有同级路由的组件路径模式

### 5. 列表 vs 详情的数据分离模式

**教训:**
- Story 31.3 发现列表 API 返回完整 trajectory 数据（JSON 大对象）浪费带宽
- 分离为 ScheduleListItem（无 trajectory）和 ScheduleDetailOut（含 trajectory）
- 列表用于概览，详情用于深入查看

**应用:**
- 后续 API 设计中，列表端点排除大字段（JSON/BLOB），详情端点包含完整数据
- Pydantic Schema 分离为 List/Detail 两层
