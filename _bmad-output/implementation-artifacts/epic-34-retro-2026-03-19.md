## ✅ 做得好的地方

### 1. 管道式 Story 拆分清晰，依赖链路无阻塞

**成就:**
- 34.1(数据模型) → 34.2(适配器) → 34.3(策略) → 34.4(分发器集成) → 34.5/34.6/34.7(并行)
- 每个 Story 产出被后续 Story 直接消费，34.4 是关键汇聚点
- 34.5/34.6/34.7 三个 Story 无相互依赖，可并行开发
- 前端统一到 34.7，避免了 34.1-34.6 各自做前端片段的碎片化

**影响:**
- 后端先行、前端收尾的模式确保 API 设计稳定后再做 UI
- 7 个 Story 间零集成问题

### 2. Redis 降级策略全链路一致

**成就:**
- 34.6 StormDetector: Redis 不可用 → 内存滑动窗口降级（asyncio.Lock 保护）
- incr_with_ttl/incrby_with_ttl: Redis 异常返回 -1，调用方检测后降级
- 风暴检测固定窗口(Redis) vs 滑动窗口(内存) 行为差异在 Dev Notes 中明确说明

**影响:**
- 单 Redis 故障不会导致通知功能中断
- 降级行为可预测，运维人员可根据日志判断系统状态

### 3. 对抗性审查持续发现高价值问题

**成就:**
- 34.6 R1 审查发现批量计数语义、site_id=None 处理、内存泄漏清理等关键问题
- 34.7 R1 审查发现 12 个问题（3 HIGH: excludedPaths 缺失、outerjoin 设计、response schema 缺失）
- 代码审查发现 `if sid:` 对 site_id=0 的处理缺陷（改为 `if sid is not None:`）
- lazy import mock 路径问题在测试阶段发现并修复

**影响:**
- 所有 P0 问题在实施前解决，避免了运行时错误
- Mock patch 路径修复（从 dispatcher 模块 patch 改为源模块 patch）形成了可复用的测试模式

### 4. 时段冲突检测设计精确

**成就:**
- 34.3 将时段转换为分钟区间进行冲突检测
- 跨午夜时段（如 22:00-06:00）正确拆分为两个子区间
- 同级别策略时段冲突检测避免了运行时策略匹配歧义

**影响:**
- 策略匹配在任何时间点都有确定性结果
- 跨午夜值班场景（夜班运维）得到正确支持

### 5. 风暴抑制设计实用

**成就:**
- 批量计数（check_storm(site_id, count=N)）避免单批次内人为膨胀
- critical 不豁免，统一合并（级联故障场景下 critical 可能同时数十条）
- 摘要通知突出 critical 数量和关键设备列表
- 站点级独立计数，site_id=None 跳过风暴检测

**影响:**
- 真实级联故障场景下，运维人员收到一条结构化摘要而非数十条轰炸
- 风暴结束后自动恢复逐条通知（Redis TTL 过期 / 内存滑动窗口清理）

## 🔧 需要改进的地方

### 1. SMS/Voice 适配器仍为桩实现

**问题:**
- 34.2 实现了 Email/IM 适配器，SMS 和 Voice 为桩（直接返回成功）
- 生产环境需要接入真实的短信网关（如阿里云短信）和语音通知服务
- 当前测试覆盖的是桩行为，非真实发送

**影响:**
- 短信和语音渠道在生产环境无法实际发送通知
- 需要额外集成工作才能上线这两个渠道

**改进建议:**
- 后续接入真实短信网关时，只需替换 SmsAdapter.send() 实现
- 适配器框架设计已支持即插即用，修改量可控

### 2. 前端 API 响应层级处理仍用 `as any`

**问题:**
- notification.vue 中多处使用 `(res as any).data || res || []` 模式
- 这是项目级别的历史遗留问题（request.ts 拦截器行为不统一）
- Epic 32/33 回顾已多次提到但未修复

**影响:**
- TypeScript 类型安全在 API 调用层被绕过
- 新开发者不确定 API 返回的是 `{ data: [...] }` 还是直接是 `[...]`

**改进建议:**
- 统一 request.ts 响应拦截器，确保所有 API 返回一致的数据结构
- 这是跨 Epic 的架构改进，应作为独立 Story 处理

### 3. 通知记录缺少用户名显示

**问题:**
- GET /records 返回 user_id 但未 JOIN users 表获取用户名
- 前端 notification.vue 记录表格显示的是 user_id（数字），而非用户名
- 运维人员难以直观判断通知发给了谁

**改进建议:**
- 在 records API 中增加 outerjoin User 表获取 username/real_name
- 或前端单独缓存用户列表做本地映射

## 🎯 经验教训

### 1. Lazy import 的 mock patch 路径必须 patch 源模块

**教训:**
- 34.6 测试中 6 个测试失败，原因是 `storm_detector` 在 dispatcher.py 中使用 lazy import（方法内 `from ... import storm_detector`）
- 必须 patch `app.services.notification.storm.storm_detector`（源模块），而非 `app.services.notification.dispatcher.storm_detector`（使用处）
- 同理 `async_session` 应 patch `app.core.database.async_session`

**应用:**
- 后续测试中遇到 lazy import，统一 patch 源模块路径
- 已在 34.6 测试代码中建立了正确的 mock 模式

### 2. outerjoin 查询需要手动构造返回对象

**教训:**
- 34.7 records API 使用 `select(NotificationRecord, Alarm.alarm_level)` + outerjoin
- SQLAlchemy 返回的是 `(record_obj, alarm_level_str)` 元组，不是 ORM 对象
- 必须手动遍历 rows 构造 NotificationRecordInfo schema 对象
- `from_attributes = True` 在此场景下无用（不是从单个 ORM 对象构造）

**应用:**
- 涉及 JOIN 查询的 API，在 Story 规范中明确返回值类型和构造方式
- 对抗性审查应检查 Schema 的 Config 设置是否与实际构造方式匹配

### 3. 前端权限控制 v-if + 后端 require_role 双重保护

**教训:**
- 34.7 前端使用 `v-if="isAdmin"` 控制 Tab 可见性
- 后端 API 同时使用 `require_admin`（策略/渠道）和 `require_viewer`（记录）
- 非 admin 用户 activeTab 默认设为 "records"（因为 policies Tab 不可见）

**应用:**
- 前端权限仅做 UI 隐藏，真正的安全保障在后端
- Tab 默认值需要根据用户角色动态设置

### 4. 编辑对话框扩展时需要条件渲染

**教训:**
- 34.7 在 user.vue 编辑对话框中新增联系方式 Tab
- 新增用户时（isEdit=false）不能显示联系方式 Tab（用户尚未创建，无 userId）
- 解决方案：编辑模式用 el-tabs 包裹，新建模式直接显示表单
- 对话框宽度根据模式动态调整（`:width="isEdit ? '680px' : '520px'"`)

**应用:**
- 扩展现有对话框时，明确哪些功能仅在特定模式下可用
- 动态宽度避免新建模式下过宽的空间浪费
