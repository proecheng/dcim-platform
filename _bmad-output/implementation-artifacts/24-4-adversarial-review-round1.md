## 审查发现

### 高严重程度问题（Critical）

1. **验收标准 #3 步骤3逻辑错误**: 第50行说"验证签名（使用当前密钥或 PREVIOUS 验证已有签名）"，但这个逻辑有问题。如果版本是第一次激活（hmac_signature 为 NULL），不需要验证签名，直接生成即可。如果版本已经有签名（重新激活），才需要验证。当前描述混淆了"生成新签名"和"验证已有签名"两个场景。

2. **技术实现 #3 activate_version 逻辑冲突**: 第236行生成签名，第238-241行验证签名。但如果版本是第一次激活，hmac_signature 为 NULL，不应该进入验证分支。如果版本已经有签名，应该先验证再决定是否重新签名。当前代码逻辑是"先生成新签名，再验证旧签名"，这没有意义。

4. **技术实现 #3 create_version 缺少设备映射**: 第192-197行构建快照时，只包含了 tree、nodes、edges，但验收标准 #1 第32行明确说"snapshot 包含完整的故障树结构（节点列表、边列表、设备映射）"。缺少 device_mappings 会导致快照不完整。

5. **技术实现 #3 create_version 缺少事务保护**: 第200-208行查询最大版本号，第211-219行创建新版本。如果两个管理员同时创建版本，可能导致版本号冲突（违反 UNIQUE 约束）。应该使用数据库锁（SELECT FOR UPDATE）或捕获唯一性冲突异常并重试。

6. **技术实现 #3 activate_version 缺少事务保护**: 第243-249行归档旧版本，第251-255行激活新版本。如果在两步之间发生异常，可能导致多个 active 版本或没有 active 版本。应该在单个事务中完成，或者使用乐观锁。

7. **技术实现 #3 activate_version 缺少 DAG 验证**: 激活版本时应该验证 snapshot 中的故障树结构是否为有效的 DAG（调用 Story 24.3 的 DAGValidator）。如果快照被篡改或损坏，激活后会导致 L2 推理引擎崩溃。

14. **验收标准 #3 缺少并发控制**: 第47-53行描述激活流程，但没有说明如果两个管理员同时激活不同版本会发生什么。可能导致竞态条件：两个版本都通过验证，但最终只有一个 active（后提交的覆盖前提交的），另一个版本状态不一致。

### 中严重程度问题（Major）

3. **技术实现 #3 缺少 func 导入**: 第254行使用 `func.now()`，但代码开头（第160-168行）没有导入 `func`。应该添加 `from sqlalchemy import func`。

8. **技术实现 #2 verify_signature 缺少输入验证**: 第138行 `verify_signature` 方法没有验证 `signature` 参数是否为有效的十六进制字符串（64 字符）。如果传入非法签名（如空字符串、超长字符串），`hmac.compare_digest` 可能抛出异常或返回错误结果。

10. **技术实现 #5 API 路由缺少 Pydantic Schema**: 第298-335行的 API 路由没有定义请求和响应的 Pydantic Schema。FastAPI 无法自动生成 Swagger 文档，也无法进行请求参数验证。

11. **技术实现 #5 review_version 未实现**: 第314-318行 `review_version` 函数只有注释，没有实现。

12. **技术实现 #5 rollback_version 未实现**: 第326-329行 `rollback_version` 函数只有注释，没有实现。

13. **技术实现 #5 list_versions 未实现**: 第331-334行 `list_versions` 函数只有注释，没有实现。

15. **验收标准 #5 回滚逻辑不明确**: 第69-73行说"找到最近一个 archived 版本"，但如果该版本的签名已经过期（使用了已删除的旧密钥），验证会失败，回滚会失败。应该明确：回滚时如果签名验证失败，是拒绝回滚还是重新签名？

18. **技术实现 #3 snapshot 序列化不完整**: 第192-197行构建快照时，节点字段使用了 `...` 省略。实际实现时必须包含所有字段。

### 低严重程度问题（Minor）

9. **技术实现 #4 validator 装饰器错误**: 第279行使用 `@validator`，但 Pydantic v2 已弃用，应该使用 `@field_validator`。

16. **技术实现 #1 表结构缺少索引**: 缺少 `(tree_id, status)` 复合索引。

17. **技术实现 #1 表结构缺少约束**: 没有添加 CHECK 约束确保 status 只能是 draft/reviewed/active/archived。

19. **备注 #2 密钥轮换步骤不完整**: 第430行说"等待所有版本重新签名"，但没有说明如何触发重新签名。

20. **测试策略 #2 缺少快照完整性测试**: 没有测试"快照是否包含完整的故障树结构"。
