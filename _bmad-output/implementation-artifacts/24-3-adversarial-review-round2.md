# Story 24.3 第二轮对抗性审查报告

**审查日期**: 2026-03-06
**审查对象**: Story 24.3 实施文档（第一轮修复后）
**审查类型**: 对抗性文档审查

## 审查发现

### 高严重程度问题（Critical）

1. **验收标准 #4 叶节点 evidence_point_id 约束不明确**: 第 72 行说"叶节点必须关联 evidence_point_id"，但表结构（第 138 行）中 `evidence_point_id` 字段没有 NOT NULL 约束，允许为 NULL。如果叶节点的 evidence_point_id 为 NULL，L2 推理引擎无法收集证据。应该明确：叶节点创建时必须提供 evidence_point_id，或者在 API 层验证。

2. **验收标准 #5 延迟验证策略不明确**: 第 84 行说"延迟 DAG 验证（不在每次操作时验证，而是在批量操作完成或故障树状态变更时验证）"，但没有说明如果管理员在 draft 状态下逐个创建节点和边，何时触发验证。如果从不触发验证，管理员可能创建出无效的故障树并将其激活（Story 24.4）。应该明确：(1) 批量创建时验证；(2) 状态从 draft 改为 active 时验证；(3) 提供手动验证 API `POST /api/v1/fault-trees/{id}/validate`。

3. **技术实现 #2 DAG 验证器缺少 gate_type 验证**: 验收标准 #4 第 71 行说"门类型（gate_type）限制为: AND, OR, NULL（叶节点和根节点为 NULL）"，但 DAG 验证器代码（第 173-293 行）没有验证 gate_type 的有效性。如果中间节点的 gate_type 是 "XOR" 或其他无效值，验证器不会报错，但 L2 推理引擎会崩溃（Story 24.5 只支持 AND/OR 门）。

4. **技术实现 #2 DAG 验证器缺少 evidence_point_id 验证**: 验收标准 #4 第 72 行说"叶节点必须关联 evidence_point_id"，但 DAG 验证器没有检查叶节点的 evidence_point_id 是否为 NULL。如果叶节点的 evidence_point_id 为 NULL，验证器不会报错，但 L2 推理引擎无法收集证据。

5. **测试策略 #1 单元测试用例 #13 说明不明确**: 第 446 行说"中间节点 gate_type 为 NULL 验证（应允许，由业务逻辑处理）"，但验收标准 #4 第 71 行明确说"叶节点和根节点为 NULL"，暗示中间节点的 gate_type 不应该为 NULL。如果允许中间节点 gate_type 为 NULL，L2 推理引擎在传播概率时会崩溃（不知道是 AND 门还是 OR 门）。应该明确：中间节点 gate_type 必须是 AND 或 OR，验证器应该拒绝 NULL。

### 中严重程度问题（Major）

6. **验收标准 #1 表结构描述不完整**: 第 25-28 行列出的表字段与技术实现 #1（第 117-169 行）不一致。验收标准中 `fault_trees` 表缺少 `updated_by` 字段，`fault_tree_nodes` 表的 `prior_probability` 未说明 NOT NULL 约束，`fault_tree_edges` 表缺少自环检查约束。验收标准应与实际表结构完全一致。

7. **技术实现 #1 表结构缺少索引**: 第 165-168 行只创建了 3 个索引，但缺少关键索引：(1) `fault_trees.status` 索引（列表查询按 status 过滤，验收标准 #3 第 53 行）；(2) `fault_tree_nodes.node_type` 索引（DAG 验证器需要按 node_type 分类节点，第 210-216 行）；(3) `fault_tree_edges.parent_node_id` 和 `child_node_id` 索引（查询节点的父节点和子节点时需要）。

8. **技术实现 #3 API 路由注释与验收标准不一致**: 第 340 行注释说"创建边（自动触发 DAG 验证）"，但验收标准 #5 第 84 行明确说"延迟 DAG 验证"。注释应该改为"创建边（延迟验证）"，避免误导实施者。

9. **技术实现 #4 ORM 模型 CheckConstraint 在 SQLite 中不生效**: 第 388 行和 405 行使用 `CheckConstraint`，但 SQLite 默认不启用 CHECK 约束（需要编译时开启 `SQLITE_ENABLE_CHECK_CONSTRAINTS`）。如果开发环境使用默认 SQLite，`prior_probability` 可以超出 [0.0, 1.0] 范围，`parent_node_id` 可以等于 `child_node_id`（自环）。应该在备注中说明 SQLite 的 CHECK 约束限制，并建议在 API 层额外验证。

10. **技术实现 #4 ORM 模型反向关系定义错误**: 第 392-393 行的反向关系定义有问题。`parent_edges` 和 `child_edges` 的 `foreign_keys` 参数应该是列表，但代码中使用了字符串（`"FaultTreeEdge.child_node_id"`）。正确的写法应该是 `foreign_keys=[child_node_id]`（已经在第 409-410 行修正，但第 392-393 行仍然是字符串）。

11. **测试策略 #2 API 集成测试缺少 DAG 验证触发时机测试**: 第 448-465 行的测试用例没有测试"何时触发 DAG 验证"。根据验收标准 #5 第 84 行，验证应该在"批量操作完成或故障树状态变更时"触发，但没有测试用例验证这个行为。应该添加：(1) `test_validate_on_batch_create`；(2) `test_validate_on_status_change`；(3) `test_no_validate_on_single_edge_create`。

12. **依赖关系缺少 points 表依赖**: 第 482-490 行列出了前置依赖，但没有提到 `points` 表。`fault_tree_nodes.evidence_point_id` 外键引用 `points` 表（第 138 行和 383 行），如果 `points` 表不存在，迁移脚本会失败。应该明确：需要 Epic 1-3 的点位管理功能（`points` 表已存在）。

13. **备注 #5 级联删除策略不完整**: 第 543 行说"删除节点时自动级联删除相关的边"，但没有说明如果删除的是根节点或中间节点，会导致整个故障树结构损坏（其他节点变成不可达）。应该明确：(1) 删除根节点时拒绝删除（或级联删除整个故障树）；(2) 删除中间节点时检查是否会导致子节点不可达，如果会则拒绝删除。

14. **备注 #6 延迟验证策略与验收标准不一致**: 第 546 行说"边的创建和更新操作不立即触发 DAG 验证"，但没有说明何时触发。验收标准 #5 第 84 行说"批量操作完成或故障树状态变更时验证"，但备注中没有提到状态变更。应该在备注中明确验证触发时机，与验收标准保持一致。

### 低严重程度问题（Minor）

15. **测试策略 #3 性能测试环境描述不完整**: 第 469-471 行描述了测试环境，但没有说明网络延迟。如果生产环境的 PostgreSQL 部署在远程服务器（如 AWS RDS），网络延迟可能达到 10-50ms，会显著影响性能目标（1000 节点加载 < 1 秒）。应该明确测试环境是本地部署还是远程部署。

16. **验收检查清单缺少 Pydantic Schema 验证**: 第 494-508 行的检查清单第 506 行说"API 文档（Swagger）更新，包含 Pydantic Schema 定义"，但没有具体的检查项。应该明确需要定义哪些 Schema（如 `FaultTreeCreate`, `FaultTreeUpdate`, `FaultTreeResponse`, `NodeCreate`, `EdgeCreate`, `DeviceMappingCreate` 等），以及每个 Schema 包含哪些字段。

17. **工作量估算缺少 Pydantic Schema 定义时间**: 第 512-522 行的工作量估算没有包含 Pydantic Schema 定义的时间。根据备注 #7（第 547 行），需要定义多个 Schema，预计需要 1-1.5 小时。总工作量应该调整为 13.5-14 小时（约 1.75 个工作日）。

18. **备注 #7 Pydantic Schema 说明过于简略**: 第 547 行只列举了几个 Schema 名称，但没有说明每个 Schema 的字段和验证规则。例如：`FaultTreeCreate` 应该包含 name（必填，最长 200 字符）、description（可选）、status（可选，默认 draft）；`NodeCreate` 应该包含 node_type（必填，枚举值）、gate_type（可选，枚举值）、prior_probability（必填，范围 [0.0, 1.0]）等。缺少这些细节会导致实施时遗漏验证规则。

19. **验收标准 #3 列表查询缺少排序说明**: 第 53 行说"列表查询（支持分页、按 status 过滤）"，但没有说明默认排序方式。如果不指定排序，查询结果的顺序是不确定的（取决于数据库实现）。应该明确：默认按 `created_at DESC` 排序（最新创建的在前），或按 `name ASC` 排序（字母顺序）。

20. **验收标准 #3 获取详情缺少性能优化说明**: 第 54 行说"获取故障树详情（含节点和边）"，但没有说明如何优化查询性能。如果使用 ORM 的懒加载（lazy loading），查询 1000 个节点会触发 1000 次数据库查询（N+1 问题）。应该明确：使用 `joinedload` 或 `selectinload` 预加载节点和边，避免 N+1 问题。
