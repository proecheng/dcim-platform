# Product Requirements Document - DCIM 算力中心智能监控系统

**Author:** proecheng
**Date:** 2026-02-15

## 执行摘要

DCIM 算力中心智能监控系统是一个 IoT Platform + Web App 混合型产品，面向数据中心运维团队，实现动力环境设备的实时监控、智能告警、能源管理和运维自动化。

**为什么现在做：** 当前数据中心运维依赖人工巡检和分散的子系统独立监控，缺乏统一视图和智能分析能力，导致告警响应慢、能耗浪费、故障定位难。本系统将六大子系统数据汇聚到统一平台，从"被动巡检"转向"主动监控+智能诊断"。

**核心差异化：** 机房物理拓扑模型（配电+空间+制冷三合一）+ 多维度智能机柜选址（空间/电力/三相平衡/温度综合评分），这是目前市场上共济、盈泽、JITON 等竞品均未实现的能力。

**目标用户：** 运维工程师、能源管理员、资产管理员、运维主管、系统管理员、集成工程师（共 7 类角色）。

**技术栈：** Vue 3 + TypeScript + FastAPI + PostgreSQL + MQTT，通过采集网关对接 6 种工业协议（Modbus/SNMP/BACnet/OPC-UA/MQTT/HTTP）。

**团队：** 2 人全栈开发。**MVP 周期：** 3 个月（120 人天）。**12 个月目标：** 200 台真实设备、电费节省 ≥ 5%。

## 产品愿景与功能分层

### MVP — 最小可用产品

核心功能（必须可用）：
- **协议采集** — Modbus TCP/RTU + SNMP v2c，覆盖空调、UPS、PDU、环境传感器
- **实时监控** — 六大子系统数据采集与展示，WebSocket 实时推送
- **告警管理** — 4 级告警、阈值配置、实时通知、确认/解除、统计
- **能源管理** — PUE 监控、配电拓扑、能耗统计、五时段电价管理（尖峰/高峰/平段/低谷/深谷）
- **采集网关** — 网关注册、状态监控、远程配置、离线缓存+断点续传
- **用户认证** — JWT + RBAC 三级权限

> 详细的 MVP 功能集、产能估算和分阶段开发计划见"项目范围与分阶段开发"章节。

### 增长功能（Post-MVP）

- **视频联动** — 告警/事件触发自动调取摄像头画面、区域联动录像、云台控制、告警回放
- **故障智能诊断** — 基于规则和历史数据的故障根因分析，覆盖 Top 20 高频故障
- **节能优化插件** — 6 种分析插件（峰谷套利、需量优化、PUE 优化、功率因数、负荷转移、设备效率）
- **机房物理拓扑** — 配电+空间+制冷三合一拓扑模型 + 多维度智能选址
- **资产管理** — 设备台账、机柜 U 位管理、生命周期、维保
- **运维管理** — 工单、巡检、知识库
- **报表统计** — 日/周/月报表、PDF 导出
- **容量管理** — 空间/电力/制冷/承重容量监控与规划
- **更多协议** — BACnet/IP、OPC-UA、MQTT、HTTP REST

### 愿景（未来）

- **数字孪生大屏** — Babylon.js 3D 可视化，设备级交互
- **AI 预测性维护** — 基于 ML 的设备故障预测
- **VPP 虚拟电厂** — 可调负荷调度、电网互动
- **多租户 SaaS** — 支持多数据中心、多客户
- **移动端 App** — 移动巡检、告警推送
- **AI 视频分析** — 人员入侵检测、烟火识别、异常行为检测（接口预留，后期开发）

## 用户旅程

### 旅程 1：运维工程师 — 告警响应（核心成功路径）

**人物：** 张磊，28 岁，某数据中心值班运维工程师，负责夜班值守。

**开场：** 凌晨 2:15，张磊在监控室值班，大屏上显示着机房各区域的实时状态。突然，系统发出紧急告警声 — B3 机柜温度飙升至 38°C，超过紧急阈值。

**上升：** 张磊点击告警通知，系统自动跳转到 B3 机柜的详情页面，同时**自动调取 B3 机柜附近的摄像头实时画面**（分屏显示在详情页右侧），张磊远程确认机柜前门已关闭、无人为异常。温度曲线显示过去 10 分钟内从 26°C 急速上升。系统的**智能诊断模块**同时给出三个可能原因：①空调 AC-07 故障停机 ②机柜前门未关闭 ③服务器负载突增。张磊查看关联设备状态，发现 AC-07 显示"压缩机故障"。

**高潮：** 张磊确认告警，系统自动创建工单并派发给空调维修组。他同时通过系统远程启动备用空调 AC-08 的制冷模式，温度开始缓慢下降。

**结局：** 从告警触发到启动应急措施，全程 6 分钟。张磊在系统中记录处理过程，工单自动流转。第二天运维主管在报表中看到这次事件的完整处理链路。

### 旅程 2：运维工程师 — 边缘场景（通信中断 + 软故障）

**人物：** 张磊，同上。

**场景 A — 硬断线：**

**开场：** 上午 10:00，张磊发现仪表盘上 A 区 12 台设备同时显示"离线"状态，但没有触发告警。

**上升：** 张磊怀疑是采集网关故障而非设备故障。他进入数据源管理页面，发现 A 区的 Modbus 网关连接状态显示"断开"，最后通信时间是 9:47。系统显示"通信中断 13 分钟，影响 12 台设备、48 个点位"。系统**自动调取 A 区摄像头画面**，张磊远程查看网关设备指示灯状态和机房现场情况。

**高潮：** 张磊尝试通过系统重新连接网关，失败。他创建工单标记为"网络故障"，系统自动将 A 区所有点位标记为"数据质量：不可靠"，避免基于过期数据产生误告警。

**结局：** 网络恢复后，系统自动重连并恢复数据采集，补采中断期间的数据（如果设备支持历史回读）。张磊在系统中确认恢复正常。

**场景 B — 传感器漂移：**

**开场：** 下午 3:00，张磊注意到 C 区 5 号机柜的温度传感器读数 18°C，比周围机柜低了 7°C，但没有触发告警（在正常范围内）。

**上升：** 系统的**数据质量检测模块**已经标记该点位为"疑似漂移" — 它检测到该传感器的读数在过去 48 小时内逐渐偏离同区域其他传感器的均值，偏差超过 3σ。系统在仪表盘上用黄色标记提示"数据可信度：低"。

**高潮：** 张磊点击诊断建议，系统显示："该传感器读数与相邻传感器偏差持续扩大，建议现场校验或更换。"他创建维保工单，标记为"传感器校准"。

**结局：** 现场检查确认传感器老化漂移，更换后数据恢复正常。系统自动解除"疑似漂移"标记。

### 旅程 3：能源管理员 — 电费优化

**人物：** 李芳，35 岁，数据中心能源管理员，每月需要向管理层汇报能耗和电费情况。

**开场：** 月初，李芳打开能源管理模块，查看上月电费账单分析。系统显示上月总电费 82 万元，PUE 1.58。节能优化模块自动识别出 3 个节能机会。

**上升：** 李芳点击"峰谷套利"机会，系统显示：当前 UPS 电池组在高峰时段放电可节省约 2.3 万元/月，并给出详细的 96 时段调度方案。她又查看"需量优化"建议 — 通过错峰启动空调，可将最大需量从 1200kW 降至 1050kW，节省基本电费约 1.5 万元/月。

**高潮：** 李芳选择"峰谷套利"方案，设置执行计划。系统自动生成调度时间表，并在执行后实时追踪效果。一个月后，电表读数确认节省了 2.1 万元。

**结局：** 李芳导出月度能效报告（含 PUE 趋势、电费对比、节能成果），向管理层汇报。电费同比下降 5.2%，管理层非常满意。

### 旅程 4：资产管理员 — 设备上架

**人物：** 王刚，40 岁，数据中心资产管理员，负责新一批服务器的上架入库。

**开场：** 王刚收到 20 台新服务器的到货通知，需要完成资产登记、机柜分配、上架记录。

**上升：** 他打开资产管理模块，批量录入设备信息（SN 码、型号、厂商、保修期）。然后进入容量管理，系统显示各机柜的 U 位占用情况、剩余电力容量和制冷余量。系统推荐 C 区 3 个机柜有足够空间和电力余量。

**高潮：** 王刚将 20 台服务器分配到推荐机柜，系统自动更新 U 位占用图、电力负载率、制冷需求。资产生命周期自动记录"上架"事件。**系统自动开始录像**，记录上架操作过程，作为资产变更的可追溯凭证。

**结局：** 上架完成后，系统自动将新设备纳入监控范围，运维工程师在仪表盘上看到新增设备的实时状态。王刚设置了保修到期提醒（18 个月后）。

### 旅程 5：运维主管 — 决策支持

**人物：** 陈总，45 岁，数据中心运维主管，每周需要了解整体运行状况并做决策。

**开场：** 周一早上，陈总打开系统，首先看到的是**智能摘要面板**："本周有 2 件事需要您决策：① B 区 UPS 电池组 SOH 降至 72%，建议 30 天内更换（预算约 8 万元）② C 区制冷容量利用率达 85%，若下月新增服务器需提前扩容。"

**上升：** 陈总点击第一条，系统展示电池组健康度趋势、历史放电记录、更换成本估算。他直接审批采购工单。点击第二条，系统显示容量趋势预测图和扩容方案对比。

**高潮：** 陈总导出周报，包含告警趋势、能耗对比、工单统计、容量使用率。报告自动生成同比/环比分析图表。

**结局：** 陈总在管理会议上用系统生成的报告汇报，数据清晰、图表直观，决策有据可依。

### 旅程 6：系统管理员 — 系统配置

**人物：** 赵明，30 岁，IT 系统管理员，负责 DCIM 系统的日常维护和用户权限管理。

**开场：** 新入职了 3 名运维工程师，赵明需要为他们创建账号并分配权限。同时，A 区新增了一批温湿度传感器，需要配置告警阈值。

**上升：** 赵明在用户管理页面批量创建账号，分配"operator"角色（可查看监控、处理告警，但不能修改系统配置）。然后进入告警阈值配置，为新传感器设置温度上限 35°C（主要告警）和 38°C（紧急告警）。

**高潮：** 配置完成后，赵明检查系统日志确认操作记录完整。他还检查了数据库备份状态 — 上次自动备份是昨晚 3:00，一切正常。

**结局：** 新员工第二天登录系统，权限正确，能看到自己负责区域的监控数据。新传感器的告警规则也已生效。

### 旅程 7：集成工程师 — 协议对接

**人物：** 刘洋，32 岁，系统集成工程师，负责将 DCIM 系统与现场设备对接。

**开场：** 刘洋到达客户机房，需要将 30 台精密空调（Modbus RTU）、10 台 UPS（SNMP v2c）和门禁系统（通过 Modbus I/O 采集模块转换干接点信号）接入 DCIM 系统。

**上升：** 他在数据源管理页面新建 Modbus 数据源，填写串口参数（波特率 9600、数据位 8、校验位 None）。然后使用"测试连接"功能验证通信正常。接着批量导入点位配置表（Excel），系统自动执行**导入预校验**：检查寄存器地址是否冲突、数据类型是否匹配、量程范围是否合理。校验报告显示 2 个点位的寄存器地址超出设备有效范围，刘洋修正后重新导入。系统默认以**只读模式**首次对接 — 仅采集数据，不下发任何控制命令。**系统自动开始录像**，记录现场调试过程。

**高潮：** 30 台空调全部接入后，刘洋在实时监控页面看到数据开始刷新。他发现 3 台空调的温度值异常（显示 0°C），排查发现是寄存器地址偏移了 1 位。他在点位配置中修正地址，数据立即恢复正常。确认数据正常后，再逐台设备开启写入权限。

**结局：** 全部设备对接完成，刘洋导出对接报告（含设备清单、点位映射、通信参数），交付给客户运维团队。系统开始正常采集数据。

### 旅程 8：消防联动 — 自动应急响应

**人物：** 系统自动执行（无人值守场景），张磊事后复盘。

**开场：** 凌晨 4:30，A 区烟雾传感器检测到烟雾浓度超标，同时极早期火灾探测器（VESDA）确认预警。消防主机通过干接点向 DCIM 系统发送火警信号。

**上升：** 系统在 3 秒内自动触发预设联动策略：
1. **制冷系统** — 关闭 A 区所有精密空调（防止烟雾扩散）
2. **通风系统** — 启动排烟风机
3. **配电系统** — 切断 A 区非关键负载电源（保留 UPS 供电的关键设备）
4. **安防系统** — 解锁 A 区所有门禁（疏散通道）
5. **照明系统** — 开启应急照明
6. **视频系统** — **自动调取 A 区全部摄像头画面（多屏显示）并开始录像**
7. **通知系统** — 向所有值班人员发送紧急告警（短信 + 系统推送 + 声光报警）

**高潮：** 张磊收到告警后 2 分钟赶到监控室，系统大屏显示 A 区联动执行状态：6 项联动全部执行成功，实时视频画面显示 A 区无明火。消防人员到场确认是空调电路短路产生的烟雾，非真实火灾。

**结局：** 张磊在系统中执行"联动恢复"流程 — 逐项恢复空调、电源、门禁到正常状态。系统自动生成完整的事件时间线报告（从检测到恢复），包含每个联动动作的执行时间、结果和**关键时刻的视频截图**，用于事后复盘和合规存档。

## 创新与差异化

### 核心创新：机房物理拓扑模型 + 多维度智能选址

#### 机房物理拓扑模型（基础能力）

传统 DCIM 仅维护配电拓扑（变压器→配电柜→回路→设备）。本系统创新性地构建**三合一物理拓扑模型**：

| 拓扑维度 | 内容 | 数据来源 |
|---------|------|---------|
| **配电拓扑** | 变压器→配电柜→PDU→机柜→设备，含三相接线关系 | 集成工程师配置 + PDU 采集 |
| **空间拓扑** | 机柜行列位置、冷热通道归属、楼层/房间/区域层级 | 集成工程师配置（机柜平面图） |
| **制冷拓扑** | 空调覆盖范围、机柜与空调的服务关系、冷通道分组 | 集成工程师配置 + 温度传感器数据 |

**拓扑模型的应用场景：**

| 应用场景 | 说明 | 阶段 |
|---------|------|------|
| **智能机柜选址** | 综合空间/电力/三相平衡/温度推荐最优上架位置 | MVP |
| **故障影响分析** | 配电柜跳闸→立刻定位受影响的机柜和设备 | MVP |
| **制冷优化** | 按空调覆盖区域评估制冷负荷分布 | Post-MVP |
| **容量规划** | 按物理区域（而非全局）评估空间/电力/制冷容量 | Post-MVP |
| **数字孪生基础** | 为未来 3D 可视化提供设备位置和拓扑关系数据 | 愿景 |

#### 多维度智能机柜选址（第一应用场景）

| 维度 | 传统 DCIM | 本系统 |
|------|----------|--------|
| 空间容量 | ✅ U 位空间 | ✅ U 位空间 |
| 电力容量 | ✅ 总功率余量 | ✅ 总功率余量 + **三相负载平衡度** |
| 热环境 | ❌ 不考虑 | ✅ **实时温度场分布**（基于环境传感器数据） |
| 制冷余量 | ❌ 或简单计算 | ✅ 区域制冷能力与当前负荷对比 |
| 推荐展示 | 文字列表 | ✅ **机柜平面图颜色标注 + 多维度评分卡 + 候选位置对比** |

**创新价值：**
- **三相平衡优化** — 避免单相过载导致零线电流过大、变压器效率下降，直接降低电力损耗和安全风险
- **温度场感知** — 避免将高功耗设备放置在已偏热区域，减少局部过热风险和制冷能耗
- **综合最优解** — 不是单一维度的"够不够"判断，而是多维度加权的"哪里最好"推荐
- **可视化决策** — 机柜平面图上用颜色标注各维度评分（绿/黄/红），点击显示详细评分卡（空间/电力/三相平衡/温度各项评分），支持对比多个候选位置

**拓扑配置（集成工程师职责）：**

在协议对接阶段，集成工程师需同步完成：
- 机柜物理位置配置（行列号、冷热通道归属）
- PDU 三相接线关系配置（每个机柜接哪个 PDU 的哪一相）
- 空调覆盖范围配置（每台空调服务哪些机柜/冷通道）

### 辅助创新

| 创新点 | 说明 | 竞品对比 |
|--------|------|---------|
| 数据质量自动检测 | 传感器漂移识别、3σ 统计偏差、相邻交叉验证 | 竞品仅做简单阈值判断 |
| 分级消防联动 | 单传感器→预警，多传感器交叉确认→联动 | 竞品多为一刀切联动 |
| 可插拔节能分析 | 6 种插件架构，自动识别+效果追踪 | 竞品多为固定报表 |

### 市场背景与竞争格局

- 共济 DCIM、盈泽、JITON 等竞品的容量管理均为空间+电力的简单计算
- 目前市场上没有将三相平衡和温度场纳入机柜选址推荐的 DCIM 产品
- 机房物理拓扑模型为未来数字孪生打下数据基础，形成战略卡位
- 该创新直接关联客户的核心痛点：电费节省和设备安全

### 验证方法

| 验证项 | 方法 | 成功标准 |
|--------|------|---------|
| 三相平衡改善 | 对比使用推荐前后的三相不平衡度 | 不平衡度降低 ≥ 10% |
| 温度场优化 | 对比推荐上架 vs 随机上架后的区域最高温度 | 无新增热点 |
| 用户接受度 | 资产管理员是否采纳推荐结果 | 采纳率 ≥ 80% |
| 拓扑模型完整度 | 集成工程师能否在 1 天内完成单机房拓扑配置 | 配置时间 ≤ 8 小时 |

### 风险缓解

| 风险 | 缓解措施 |
|------|----------|
| 传感器数据不足导致推荐不准 | 推荐结果标注置信度（高/中/低），数据不足时降级为传统空间+电力推荐 |
| 用户不信任算法推荐 | 展示推荐理由（各维度评分卡），支持人工覆盖推荐结果 |
| 三相数据获取困难 | 部分老旧 PDU 不支持分相电流采集，系统兼容"无三相数据"场景，该维度评分标记为"不可用" |
| 拓扑配置成本高 | 提供批量导入（Excel）、可视化拖拽配置、常见机房布局模板 |

### IoT 采集层技术要求

#### 采集网关硬件规格

| 参数 | 要求 | 说明 |
|------|------|------|
| 硬件平台 | 工控机（x86） | 工业级可靠性，支持宽温运行 |

> **磁盘分区策略（MVP 阶段预留）：** 即使 OTA 功能在 Post-MVP 实现，网关部署时必须采用 A/B 双分区方案 — 系统分区 A（当前运行）+ 系统分区 B（升级备用）+ 数据分区（离线缓存）。确保未来 OTA 升级失败时可自动回退到原分区，避免网关变砖。

#### 网关部署策略

| 部署模式 | 网关数量 | 适用场景 | 串口需求 |
|---------|---------|---------|---------|
| 单房间单网关 | 每个机房房间 1 台 | 房间间物理隔离、设备协议差异大 | 4 串口通常够用 |
| 单楼层单网关 | 每个楼层 1 台 | 同楼层设备集中、协议统一 | 可能需要 8 串口或串口扩展卡 |
| 按协议分网关 | 按协议类型部署 | Modbus 网关 + SNMP 网关分离 | 按需配置 |

> **推荐方案：** 单房间单网关，每台网关负责一个物理房间的所有设备采集。优点：故障隔离（一台网关故障只影响一个房间）、布线简单（串口线缆长度有限，通常 ≤ 1200 米）。

#### 采集性能要求

| 指标 | 目标 | 说明 |
|------|------|------|
| 单网关采集点位数 | ≥ 2,000 个 | 覆盖一个中型机房 |
| 采集周期 | 可配置 1~60 秒，默认 5 秒 | 不同设备可设不同周期 |
| 协议并发 | 同时运行 ≥ 4 种协议 | Modbus + SNMP + BACnet + MQTT |
| 离线缓存 | ≥ 72 小时数据 | 服务器宕机时本地缓存 |
| 断点续传 | 服务器恢复后自动补传 | 保证数据完整性 |

| 功能 | 说明 | 阶段 |
|------|------|------|
| 网关注册 | 网关上线自动注册到平台，分配唯一 ID | MVP |
| 状态监控 | 网关在线/离线状态、CPU/内存/磁盘使用率 | MVP |
| 远程配置 | 通过平台下发采集配置（数据源、点位表） | MVP |
| OTA 固件升级 | 远程推送网关固件更新，基于 A/B 双分区，支持自动回滚 | Post-MVP |
| 升级策略 | 分批升级、灰度发布、升级失败自动回退到原分区 | Post-MVP |

### 实时通信架构

```
采集网关 ──MQTT──> MQTT Broker (EMQX/Mosquitto) ──订阅──> 后端服务
                                                            │
采集网关 <──MQTT── MQTT Broker <──发布── 后端服务（控制命令/配置下发）
                                                            │
采集网关 ──HTTP──> 后端服务（网关注册、OTA 升级包下载）         │
                                                            │
                                              后端服务 ──WebSocket──> 前端
                                                            
                                              前端 ──RTSP/ONVIF──> NVR（视频直连）
```

| 通信链路 | 协议 | 方向 | 用途 | 说明 |
|---------|------|------|------|------|
| 网关→Broker→后端 | MQTT | 上行（主通道） | 实时数据上报、告警事件 | 长连接，高频低延迟 |
| 后端→Broker→网关 | MQTT | 下行 | 控制命令、配置下发 | 通过 Broker 解耦 |
| 网关→后端 | HTTP | 上行（辅助通道） | 网关注册、OTA 升级包下载、大文件传输 | 短连接，低频 |
| 后端→前端 | WebSocket | 推送 | 实时数据、告警通知、系统状态 | 3 个通道：realtime/alarms/system |
| 前端→NVR | RTSP/ONVIF | 直连 | 视频流调取、云台控制 | 不经过后端，减轻服务器压力 |

### 部署架构

#### 单站点部署

| 部署模式 | 说明 | 适用场景 |
|---------|------|---------|
| 单机部署 | Docker Compose，全部服务在一台服务器 | 开发测试、小型机房（≤ 50 台设备） |
| 标准部署 | 应用服务器 + 数据库服务器 + MQTT Broker 分离 | 生产环境（50~200 台设备） |
| 高可用部署 | 双机热备 + 数据库主从 + 网关冗余 | 大型机房、高可靠性要求 |

#### 多站点集中管理（单租户多站点）

```
机房 A 网关群 ──MQTT──┐
                      ├──> 中心 MQTT Broker ──> 中心平台服务器 ──> 统一管理界面
机房 B 网关群 ──MQTT──┤                              │
                      │                         中心数据库
机房 C 网关群 ──MQTT──┘                        （所有站点数据汇聚）
```

| 特性 | 说明 |
|------|------|
| 统一视图 | 运维主管在一个界面查看所有机房状态、告警、能耗 |
| 站点隔离 | 每个机房的运维人员只能看到自己负责的机房数据 |
| 数据汇聚 | 所有站点数据汇聚到中心数据库，支持跨站点报表和对比分析 |
| 网络要求 | 各机房到中心平台需要稳定的网络连接（VPN / 专线） |
| 离线容错 | 网络中断时，各机房网关本地缓存，恢复后自动补传 |

> **注意：** 多站点集中管理不等于多租户。这是同一个客户的多个机房统一管理，不涉及租户隔离。多租户 SaaS 是愿景阶段的目标。

## 项目范围与分阶段开发

### MVP 策略与理念

**MVP 方式：** 平台型 MVP — 打通"真实设备→协议采集→数据展示→告警处理"的完整链路，证明系统能在真实环境中运行并产生价值。

**核心验证目标：** 能接真实设备、能看到真实数据、能处理真实告警。

**团队规模：** 2 人（全栈）

**MVP 时间线：** 3 个月（120 人天），保留 20 天缓冲应对协议兼容性问题。

### MVP 功能集（Phase 1 — 月 1~3）

**支撑的核心用户旅程：**
- 旅程 1（告警响应）— 简化版：告警推送+确认，无智能诊断
- 旅程 7（协议对接）— 核心版：Modbus + SNMP 优先
- 旅程 6（系统配置）— 基础版：用户管理 + 告警阈值配置

**必须具备的能力：**

| 模块 | MVP 范围 | 说明 |
|------|---------|------|
| **协议采集** | Modbus TCP/RTU + SNMP v2c | 覆盖空调、UPS、PDU、环境传感器（占设备总量 60%+） |
| **采集网关** | 网关注册、状态监控、远程配置下发、离线缓存+断点续传 | A/B 双分区磁盘预留，OTA 功能不做 |
| **MQTT 通信** | 网关→Broker→后端 数据上报链路 | EMQX/Mosquitto 部署 |
| **实时监控** | 六大子系统数据展示、设备状态看板、WebSocket 实时推送 | 复用现有前端，适配真实数据 |
| **告警管理** | 4 级告警、阈值配置、实时通知、确认/解除、统计 | 复用现有功能，适配真实设备 |
| **能源管理** | PUE 监控、配电拓扑、能耗统计、五时段电价管理（尖峰/高峰/平段/低谷/深谷，时段与费率均可配置） | 复用现有功能，接入真实电表数据 |
| **用户认证** | JWT + RBAC 三级权限 | 已实现 |
| **数据源管理** | 数据源配置、连接测试、点位批量导入（Excel）、导入预校验 | 新开发 |
| **数据质量** | 通信中断检测、点位数据质量标记 | 基础版，不含漂移检测 |
| **合规基础** | 操作日志 180 天保留、审计记录、数据备份 | 复用+增强现有功能 |

### 风险缓解策略

**技术风险：**

| 风险 | 缓解 |
|------|------|
| 协议兼容性（最大技术挑战） | MVP 只做 Modbus + SNMP，用真实设备验证；建立设备模板库 |
| 2 人团队产能不足 | 最大化复用现有代码；MVP 严格砍需求；保留 20 天缓冲 |
| 网关稳定性 | 离线缓存+断点续传保证数据不丢；网关状态监控及时发现问题 |

**市场风险：**

| 风险 | 缓解 |
|------|------|
| 用户不愿迁移到新系统 | MVP 阶段找 1 个试点机房验证，降低用户切换成本 |
| 电费节省效果不明显 | 先建立基线数据，3 个月后对比验证 |

**资源风险：**

| 风险 | 缓解 |
|------|------|
| 2 人不够用 | MVP 砍到最小：采集+监控+告警。资产/运维/报表全部推迟 |
| 如果只剩 1 人 | 进一步缩减：只做 Modbus 采集 + 实时监控 + 基础告警，其余全部推迟 |

## 功能需求

### 数据采集与协议管理

- FR1: 集成工程师可以配置 Modbus TCP/RTU 数据源（IP/串口参数、从站地址、寄存器映射）
- FR2: 集成工程师可以配置 SNMP v2c/v3 数据源（目标地址、团体名/认证参数、OID 映射）
- FR3: 集成工程师可以配置 BACnet/IP 数据源（设备实例、对象标识符映射）
- FR4: 集成工程师可以配置 OPC-UA 数据源（端点 URL、节点 ID 映射、证书认证）
- FR5: 集成工程师可以配置 MQTT 数据源（Broker 地址、Topic 订阅、消息解析规则）
- FR6: 集成工程师可以配置 HTTP REST 数据源（URL、请求方式、数据解析规则）
- FR7: 集成工程师可以对数据源执行连接测试，验证通信参数是否正确
- FR8: 集成工程师可以通过 Excel 批量导入点位配置表
- FR9: 系统在点位导入时自动执行预校验（寄存器地址冲突、数据类型匹配、量程范围合理性）
- FR10: 系统默认以只读模式首次对接设备，集成工程师可逐台开启写入权限
- FR11: 系统按可配置周期（1~60 秒）自动采集设备数据
- FR12: 系统支持干接点信号通过 Modbus I/O 采集模块转换接入（消防主机、门禁）
- FR13: 集成工程师可以创建和管理设备模板（按厂商/型号预置点位配置）
- FR14: 集成工程师可以导出对接报告（设备清单、点位映射、通信参数）

### 采集网关管理

- FR15: 采集网关上线时自动注册到平台并分配唯一标识
- FR16: 运维工程师可以查看网关运行状态（在线/离线、CPU/内存/磁盘使用率）
- FR17: 系统可以远程向网关下发采集配置（数据源参数、点位表）
- FR18: 网关在与服务器断开连接时自动本地缓存采集数据（≥ 72 小时）
- FR19: 网关在服务器恢复后自动补传缓存数据（断点续传）
- FR20: 系统支持远程 OTA 固件升级（A/B 双分区、灰度发布、失败自动回滚）

### 实时监控

- FR21: 运维工程师可以在仪表盘上查看六大子系统（供配电、制冷、环境、安防消防、智能基础设施、能效）的实时数据
- FR22: 运维工程师可以查看单台设备的详情页面（实时参数、历史曲线、关联告警）
- FR23: 系统实时推送数据变化到前端（延迟 ≤ 1 秒）（当前实现：WebSocket）
- FR24: 运维工程师可以查看设备状态看板（按区域/类型分组的设备在线/离线/告警状态）

- FR26: 运维工程师可以查看数据源连接状态（连接/断开、最后通信时间）

### 告警管理

- FR27: 系统管理员可以为点位配置 4 级告警阈值（提示、次要、重要、紧急）
- FR28: 系统在点位数据超过阈值时自动触发告警（延迟 ≤ 1 秒）
- FR29: 运维工程师可以接收实时告警通知（系统推送 + 声光报警）
- FR30: 运维工程师可以确认、处理、解除告警并记录处理过程
- FR31: 运维工程师可以查看告警统计（按级别/区域/设备类型/时间段）

### 性能

| 指标 | 要求 | 场景 |

| API 响应时间 | P95 < 500ms（常规查询）、P95 < 2s（复杂报表） | 用户操作 |
| WebSocket 推送延迟 | 后端到前端 < 1 秒 | 实时数据刷新 |
| 首屏加载 | ≤ 3 秒 | 登录后仪表盘渲染 |
| 页面切换 | ≤ 500ms | SPA 路由切换 |

| 图表渲染 | ≤ 1 秒 | ECharts 趋势图 |

### 可靠性

| 要求 | 说明 |
|------|------|
| 系统可用率 | ≥ 99.5%（年停机 ≤ 43.8 小时） |
| 优雅降级 | 系统在部分组件故障时应优雅降级（显示最后已知数据 + 状态提示），而非完全不可用 |
| 离线容错 | 网关本地缓存 ≥ 72 小时，服务器恢复后自动断点续传 |
| 数据完整性 | 采集数据不丢失（网络中断期间本地缓存保证） |
| 数据一致性 | 网关补传数据后，中心平台数据与网关本地缓存数据一致性 ≥ 99.99% |
| 数据保留 | 原始数据 90 天、小时聚合 3 年、告警记录永久保留 |
| 数据备份 | 自动每日备份，支持手动备份和恢复 |
| 消防联动可靠性 | 联动策略执行成功率 100%（消防信号最高优先级） |
| 网关故障隔离 | 单台网关故障只影响其负责的物理区域，不影响其他区域 |
| OTA 升级安全 | A/B 双分区，升级失败自动回滚到原分区（Post-MVP） |
| 系统可观测性 | 系统提供自身运行状态的可观测性（服务健康检查、关键指标暴露、错误率监控），支持快速定位系统自身故障 |
| 网关网络冗余 | 网关网络链路冗余，单链路故障不影响采集（当前方案：双网口主备模式，分别接不同端口） |

#### 硬件验收标准

| 设备类型 | 验收测试 | 时长 | 通过标准 |
|---------|---------|------|---------|
| 服务器 | memtest 内存测试 + fio 磁盘压力测试 | 72 小时 | 零错误、IOPS 达标 |

#### 选型说明

1. **采集网关** — 推荐研华 ARK/UNO 系列或华北工控 BIS 系列（¥3,000~8,000/台）。轻量替代方案：EG8208 等 8 串口边缘计算网关（~¥900/台），适合串口需求多但预算有限的场景
2. **MQTT Broker** — EMQX 官方基准：4vCPU/8GB 单节点可支撑 2M msg/s（QoS 0），5,000 msg/s 需求无需独立服务器
3. **NVR** — 海康威视/大华主流型号：16 路 ¥3,000~5,000、32 路 ¥5,000~6,000、64 路 ¥4,200~5,500
4. **服务器** — Dell PowerEdge R260 起价 ¥47,870，推荐 R360/R660。联想 ThinkSystem 同级价格相近。国产替代可选浪潮/华为
5. **数据库存储** — TimescaleDB 压缩比约 10:1，1.5 亿条原始数据压缩后 ~500GB~1TB，4×4TB SSD RAID10 提供充足余量
